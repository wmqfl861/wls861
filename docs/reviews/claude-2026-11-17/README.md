# 2026-11-17 审核：真实运行为何卡住，以及多 Agent 协同

基线：`main@654d232`（实现 0.13.0，蓝图 v0.5，Store 410）。上一轮在 `8d44256`，之后合入 18 个 PR（#121–#138）。

## 结论

1. **过程合规，产品没过线。** 18 个 PR 都符合规则，main 的 CI 15 次全部通过。0.13.0 已出，但 U1、U2 仍未通过：11-16 又发了 58 次真实调用，三次完整请求都没有交付。
2. **卡住的根本原因是一个产品缺陷。** owner 11-15 要求取消金额门禁后加的观察模式，少了一条规则：模型调用拿不到用量时按预留额记账。于是任何一次应答不可用，请求就永久停在“账目未就绪”，重跑也过不去。三个失败的请求都是这样停的，其中两个离交付只差几步。
3. **我的两个决定加重了问题。** 11-16 我让验收改用流式，中转在流里加的非标准内容引出三处解码器拒绝，一天修了两处。我写的两条规则（“两轮即停”“没有改善就回退”）被按字面执行，又停了一条线、退了一个优化。本轮都改回来：验收用非流式，规则改写。
4. **中转约 4% 的调用上游失败，而自动重试是 0。** 30 次调用的请求很难跑完。本轮恢复有界重试（最多 2 次，只对中转没有产出可用应答的情况）。这改变了你 11-15 的指示。
5. **多 Agent 协同：有分工，没有协同。** 四个角色上下级传话，任务不能有依赖，团队之间不能传成果，一次只跑一个调用，没有审核角色。都能加，架构留了位置。建议把“任务依赖与成果传递”“共享笔记板”“独立审核团队”提前到 G6，和并行一起做。详见 `02-collaboration.md`。
