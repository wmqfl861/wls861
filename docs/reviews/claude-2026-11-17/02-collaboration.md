# 02 多 Agent 协同：现状、差距与加法

回答 owner 2026-11-17 的问题：“项目是否有多 agent 协同工作能力，如果没有是否可以加，建议怎么加？”

## 1. 一句话回答

**有多 Agent 分工，没有多 Agent 协同。** 四个角色各自是一次模型调用，由宿主按固定流程逐个驱动，只能上下级传话，不能平级交流；任务之间不能有依赖，团队之间不能传成果，一次只跑一个调用，也没有审核角色。这些都能加，而且架构为它们留了位置。建议把“任务依赖与成果传递”从 G10 提前到 G6，和并行一起做；团队间的信息传递用一块宿主管理的共享笔记板，不做自由对话。

## 2. 现状：有什么

| 能力 | 现状 | 依据 |
| --- | --- | --- |
| 角色分工 | Root 收单与交付，Dispatcher 规划与验收，TeamLead 下指令与检查，Worker 执行。只有 Worker 能动文件和跑命令 | `AGENTS.md`；`src/offline_runtime.cpp:88-99` 的工具目录 |
| 上下级通信 | Dispatcher→TeamLead：任务简报；TeamLead→Worker：工作说明；Worker→TeamLead：提交、提问；TeamLead→Dispatcher：转问、升级；Dispatcher→用户：问题 | 工具 `submit_plan`、`issue_work_order`、`submit`、`ask`、`forward_question`、`escalate_task`、`answer_question` |
| 检查与返工 | TeamLead 检查提交，不合格有限次返工；Dispatcher 验收候选 | `check_submission`、`change_task`、`accept_candidate` |
| 一个请求多个团队 | 可以。11-16 的 R3、R5 都由真实模型建了 3 个任务、3 个团队 | `docs/reports/g2-first-real-run.md` |
| 团队隔离 | 每个团队一个工作区，互不可见、互不可写 | `src/store.cpp:3495`；`src/worker_tools.cpp:584` |
| 全程记录 | 每次调用、每步操作进 SQLite，可恢复 | 契约 |

这是一个纵向的指挥链。把它比作公司：有经理、组长、组员，有汇报和检查，但组员之间不说话，各组之间不交接半成品，所有组按顺序一个一个干。

## 3. 差距：没有什么

| 缺的能力 | 现在的限制 | 依据 |
| --- | --- | --- |
| 任务依赖（B 用 A 的结果） | 计划里的 `depends_on` 必须为空数组，否则拒绝 | `src/tool_descriptions.hpp:85`；`src/offline_runtime.cpp:344`；`src/store.cpp:1613-1614` |
| 成果在团队间传递 | 没有通道。只有 Root 在最后汇总各团队的交付 | 工作区隔离 |
| 并行 | 泵一次只做一个模型调用，团队按顺序执行。R3 的 3 个团队 21 次调用用了 325 秒 | `src/event_runtime.cpp` 的单线程循环；v0.5 §4 第 65 行把并行排在 G6 |
| 平级交流 | Worker 之间、团队之间没有任何通道。Worker 的 `note` 只进自己的历史 | 工具目录 |
| 审核角色 | 计划里的 `review` 节点被拒绝。检查由同一团队的 TeamLead 做 | `src/store.cpp:1614` |
| 跨请求的经验 | `report_experience` 产生经验记录，但没有人读。G8 记忆未开始 | 计划 §9 |
| 被别的 Agent 调用、调用别的 Agent | G9 MCP 服务端、G10-A A2A 未开始 | 计划 §10、§12 |

## 4. 能不能加

能，而且加起来比看上去便宜。原因有三：

1. **Store 已经是唯一事实源。** 任务状态、版本、声明、派发都在数据库里，带 CAS 和事务。协同需要的“谁依赖谁、谁完成了、谁能看什么”都是在这上面加几张表和几条门禁，不用改执行模型。
2. **沙箱刚有了只读输入挂载（G4-N3）。** 把上游团队的已验收快照挂到下游团队的 `/input/<上游任务>/`，就是成果传递。不需要新的通信原语：文件就是消息。
3. **泵的循环是事件驱动的。** 并行不需要重写流程，只需要让多个团队的调用同时在途，Dispatcher 的控制事件保持串行（v0.5 §4 已经这样定）。

v0.4.1 §5.10 和 G10-R 已经写了 DAG 和独立审核团队。欠的只是排期：现在它们排在 v1.0 之后。

## 5. 建议怎么加

按收益与成本排序。每一项都是“宿主管理、全程记录、有界”，不引入 Agent 之间的自由对话。

### C1 任务依赖与成果传递（最先做）

- **做什么。** 允许 `depends_on` 非空。计划校验：无环、节点数上限不变、被依赖的节点必须存在。派发门禁：一个任务的全部上游都 ACCEPTED 之后才进入 READY。下游团队的沙箱里，每个上游任务的已验收不可变快照以只读方式挂在 `/input/<上游节点 id>/`。工作说明里由宿主填入“你的输入在 `/input/<节点>/`，内容是什么”这一段，不靠模型转述。
- **为什么够用。** 绝大多数需要协同的任务都是流水线：A 产出数据，B 用数据做分析，C 把两者写成报告。这是协同里最常见也最可审计的形式。
- **改哪里。** 计划 Schema 与校验（`store.cpp:1613`、`offline_runtime.cpp:344`、`:358`）；派发门禁；工作区绑定时加输入树（复用 G4-N3 的 `input_root` 机制，从一个变成多个）；`current_state` 里给 TeamLead 和 Worker 的输入说明。
- **先串行。** 拓扑排序后仍然一个一个执行，先把语义做对；并行是 C4 的事。
- **验收。** 合成：一个三节点流水线请求，B 读到 A 的文件，C 读到 A 和 B 的文件；A 被改后 B、C 的旧快照不变。真实：一个“先抽取再汇总”的两步请求。
- **规模。** 产品 500 行左右，两个 PR。

### C2 共享笔记板（第二步，小）

- **做什么。** 每个请求一块板。Worker 现有的 `note` 加一个 `share: true` 标志；分享的笔记经 TeamLead 放行后进入请求级共享区。Dispatcher 和所有团队的 TeamLead、Worker 在 `current_state` 里看到一段“共享笔记”，每个团队最多 N 条、合计不超过 2 KB，超出的只给索引，用 `history_read` 一类的工具按需读。
- **解决什么。** 团队 A 发现“CSV 的列名是 X、Y、Z”，团队 B 不用再花一次调用去看。接口约定、路径约定、已知坑，这类信息值得横向传。
- **不做什么。** 不做 Agent 之间的自由对话、不做广播、不做订阅。每条笔记有作者、版本、放行者，可追溯。
- **规模。** 产品 300 行左右，一个 PR。

### C3 独立审核团队（在 C1 之上很便宜）

- **做什么。** 计划节点允许 `review: {"of": "<节点 id>"}`。审核节点就是一个下游任务：它的 `/input` 是被审核任务的候选快照，它的产出是一个固定 Schema 的审核结论（通过 / 不通过 + 逐条理由）。Dispatcher 只有在审核结论为通过时才能 `accept_candidate`；不通过时按既有的有限返工流程打回。
- **为什么要有。** 现在检查者（TeamLead）和被检查者（Worker）在同一个团队、看同一份说明，容易一起错。独立审核是多 Agent 系统里最明确能提高正确率的协同形式。
- **规模。** 在 C1 之上约 300 行。G10-R 里的内容就是这个，可以直接搬过来。

### C4 并行（G6，已在计划里）

- 请求级并行（两个 `wls run` 同时跑）和团队级并行（一个请求里多个团队同时在途）。Dispatcher 控制事件串行；每个团队一个工作线程，模型和工具等待在锁外；并发上限可配。
- 有了 C1，并行的调度规则就是“READY 的任务都可以同时跑”，不需要另一套规则。
- 风险在共享状态的数据竞争，所以先审计、加 TSan（计划 G6-C、G6-T 已有）。

### C5 记忆（G8，已在计划里）

跨请求的协同：第二次做同类任务时用上第一次的经验。计划 §9 不变。C2 的共享笔记在交付确认后可以作为经验候选进入记忆，两者衔接自然。

### C6 与别的 Agent 协同（G9、G10-A，已在计划里）

MCP 服务端让别的 Agent 提交任务、取回交付；A2A 互通。计划 §10、§12 不变。

### 不建议做的

- **Agent 之间的自由聊天室。** 调用数和 token 会失控，结论不可审计，也和“模型的话不是授权”这条不变量冲突。
- **让 Worker 直接写别的团队的工作区。** 破坏隔离，交付的字节核对会失去意义。成果只经由已验收快照的只读挂载传递。
- **在 U1、U2 通过之前开工 C1。** 协同建立在“一个团队能可靠地从头跑到尾”之上。现在还没有。

## 6. 排期建议

| 项 | 建议放在 | 原因 |
| --- | --- | --- |
| C1 依赖与成果传递（串行） | G6 的第一项，G4 之后 | 依赖 G4-N3 的输入挂载；是并行的前提 |
| C2 共享笔记板 | G6 的第二项 | 小；和 C1 同一批真实验收 |
| C4 并行 | G6 原有内容，排在 C1、C2 之后 | 调度规则依赖 C1 |
| C3 独立审核团队 | 从 G10-R 提前到 G8 之前，作为 G6 的最后一项或单独一小段 | 在 C1 之上很便宜；对正确率的收益大 |
| C5、C6 | 不变 | — |

G6 的粗估从 5 到 7 天变为 9 到 12 天。到 v1.0 的总估算相应加 4 到 5 天。具体的修订文字在 `04-plan-revisions.md`。

## 7. 验收时怎么判断“有协同了”

| 能力 | 真实模型上的判据 |
| --- | --- |
| 依赖与传递 | 一个“抽取→汇总→成文”的三步请求：下游团队的产出里有上游产出的内容；上游不被重做 |
| 共享笔记 | 两个并列团队的请求：B 的 Worker 没有读 A 的文件就用上了 A 分享的约定（从调用记录看） |
| 独立审核 | 一个故意留错的候选被审核节点打回；改正后通过 |
| 并行 | 3 个团队并行的墙钟不超过串行的 60%（计划 G6 已有） |

这些判据都来自调用记录和成果核对脚本，不靠主观评价。
