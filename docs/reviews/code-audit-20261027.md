| A04 | 进程证据扫描先以读模式打开 FIFO 再拒绝；增长文件也可比实际预算多读一个块 | O_PATH 类型先检，重开固定普通 inode，实际读取预算只额外允许一个 EOF 字节 |

### 反例如何构造

A01 使用真实 `fork`、子进程析构和另一个竞争 Store 写者；父进程原请求保持，关闭后后继写者仍可恢复。
A02 使用 SQLite 每连接 trace hook 固定“预算读取结束→另一已打开写者提交”的顺序，
没有 sleep 或概率竞态；新实现本次看见旧完整快照、下次看见新预约。
A03 验证控制预留从16到20；三预算维度已知但 cache_write 未知时保持20，五维完整后回到16，
原 attempt 字节不变；争议、超预留及408/410 Fake兼容另有覆盖。

A04 的 FIFO 用 inotify `IN_OPEN` 证明旧代码确实打开过数据通道；增长读取由测试专用 syscall
替身固定在第一次实际读取后追加，观察旧版多读整块与新版16MiB+1上限。
A05 夹具先构造额外尾字节，再只对测试创建的指定 inode 注入短报 statx 长度；
statx 替身本身不改磁盘字节和权限。分别验证 marker
前缀不能建立身份、旧库存前缀不能授权删除追加字节。它验证异常元数据/增长边界，
不声称普通 ext4 总会返回错误长度。
A06 经过真实临时 Store/Fake 的接受、交付、回执与 cleanup，原失败原因明确为
`original_process_exit_proof_missing`；重复执行仍返回原结果，没有再次运行或文件效果。

A07 先完成独立 loopback TLS 工作流，再在临时数据库副本中改来源单列，或同时改
settings 并重新计算其哈希，三个评测版本均验证拒绝且评测自身不写库。
这补齐证据一致性检查；本地所有者能重写全部数据库事实不属于数据库真实性证明。
A08 覆盖非法 octet、短写/八进制/整数/十六进制数字主机与冲突映射，并保留合法 DNS+
显式 IPv4、严格数字主机及原 DNS 运行时分支。A09 用父目录 symlink 和 `link/../source`
验证原路径成分检查，以 IN_OPEN 确认拒绝发生在 Schema 内容打开之前。
A10 修改临时副本中一次完整调用的原生消息并重新计算局部 input/request 哈希，
保持原 admission/send/transport 记录不动，验证 v1/v2/v3 都将矛盾输入判为无效。
A11 先由真实 single-Agent/Fake 运行保存带额外 `0.1` 参数、被 Schema 拒绝的完整响应，
再继续合法流程并完成 publish/ack；原评测仍报 `single-Agent immutable feedback fingerprint mismatch`。
修复后该完整历史有效，另用 C++ 生成的原请求覆盖 `1E0`、`1E-1`、负零和嵌套同名哈希字段，
修改嵌套内容仍会拒绝。真实408/Fake/framed-v1和既有 v1/v2/v3计划身份另做兼容核对。

## 优化与兼容性

优化集中于有明确影响的资源与失败路径：核账完整后释放无用的结算控制容量；
Schema 在累计/读取过程中执行限额；进程证据对增长文件严格限制实际读入；
配置错误在任何模型预约之前返回。没有引入新的全局配置缓存、后台重试或宽松权限。

原版本的完整配置复用仍限定在当前调用栈/事务，并逐次匹配当前字节和 hash。
原结算、业务 UNKNOWN、一次发送权、原十字段绑定、旧 Schema 映射字节入口和已发布 SQL
全部保持。旧的取消缺证据记录仍然保留缺口，不由升级补造过程事实。
原 Store 事实的数字拼写与计划/报告的 Python 规范序列化分别遵循既有生产者；
没有放宽指纹检查，也没有全局改变历史计划和报告的 hash 规则。

### ASan性能复验补充

初始审核候选在普通用户ASan的耗尽重试场景触发原60秒batch deadline；
完整E2E在有并发编译和无其他编译/测试时均失败。同机顺序对照中，原发布版本的原case04
通过，初始候选失败，提前停止的总耗时不能用作速度比较。原失败均保留在验证档案。

诊断按 `pump_workflow` 调用栈区分batch内外。单Agent最慢一批墙钟54.312秒、CPU54.115秒，
完整context恢复累计25.472秒、transcript累计8.213秒；inclusive计时相互嵌套，不能相加。
该批包含两个LEFT JOIN的整条容量查询累计0.007秒。在这次测量中，主要成本来自重复JSON处理。
诊断重编译/插桩/重链接改变了代码布局，其单次通过不替代实际产品门禁。

优化仅涉及纯局部重复工作：同一结构化请求解析中的完整context恢复从三次减为一次，保留原字段、
结构与完整回序列化检查；同次编译和捕获复用prompt字节或长度；单次transcript使用经外层数组
检查的原记录字节构建prefix。每次公开可变请求校验、Store当前权限与历史、原send claim、
原发送编码仍独立验证，没有跨状态缓存或删减完整原历史。新增回归用完整canonical数组作
独立oracle，并覆盖重哈希非法请求、恢复后再篡改、浮点/转义、外层深度及精确字节预算。
后继正式构建、原case04与整仓门禁的实际结果以新验证报告为准。

## 已核对但未作为缺陷修改的疑点

- CLI 交付预检只遍历目标请求，但 Store 提交守卫检查全库 workspace/owned/delivery 根目录，
  反向绑定也检查历史交付根；不能据局部预检推断可跨请求发布。此次未另加重复 Store API。
- 重复 live send claim 的请求版本不构成第二次发送许可；原 claim 返回不含新的发送权。
  现有契约未要求重放 CAS 改变历史指纹，因此没有改写幂等身份。
- 继承连接的任意跨进程数据库使用、任意同 UID 恶意宿主代码和整库事实重写需要独立的
  宿主进程/可信边界设计；这次针对已复现的析构锁影响修复，没有承诺这些新能力。
- Store 大文件拆分、统一多个读取器、服务化并发和自动后台维护仍需专门设计与验收，
  没有为代码形式上的整洁扩大本补丁风险。
