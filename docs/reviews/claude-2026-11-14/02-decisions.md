## 3. 细则

### 3.1 D-20 `acceptance_runtime`

依据见 `01-audit-report.md` §5.2：这个套件在 #79 之后体量翻倍，产品没有变慢。

1. **拆分。** `acceptance_runtime_tests` 增加 `--group` 参数，做法照 `single_agent_tests`（`CMakeLists.txt:121-131`）。CTest 注册成 3 到 4 个。原有用例在 #79 之前在 ASan 下就要 64 到 90 秒，所以也要分开：原有用例分两组，#79 加的两个用例各一组；逐条规则核对的那个用例仍然超过 90 秒的话，按规则表再分一次。Makefile 里整套运行的那一行不变。
2. **验收。** 合并之前在分支上手动触发一次完整矩阵，9 个 job 全绿，并且每个新注册在 CMake ASan 下不超过 90 秒（时限 180 秒的一半）。合并之后 main 的完整矩阵通过。
3. **D-11 补充一条长期规则。** 每次 main 的完整矩阵跑完，看一眼各套件在 ASan 下的耗时占自己时限的比例；超过一半的，下一个 PR 就给它分片。新增或明显加重的套件还没有数据时，按 Release 耗时的 10 倍估算（本轮日志里是 6 到 13 倍），估算值超过一半就在同一个 PR 里分片。按最近三次运行，`acceptance_runtime` 之外最高的是 `r3_evaluation`，占 48.5%，此前出现过 51.5%；下一个改动它的 PR 顺手给它分片。
4. “acceptance 性能问题”这一条关闭。#83、#85 是等价的小优化，保留，不回退。
5. 同一个 PR 里顺带把 `CHANGELOG.md`、`AGENTS.md` 加进 CI 的“只改文档”清单（CI-2）。

### 3.2 D-22 G4-A1 与 G4-B

1. **顺序。** 先 G4-A1，再 G4-B，各自变基到最新 main。G4-B 给 Store 加的守卫要按 #93 之后的文件布局落位。两者的产品行加起来 318，可以合成一个 PR，也可以两个顺序的 PR。

4. **托管 runner 上可以试一次正向路径。** 在手动触发的 `standard-native` 作业里（不是 PR 门禁，不是完整矩阵，不是产品代码），原生检查之前加一步 `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`。托管 runner 是一次性的虚拟机，这不改变产品行为，也不动 owner 的机器。结果照实写：通过就记为“托管 runner 上的正向结果”；仍然 BLOCKED 就写 BLOCKED，不再深挖。
5. **退路。** 出现下面任一情况就不合并，改为停放：变基需要重新设计，而不是机械调整；合并前的完整矩阵修了两轮仍然不过。停放的做法：打标签 `archive/g4/a1-standard-cgroup-20261113`、`archive/codex/g4-b-xqrck4ht`，关闭 #84 并在评论里写明标签名，在收敛报告里记一行。以后从标签拉出新分支继续。

### 3.3 D-23 分支、工作树、标签

1. **最终状态。** 远端只有 `main` 一个分支，没有打开的 PR。本机只有一个位于 `main` 的工作树、一个本地分支 `main`，没有这个仓库的其他克隆目录。
2. **规则只有一条，不逐个判断“有没有价值”。** 分支末端是 `origin/main` 的祖先：直接删。不是：先打 `archive/<分支名>` 标签，推送，核对远端标签指向的提交正确，再删。本机独有、没有推送过的分支同样处理。同名标签已存在且指向别的提交时，用 `archive/<分支名>-<7 位提交号>`。
3. **标签全部保留**：现有的 41 个，加上这次新增的。标签不出现在分支列表里；有它，这次删除随时可以恢复（`git switch -c <新分支> archive/<原分支名>`）。
4. **保险包。** 动手之前做一个包含全部引用的 bundle，连同引用清单放在仓库之外，至少保留 30 天。
5. **工作树里没提交的东西。** 是在途工作：提交到它所在的分支，再按第 2 条处理。是构建产物：随工作树删除。是不足 30 天的原始证据：先移到仓库之外的归档目录（D-12 不变）。
6. 不强推，不改写历史，不删 main，不删标签，不删仓库里的文件。

## 4. owner 要做的事

**1. 提供一个密钥。** 这是唯一卡住项目的事，和上一轮相同，约 5 分钟：

1. 准备一个 OpenAI API 密钥，余额不少于 10 美元。手头是别家端点也行，见 §3.6。
2. 在运行本地 agent 的那个 shell 里执行 `export WLS_G2_API_KEY=<密钥>`。
3. 告诉 agent“密钥已就绪”；如果不是 OpenAI，同时告诉它基址和型号。

**2. 可选：允许 bwrap 使用用户命名空间。** 只在想验收“能跑命令”（G4）的时候才需要，G2 不需要。按 agent 的记录，本机的 AppArmor 拦住了 bwrap 配置回环网卡这一步；这是 Ubuntu 24.04 起的默认限制【查证】。需要 sudo，所以只能 owner 本人做。公开资料给出的做法是给 bwrap 单独加一个配置，比全局关掉限制的范围小：

```
sudo tee /etc/apparmor.d/bwrap >/dev/null <<'EOF'
abi <abi/4.0>,
include <tunables/global>

profile bwrap /usr/bin/bwrap flags=(unconfined) {
  userns,

  # Site-specific additions and overrides. See local/README for details.
  include if exists <local/bwrap>
}
EOF
sudo systemctl reload apparmor
```

它的作用是让 `/usr/bin/bwrap` 可以照常使用用户命名空间，本机任何用户通过 bwrap 都能这样做。撤销的办法是先执行 `sudo apparmor_parser -R /etc/apparmor.d/bwrap` 卸载它，再删掉这个文件。这段配置来自公开文章（`01-audit-report.md` §11），我没有在 owner 的机器上验证过；执行前先确认本机确实是带这项限制的 Ubuntu。做完告诉 agent“bwrap 已放开”，它会重跑原生检查。

**3. 可能需要点两下。** D-24 的两项仓库设置，如果 agent 的令牌没有权限：仓库 Settings → General 勾选 “Automatically delete head branches”；Settings → Branches 给 `main` 加一条规则，不勾任何必需检查，保持“Allow force pushes”和“Allow deletions”为关闭。

**不需要 owner 做的**：收敛的全部步骤、G4 分支的处置、CI 修复，agent 按本目录执行即可。

**如果连标签也不想留**：说一声“标签也删”。那一步不可恢复，所以这里没有替 owner 定。
