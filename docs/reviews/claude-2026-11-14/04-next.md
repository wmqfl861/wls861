### N1 停止时的提示说实话

- 对应：LIVE-26。
- 位置：`src/run_cli.inc:340-345`。
- 问题：几种终局性的停止，摘要给的下一步都是“解决原因后再执行同一条命令”，照做只会撞上同一个限制。
- 做法：先逐个核对哪些停止原因是终局的（下表是读代码得出的判断，以核对结果为准），给它们单独的提示。

| 停止原因 | 能不能用同一条命令继续 | 提示里要说清的事 |
| --- | --- | --- |
| `correction_limit` | 不能，失败计数是持久的 | 模型在同一个动作上连续失败到了上限；最后一次失败的原因；要继续就用新的请求 |
| `stall_same_error_repeats` | 不能 | 同上 |
| 连续两次输出截断 | 不能 | 同上；另外提示调大该角色的最大输出，或把任务拆小 |
| `wall_clock_exceeded` | 不能，墙钟从请求创建时算起 | 调大 `max_wall_minutes` 后用新的请求 |
| `total_call_limit`、预算用尽 | 不能，上限在请求创建时冻结 | 调大对应的上限后用新的请求 |
| `paid_retry_limit`、中途断开、单次命令的调用数到限 | 能 | 现有提示不变 |
| 等待回答 | 回答后能 | 现有提示不变 |

  “用新的请求”要写成用户能照做的话：改动请求文本，或者把配置复制到一个新目录再执行。README 的运行一节加三行说明同样的事。
- 验收：每种终局停止各有一个断言，提示里有“不能继续”的意思和具体原因；能继续的几种提示不变。
- 产品行预算：30。

### N2 成果核对脚本

- 对应：11-13 `04-plan.md` G2-6 报告的“成果核对”一栏；G3-B 缺的共同核对标准。
- 做法：新增 `scripts/check_g2_outputs.py`，输入 `wls run` 导出的 `output/` 目录和任务名（`smoke` 或 `three`），按 11-13 `04-plan.md` 附录 A 的预期结果逐项核对，输出 JSON：每一项通过与否、没通过的原因、总的结论。

| 文件 | 核对点 |
| --- | --- |
| `hello.md` | 内容恰好是那三行（允许结尾换行） |
| `meeting.md` | 有“背景”“决定”“待办”“风险”四个二级标题；“待办”里同时出现“周”与“11 月 17 日”、“陈”与“11 月 24 日”；“风险”里提到紧急通道 |
| `summary.csv` | 表头 `region,orders,total`；随后恰好三行，依次是 `华东,4,4100`、`华北,4,3850`、`华南,4,2650` |
| `summary.md` | 提到华东；出现 38.7% |
| `faq.md` | 修订记录之前恰好 5 个三级标题；第 3 个答案不超过 40 个汉字；末尾有标题含“修订记录”的一节 |
| 交付范围 | `output/` 下一共只有这 4 个文件（不论在哪个节点目录下） |

- 测试：一个只用 Python 的测试，给每条规则各准备一份合格样本和一份不合格样本。注册为快速测试，不依赖 `wls` 二进制。
- 用法：G2-3、G2-4、G2-5 的报告直接贴它的输出；G3 的三种条件用同一个脚本核对，结果才可比。
- 边界：它只核对这几个固定任务的确定性要求，不是通用的质量评估，也不评价文字好坏。
- 不改产品代码。测试行预算：200。

只有 owner 给的是别家 Chat 端点时才做。先探针，探针没有暴露的不做。每项一个小 PR，各带一个合成端点上的回归。

| 编号 | 做法 |
| --- | --- |
| CHAT-1 | provider profile 增加一个冻结的“附加请求字段”对象，原样并入请求体，计入 profile 指纹。用它发端点自己的开关，首先是把思考关掉。应答里非空的 `reasoning_content` 一类字段：记录键名，不派发，不计入文本。只有 owner 明确要用带思考的型号、并且该端点要求回传时，才做“在后续请求里原样带回”，那一项要改历史的编码，单独评估 |

| CHAT-3 | provider profile 增加方言选项：`openai`（现状）和 `minimal`（只发 `model`、`messages`、`tools`、`tool_choice`、`max_tokens`、`stream`，函数定义里不带 `strict`） |
