## 1. 总体判断

项目已建立较完整的持久化执行基础：身份与修订分离、事务 CAS、原反馈/原结算保留、
一次性副作用派发、UNKNOWN 围栏、按请求恢复、受控交付与工作区清理都有实际代码和回归。
本轮针对 Store 和运行器的重点审阅未确认新的跨请求越权、CAS 绕过或 UNKNOWN 被错误清除。
这只描述已检查路径，不证明所有输入、并发排列和部署环境都没有缺陷。

当前产品仍处于 FakeModel 与离线协议阶段。R3.1/R3.2 的本地 Completed 不证明真实模型可用，
大量回归也不回答多角色是否比单 Agent 改善质量、费用或耗时。最有价值的下一步是把现有
机制接成一个可核对账目的小型真实闭环，再按证据扩大容量和并发。

本轮五类确认缺陷都来自模块交接或异常路径：合法业务文件名与清理名称规则不一致；
只读诊断在类型检查前实际打开特殊文件；哈希检查把声明大小当作实际 EOF；
严格协议夹具漏掉默认传输字段；新 CLI 有输入预检而旧命令和最终错误输出未贯通。
因此测试应增加“上游合法输出可以进入下游”和“失败过程本身保持契约”的反例，
不能只分别证明各模块的常见成功输入。

## 2. 审核方法与范围

从当前源码、实施契约与蓝图重新核对，分开审阅协议、文件系统和 Store/运行器，再交叉检查补丁。
协议依据另核官方资料；新反例链接原发布基线静态库或调用原基线 CLI，先保存实际失败，
再对最小修复进行验证。没有执行生产请求、真实模型或付费尝试。

这是同一模型体系下分开执行的工程审阅，不能登记为 S2 所要求的独立第二模型业务验收。
没有做全面模糊测试、整机掉电、任意同 UID 对抗、真实供应商能力或强沙箱部署验收。

重点范围：`store.cpp` 的预约/结算/派发/恢复与 AMEND，`store_cleanup.inc` 的清理准入，
`cleanup_runtime.cpp` 的分配收据/发布，原反馈与 Worker 历史窗口，事件领取/完成，
provider profile、HTTP/SSE 编解码，sandbox/doctor 固定字节，Workspace 与清理路径，CLI 输入和错误。

## 3. 确认问题及直接修复

本轮五项均定为 P2：已可复现的证据、只读承诺、兼容性、可恢复性或输入处理缺陷。
没有据本轮证据定为 P0/P1 的问题；不把诊断假阳性扩大为执行授权已被绕过。

| 编号 | 级别 | 基线行为及实际影响 | 修复位置与规则 |
| --- | --- | --- | --- |
| A1 | P2 | `pin_file` 及共享配置/运行输入读取器先 `O_RDONLY` 打开再检查类型。FIFO 即使加 `O_NONBLOCK` 也发生打开，可唤醒等待对端；运行源、doctor manifest/config 和两类读取器夹具均观察到 `IN_OPEN` | [sandbox_posix.cpp](../../src/sandbox_posix.cpp)、[config_loader.cpp](../../src/config_loader.cpp)、[offline_runtime.cpp](../../src/offline_runtime.cpp)：先 `O_PATH` 固定并检查普通文件，再通过自己的 fd 重开同一 inode 并复核元数据；特殊文件不进入读模式，内核读权限与原路径守卫保留 |
| A2 | P2 | doctor 读到 `st_size` 就停止，未验证 EOF。固定 `/proc/sys/kernel/ostype` 是普通文件、声明大小 0、实际非空，原实现可验证空 SHA 并报告运行文件已就绪 | 同一 `pin_file`：在实际预算内证实 EOF；多读到的失败哨兵字节计入预算，预算恰满则 `not_checked`，不能生成完整 SHA/identity 成绩。生产 sealed memfd 与原权限守卫保留 |
| A3 | P2 | Workspace 可创建反斜杠、换行、制表符等合法 UTF-8 POSIX 名称，cleanup 却套用资源标识规则拒绝，导致合法成果无法进入清理清单 | [cleanup_posix.cpp](../../src/cleanup_posix.cpp)：业务条目 basename 与运行时资源/staging ID 分开校验。保留 JSON 原字节、相对路径/无链接/原代次/清单删除检查；资源 ID 仍严格 |
| A4 | P2 | 非 UTF-8 未知命令使错误 JSON 再次抛异常并以 SIGABRT 退出；非 UTF-8 admission key 在原 CLI 可成功建库准入；错误信息长度未统一约束 | [cli.cpp](../../src/cli.cpp)：所有 argv 在读文件/Store 前验证 UTF-8；错误原消息前缀最多 4096 字节，截断/原长度显式，无法表示的前缀用 hex 保留，异常处理有固定 JSON 兜底 |
| A5 | P2 | 支持的两类 SSE delta 白名单拒绝官方默认 `obfuscation`，合法文本/函数参数流被当作未知字段拒绝；原自建夹具未覆盖 | [sse_replay.cpp](../../src/sse_replay.cpp)：仅两类已支持 delta 接受可选字符串填充，保留 raw 和观测计数，受原输入容量约束，不混入文本/参数；其他字段/类型仍拒绝 |

A2 是诊断证据假阳性，不代表原生产执行器已绕过冻结字节验证；原生产读取会发现非空内容。
A3 不批准清理外来目录或任意路径，也不扩大条目/字节删除上限。
A4 的预检范围是 argv；不声称所有文件内容都已在副作用前完成业务校验。正常短 Unicode 错误
继续使用原 `{error,message}` 形状；4096 是原消息前缀字节数，JSON 转义/hex 后的整行可以更长。
A5 的计数是已解析填充字段及其解码后 UTF-8 字节，不等于 wire 字节数或后续事件校验成功。

官方依据为 [OpenAI Python SDK 的 StreamOptions](https://github.com/openai/openai-python/blob/main/src/openai/types/responses/response_create_params.py)
（2026-10-26 检索），它说明 delta 填充默认开启。API Create 参考页因页面超过读取上限未能完整获取，
没有把未读取的整份规范当作已核验。没有以关闭填充或放开任意未知字段替代兼容修复。

## 4. 回归设计与证据解释

新增 16 个独立注册用例：doctor 2、cleanup 3、sandbox 1、SSE 3、配置读取 1、运行输入读取 1、CLI 5。
原 SSE 全部二块切分/BOM/CRLF/Unicode 用例增加填充字段，原断言保留；原 doctor CLI 特殊输入
用例增加 manifest/config 的真实 FIFO 打开观察，两个 subtest 不重复计作新增注册用例。
反例覆盖特殊文件无读打开、实际 EOF 与预算恰满、合法名称跨创建/清单/分批删除、
路径穿越与严格资源 ID 继续拒绝、非法参数零建库、长错误边界和原 Unicode 兼容性。

基线 CLI 的新增套件实际出现两项失败与两项错误；其中 admission key 反例是原实现返回成功，
命令反例是 SIGABRT，长消息两项则缺少新契约要求的截断事实。它们不能混写成四次崩溃。
doctor 两个新反例、合法名称清理反例以及含填充的 SSE 反例均有原实现失败日志。
共享配置/运行输入读取器和 doctor manifest/config 的加强反例也分别保存原实现的失败日志。
新增的守卫反例和预算边界用例不都属于原缺陷，不能全部声称“基线失败”。

正式验证继续使用原完整 CTest、普通用户、两种调用 umask 和受影响组的 ASan/LSan、UBSan；
最终提交仍核对六路远端 CI 与源码快照。开发期间曾在测试文件编辑中启动构建，遇到重复测试
函数的编译失败；该日志保留，修正后重建，不把失败过程从报告删除，也不增加超时或放松断言。
具体成绩、有效 umask 和日志/源码哈希以[验证报告](../reports/independent-audit-validation.md)为准。

## 6. 保留的风险与明确未做

强 bwrap/cgroup 正向、进程逃逸/残留恢复、真实供应商能力和成本质量仍需独立验收。
profile 可配置 reasoning effort 不表示解码器已支持 reasoning 输出项；首次真实模型须核验
当前文本/function 子集，或先单独增加版本化支持，不能静默忽略不支持的语义。
历史函数消息与 `tool_calling` 能力的含义应先定义，本轮未据字段名称猜测并修改行为。

并发租约、管理上下文、全量记忆、跨功能审核、private-row purge 和常驻服务均仍开放。
本轮没有因测试通过扩大当前产品声明，没有修改原 handoff、历史审核原件、SQL、vendor 或 CI 时限。
