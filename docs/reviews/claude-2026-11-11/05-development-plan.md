# 05 后续开发计划

依据 `02-optimization-plan.md` 的方向和 `04-fix-list.md` 的条目。阶段编号沿用 G 系列；G0–G3 保持 11-06 登记的含义，G4 起为新增。执行顺序是 **阶段 0 → G1 → G2 → G4 → G3 → G5 → G6 → G7 → G8 → G9 → G10**。

时长是按“一个 agent 串行推进、每个 PR 半天到一天”的粗估，只用于排期参考，要按实际进度校准。

## 1. 工作规则

### 1.1 每个 PR 的完成标准

1. 直接基于 main，不堆叠在未合并分支上。
2. `src/` 与 `include/` 的增删合计不超过 800 行；超过就拆。
3. 测试只写三类：新功能的正向用例、被修缺陷的回归、不变量的反例。D-6 采纳后，测试行数不超过产品行数的 2 倍。
4. PR 说明一页以内，四段：改了什么、为什么、怎么验证（命令与结果）、没做什么。
5. CI 通过。
6. 不新增 `docs/reports` 文件，除非是本计划点名的里程碑报告。
7. 提交信息写清动机；代理身份写 `Co-Authored-By`。

### 1.2 节奏

- 同时在制的 PR 不超过 3 个。
- PR 开出后 48 小时内必须有结论：合并，或者写明原因后关闭。
- 合并权限按 D-1。D-1 未决定时，agent 每天向 owner 列一次待合并清单（PR 号、一句话说明、CI 状态）。
- 合并后才更新 `docs/STATUS.md`。

### 1.3 卡住时怎么办

某项工作超过行数预算的 2 倍，或超过 2 天没有可合并的结果：停下来，用 10 行以内写清卡在哪里，提出一个更小的切法，交 owner 选择。不允许靠增加证据材料、复现矩阵或审核轮次来“推进”。

### 1.4 必须先问 owner 的事

- 任何真实或付费的模型调用（需要 D-2、D-3）。
- 数据库版本变更、已发布 SQL 的任何改动。
- 删除分支、标签、数据或历史档案；强推。
- 本计划之外的新功能或新工具链。
- 标了“需 D-x”的条目在对应决定作出之前。

### 1.5 每阶段结束要更新的文档

`docs/STATUS.md`（当前能力与缺口）、`CHANGELOG.md`（一条）、本文件的阶段状态表（§2 的“状态”列）、该阶段的一页里程碑报告。

## 5. G2：首个真实闭环

前提：D-2（端点、模型、凭据环境变量名）和 D-3（预算、重试）已由 owner 书面给出。凭据只放在 owner 本机的环境变量里，不进仓库、不进日志、不进任何文档。

| 步骤 | 内容 |
| --- | --- |
| G2-1 | 在仓库之外写一份真实端点的配置：模型条目、四项单价、预算上限、各角色的模型与思考等级 |
| G2-2 | `wls doctor` 检查域名解析、TLS、代理（如需要）；不发模型请求 |
| G2-3 | 冒烟：一个最小请求，预算上限设为计划值的十分之一。确认用量与费用估算有值、缓存字段被记录 |
| G2-4 | 跑 3 个只用文件工具的小任务，任务文本预先固定并提交到 `tests/fixtures/g2/`：①按给定要点写一份结构化文档；②根据请求文本里给出的数据生成汇总表；③先生成一份文件，再按第二条要求修订它 |
| G2-5 | 如果有三个可用模型，三个角色各用一个；只有一个模型时三个角色用不同的思考等级，并在报告里注明 |
| G2-6 | 一页报告 `docs/reports/g2-first-real-run.md`：每个任务是否完成、调用次数、格式错误次数与类型、纠正次数、四项 token、缓存读取占比、估算费用、耗时、失败与未知样本原样列出 |
| G2-7 | 按报告修最影响成功率的问题，最多 3 个小 PR，然后重跑一次 |

出口：U1、U2 达成，或者报告明确写出没达成的原因和下一步。失败样本不删除、不改写。

停止条件：单个请求触达预算上限；连续 3 次同类格式错误；任何 UNKNOWN。出现任一情况都停下来报告，不自行加预算。
