## 1. 目标与成功标准

构建通用 C++ 多 Agent 系统：Root 对外；每个请求一个 Dispatcher；多个 TeamLead + Worker 一对一团队并行工作；中途修改能准确落到执行；验收后统一交付并清理；经验能积累和演化；能用现有模型端点、MCP 和 Skill，也能被别的 Agent 调用。

成功标准按用户能感知的结果来写，每个阶段至少对应一条：

| 编号 | 用户能看到的结果 |
| --- | --- |
| U1 | 一条命令提交任务，真实模型完成，拿到交付包和费用明细 |
| U2 | Dispatcher、TeamLead、Worker 用三个不同的模型或思考等级跑通同一请求 |
| U3 | Worker 能运行 Python、git 等命令完成数据处理或代码任务 |
| U4 | 执行中途发修改，未受影响的任务继续，受影响的任务按新要求返工 |
| U5 | 换一个不同协议的端点，只改配置不改代码 |
| U6 | 两个请求同时跑、一个请求内多个团队同时跑，互不串扰，总时长明显短于串行 |
| U7 | Worker 能调用一个现成的 MCP 服务器，能加载一个现成的 Skill |
| U8 | 第二次做同类任务时系统自动用上第一次的经验，并能看到它用了哪条 |
| U9 | 别的 Agent 通过 MCP 提交任务并取回交付 |
| U10 | 交付确认后临时目录和运行记录被清掉，交付包、经验和回执还在 |

## 2. 设计原则

1. **不变量守死，其余可配。** §14 列出的不变量由运行时强制；其余全部是带默认值的配置，默认值偏向可用。
2. **先真实运行，再加防护。** 新防护必须来自真实运行里出现过的问题，或 §14 的直接要求。
3. **宿主管状态，模型管判断。** 身份、版本、权限、预算、幂等由程序保证；模型只看到完成任务需要的信息，不看哈希、ID、内部记账。
4. **稳定在前，变化在后。** 发给模型的每个请求都按“越稳定越靠前”排列，历史只追加。
5. **小步合并。** 每个能力拆成可独立合并的小改动，合并标准是 CI 通过加一页说明。

## 3. 架构总览

```
            CLI / 本地 API / MCP Server
                       │
                  RootGateway        准入、幂等、路由、交付、回执
                       │
        ┌──────────────┴───────────────┐
   请求 A（独立目录与数据库）       请求 B ...
        │
   Dispatcher ── 计划、变更处置、验收
        │
   ┌────┴─────┬──────────┐
 Team 1     Team 2     Team n        TeamLead + Worker，一对一，并行
   │
 Worker ── 工具：文件 / 进程(沙箱) / MCP / 记忆

 横向模块：
   Store（SQLite，状态与事件）      ContextCompiler（布局与缓存）
   ModelAdapter（多协议）           ToolRegistry + Sandbox
   Delivery + Cleanup               MemoryEngine（同进程独立模块）
```

| 模块 | 职责 | 相对现状的变化 |
| --- | --- | --- |
| RootGateway | 准入、幂等、路由、交付、回执 | 增加“一条命令跑完”的编排入口 |
| Engine / Store | 状态、事件、修订、预算、恢复 | 语义不变；每请求一个库；按子域拆分源文件 |
| Agents | 四角色运行器 | 增加纠错回路、快路径、团队级并行 |
| ContextCompiler | 上下文布局 | 重排线上顺序，见 §6 |
| ModelAdapter | 模型协议 | 从单协议变为多协议，见 §5 |
| Tools / Sandbox | 工具与进程隔离 | 工具带说明；沙箱两档，见 §7 |
| Delivery / Cleanup | 交付包、回执、清理 | 默认清运行态，见 §11 |
| MemoryEngine | 记忆 | 新增，见 §9 |
| Interop | MCP 客户端与服务端、Skill、A2A | 新增，见 §8 |

## 4. 角色与执行模型

### 4.1 职责

沿用 v0.4.1 §4.1：Root 只做技术准入和交付；Dispatcher 规划、处置变更、验收；TeamLead 把任务和变更翻译成当前说明并检查成果；Worker 是唯一执行业务工具的角色。修订、状态机、AMEND 处置、恢复沿用 §5.2–§5.9。

### 4.2 标准流程与快路径

标准流程：Dispatcher 出计划 → 每个任务的 TeamLead 出说明 → Worker 循环执行并提交 → TeamLead 检查 → Dispatcher 验收 → TeamLead 写经验 → Root 交付。

快路径用来减少固定开销，逐项可配，默认开启前两项：

| 快路径 | 条件 | 省掉的调用 |
| --- | --- | --- |
| 模板计划 | 功能模板声明了固定的单任务计划 | Dispatcher 的规划调用 |
| 检查与经验合并 | TeamLead 检查通过 | 一次调用里同时提交检查结果和经验报告 |
| 说明沿用 | 纯代次恢复、语义未变 | TeamLead 重写说明（v0.4.1 已有） |

快路径不改变任何权限和版本检查。四角色的收益和开销用 §16 的对照评测量化，评测结果用来调快路径，不用来否定四角色架构。

### 4.3 并行

- **请求级**：每个请求有独立目录 `<data>/requests/<request_id>/`，里面是它自己的数据库、工作区和交付目录；一个进程推进一个请求。全局只有一个很小的登记库，记录幂等键到请求目录的映射和保留的回执。请求之间没有共享写锁。
- **团队级**：同一请求内，每个活动团队一个执行线程。Store 调用是短事务，模型调用和工具执行在锁外等待。并发上限取 `limits.max_teams_per_request`、每端点并发和工具并发。Dispatcher 的控制事件保持串行。
- **审核预留**：沿用 v0.4.1 §5.10 的双容量，在独立审核团队实现时一并落地。

### 4.4 错误分级与纠错

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| 可纠正 | 只回文字不调工具；参数不合 Schema；调用未声明的工具；读不存在的文件；工具返回已结算的失败 | 把错误作为工具结果或提示交还模型，继续同一批；同一目标连续 3 次（可配）后转为阻塞并上报 |
| 可重试 | 未收到任何响应字节的连接失败、429、5xx | 重新预留预算后带退避重试，默认最多 2 次 |
| 必须停 | UNKNOWN 副作用、权限不符、预算不足、取消、超时、存储错误、不变量被破坏 | 立即停止该团队的新业务，保留待办，等待核对或人工处理 |

每次纠正和重试都是一次完整记账的尝试。

## 5. 模型适配层

### 5.1 统一内部请求

ContextCompiler 产出与供应商无关的结构化请求：工具列表、系统文本、任务契约、历史回合、本次状态、允许的工具、模型与思考选择。适配器只负责把它映射成具体协议，不改变内容顺序。

### 5.2 协议适配器

| 适配器 | 协议 | 覆盖 | 顺序 |
| --- | --- | --- | --- |
| `openai-responses` | Responses | OpenAI 及实现了该协议的网关 | 已有，补齐推理项、拒绝、别名 |
| `openai-chat` | Chat Completions | 兼容面最广，多数第三方端点和本地推理服务 | 第二个；若首个真实端点只支持它，则提到最前 |
| `anthropic-messages` | Messages | Anthropic 及兼容网关 | 第三个 |
| 其他 | Gemini 等 | 按需 | 有具体需求再加 |

每个适配器交付时附一组官方样例的离线回放测试。第三方端点对协议的支持程度不一，接入前按端点核验。

### 5.3 能力表与价格表

每个模型条目写明：协议、端点、凭据环境变量名、上下文长度、最大输出、是否支持工具调用、并行工具调用、流式、思考档位、缓存方式（无、自动前缀、显式断点），以及输入、缓存读、缓存写、输出四项单价。未知的能力按不支持处理。费用按冻结单价估算并标明“估算”，供应商给出实际金额时以实际为准。

### 5.4 宽容解码

- 原始响应字节始终完整保存。
- 元数据位置（顶层、usage 明细等）出现未知字段：忽略，并把未知键名记入证据。
- 输出项里出现未知类型：该项不执行；若响应因此没有可用内容，按“可纠正”处理。
- 语义位置的已知字段类型不对：按错误响应处理。
- 响应里的模型名允许与请求名不同，按别名表核对。

### 5.5 思考语义、继承、重试

思考语义和逐字段继承沿用 v0.4.1 §8.2–§8.3。重试按 §4.4：默认 2 次，只针对未收到响应字节的失败；每次重新预留；已收到部分响应的不重试，其费用按未知保留预留额。

### 5.6 传输

- 域名解析：宿主在截止时间内解析出地址后交给 libcurl（沿用现有的显式地址映射路径），解析超时即失败。不要求 c-ares，不引入独立解析进程。
- 代理：默认不用；配置里显式给出代理地址时启用。证书和主机名校验、截止时间、取消语义不变。
- 同一批内对同一端点复用连接。

## 6. 上下文与缓存

### 6.1 线上布局

所有协议都按下表的顺序发出，越靠上越稳定：

| 段 | 内容 | 何时变化 |
| --- | --- | --- |
| ① 工具 | 该角色的完整工具集，按名字排序，每个带说明 | 同一请求内同一角色不变 |
| ② 系统文本 | 通则、角色提示、功能提示、环境卡片、固定加载的规则与 Skill 索引；纯文本 | 同一请求内同一角色和模板不变 |
| ③ 任务契约 | 请求原文、约束目录、任务、当前说明、验收项 | 只在 AMEND 或新说明时变；变化以追加一条“契约更新”表达，不改写旧条目 |
| ④ 历史 | 模型输出、工具调用、工具结果 | 只追加 |
| ⑤ 本次状态 | 预算余额、待办事件、本次捕获的目标、本次允许的工具、记忆卡片 | 每次不同；不写入历史 |

规则：
- 团队唯一的值（工作区标识、策略哈希等）不进 ①②。
- 适配器映射：Responses 用 `tools`、`instructions`、`input`；Chat Completions 用 `tools`、system 消息、其后的消息；Messages 用 `tools`、`system`、`messages`，并在 ②、③、④ 末尾各放一个缓存断点。
- 时间戳、随机 ID、宿主路径不进 ①–④。

### 6.2 追加与折叠

历史默认只追加。当估算的输入长度超过上下文窗口的 `compaction_at_fraction`（默认 0.6）时做一次**批量折叠**：把最旧的一半回合替换成一条折叠记录，写明回合范围、每回合的工具名和结果摘要、原记录的引用。折叠是确定性的，不调用模型。折叠后前缀只变化这一次，之后继续追加。被折叠的原始结果可用 `history_read` 按文本分页取回。任务契约、未决副作用、未答问题、当前说明不参与折叠。

### 6.3 工具集稳定

同一角色每次调用声明同样的工具。本次调用实际允许的子集有两道限制：协议支持时用协议自带的允许列表；同时宿主对每个工具调用做权限检查，越权调用作为可纠正错误返回。

### 6.4 不发给模型的内容

来源元数据、记录哈希、attempt 与 call 的内部 ID、base64 副本、配置依赖哈希、审计性质的否定声明。这些留在 Store 里作证据。模型需要引用历史记录时用短序号。

### 6.5 计量

每次尝试记录输入、缓存读、缓存写、输出四项 token 和估算费用，未知为空。按角色汇总缓存读取占比，写入请求的费用明细。输入预留用按协议的 token 估算，不再用字节数。

## 7. 工具、沙箱与基础包

### 7.1 工具注册

每个工具必须有：名字、给模型看的说明、参数 Schema（每个参数有说明）、副作用类别、是否幂等、超时、类别（业务、诊断、控制）。没有说明的工具不能注册。提示词里提到的工具名必须能在注册表里找到，由一个测试强制。

### 7.2 文件工具

沿用现有的限根、整文件 SHA 保护、原子写入。调整：`fs_read` 默认只返回文本，二进制才返回 base64；单文件读写上限和提交体积上限改为配置项；`/input` 接通只读输入。

### 7.3 进程工具与沙箱档位

| 档位 | 文件系统 | 网络 | 后代清理 | 资源上限 | 用途 |
| --- | --- | --- | --- | --- | --- |
| `standard`（默认） | 只读挂载系统运行目录（`/usr` 及其符号链接、必要的 `/etc` 白名单）；`/work` 可写；`/input` 只读；独立 `/tmp` | 默认断开；功能模板可显式声明放行 | PID 命名空间：其中 1 号进程退出时内核终止全部后代 | 有 cgroup 委派时用 cgroup；没有时用 rlimit 加墙钟超时 | 通用任务 |
| `strict` | 现有的逐文件封存清单 | 断开 | PID 命名空间加 cgroup | cgroup，缺失即拒绝 | 高保障场景 |

两档都：不继承宿主环境变量和凭据、丢弃全部能力、不挂载宿主 home 和控制数据库。宿主不满足所选档位的前提时拒绝执行并给出原因，不静默降级。`doctor` 报告当前宿主能用哪一档。操作生命周期、UNKNOWN 语义沿用 v0.4.1 §9.5。

### 7.4 环境卡片与基础包

基础包是宿主上预装的一组常用程序（bash、coreutils、python3、git、ripgrep、jq 等），由功能模板的环境定义列出。团队启动时在沙箱里实际执行检查命令，把“可用工具、版本、用法示例、缺失项”写进环境卡片。卡片的稳定部分进 ②；检查结果参与缓存指纹。卡片不是权限。

### 7.5 MCP 工具

MCP 服务器提供的工具注册为 Worker 工具，名字加服务器前缀，默认按“有外部副作用、非幂等”对待，经功能模板显式授权后才可见。

## 8. 生态互通

| 能力 | 目标 |
| --- | --- |
| MCP 客户端 | 支持 stdio 和 Streamable HTTP；实现 `tools/list`、`tools/call`；以规范 2026-07-28 为准并兼容仍在使用旧握手的服务器；服务器清单写在功能模板里 |
| Skill | 读取 Agent Skills 格式的目录（`SKILL.md` 加资源文件）；模板固定加载的 Skill 把名字和说明放进 ②，正文按需加载；Skill 自带脚本经沙箱执行 |
| MCP 服务端 | 暴露 submit、status、amend、answer、get_delivery、ack、cancel，全部走 RootGateway |
| 功能互调 | 计划节点可以是“调用另一个功能的 Root”，走与外部请求相同的入口 |
| A2A | 有明确对接对象时再做 |

协议版本和可用的 C++ 库在开工时核验。MCP 是基于 JSON-RPC 的协议，可以用现有的 JSON 库、子进程和 HTTP 组件实现最小客户端。

## 9. 记忆 v1

模块边界、内容布局、四态、版本与加载绑定沿用 v0.4.1 的 `03_记忆系统v1规格`。分两步交付：

**第一步：最小闭环**
- 存储：Markdown 正文放 Git 目录，分 `rules`、`facts`、`experiences`、`skills`；SQLite 存元数据、标签和全文索引。
- 写入：经验报告的条目进入 `draft`；`personal` 治理下，项目作用域内的事实和经验可自动转 `active`；规则、脚本、扩大作用域要人工确认。
- 读取：模板固定的规则确定性加载进 ②；其余在任务开始、说明变化、工具报错时按标签和关键词检索，以卡片形式放进 ⑤；Worker 用 `recall` 和 `load_memory` 取全文，全文作为工具结果进 ④。
- 反馈：提交时声明实际用了哪条记忆的哪个版本、效果如何，按版本统计。

**第二步：演化**
- 同一问题的不同方法并存，按验证结果调整权重；多次验证后合并，矛盾部分归档。
- 撤销先生效于派发门禁，再通知。
- 向量检索在关键词检索不够用时再引入。

## 10. 状态、存储与恢复

沿用 v0.4.1 §5.8、§5.9、§14.2 的全部语义。变化只有三点：

1. **每请求一个库**（§4.3）。删除请求目录就是删除它的全部私有记录。
2. **Store 按子域拆分源文件**：准入与配置、任务与修订、操作与结果、模型尝试与账本、工作流（问答、提交、验收）、交付与清理、历史读取。只移动代码，不改 SQL、事务范围和公开接口；每个 PR 只移一个子域。
3. **语句缓存**：预编译语句按 SQL 文本缓存复用。

数据库版本保持 410，直到有功能确实需要新表。

## 11. 交付与清理

交付包、回执沿用 v0.4.1 §10.1–§10.2。清理默认值改为：回执确认并且经验报告完成后，自动删除该请求的工作区、输入副本和运行数据库；保留交付包、经验、回执和一行登记记录，保留期默认 30 天。存在未核清的 UNKNOWN、未完成的经验报告或未确认的交付时不清理，并说明原因。可配置为“全部保留”。

## 12. 接口

| 命令 | 作用 |
| --- | --- |
| `wls run --config FILE --text-file FILE [--budget-usd N]` | 提交并推进到交付或阻塞，打印进度、费用明细和交付位置 |
| `wls status / amend / answer / cancel / deliver` | 查看、修改、回答问题、取消、确认交付 |
| `wls doctor` | 检查依赖、沙箱档位、端点连通性 |
| 现有细粒度子命令 | 保留，供调试和恢复使用 |

真实调用的授权简化为：配置文件写明端点、模型和预算上限，`wls run` 启动时显示将要使用的模型和预算，由命令行参数确认。常驻服务和本地 API 沿用 v0.4.1 §12.2，在并行稳定后实现。

## 13. 配置

提供一个不超过 40 行的入门配置，包含：一个真实模型条目、默认模型、各角色覆盖、预算、沙箱档位、清理策略。完整配置项保留，但都有默认值。配置检查区分“已生效”和“仅校验”，仅校验的项在入门配置里不出现。

## 14. 安全不变量

1. 只有 Worker 执行业务工具；工具调用经 Schema、身份、版本、权限检查后才派发。
2. 四套修订独立；状态变更带 CAS 与代次；迟到结果不能盖新版本。
3. AMEND 后逐任务显式处置，遗漏保持暂停。
4. 有副作用的操作先持久意图；结果不可证明标 UNKNOWN，核对前不重做。
5. 原请求、原响应、原用量不可变；未知不填 0。
6. 预算先预留后发送；余额不足不发；每次尝试记账。
7. 凭据只经环境变量引用，不入库、不入日志、不进提示词。
8. 文件工具限定在工作区；进程默认断网；控制数据库不进工作区。
9. 交付先持久意图再发布；回执绑定包哈希；只删除登记过所有权的目录。
10. 测试不调用真实模型；不改写已发布的 SQL 和历史档案。

## 16. 度量

每个真实请求输出一份费用与质量明细：各角色调用次数、四项 token、缓存读取占比、估算费用、耗时、格式错误次数、纠正次数、返工次数、未知项。对照评测用同一组任务、同一模型、同一预算比较三种条件的成功率、费用和耗时。指标目标见 `02-optimization-plan.md` §7。

## 17. 与 v0.4.1 的差异

| 主题 | v0.4.1 | v0.5 |
| --- | --- | --- |
| 阶段顺序 | S1 闭环 → S2 并行审核 → S3 记忆 → S4 互通 → S5 扩展 | G1–G10，按用户需求重排 |
| 错误处理 | 任何错误停批；付费重试 0 | 三级分类；可纠正的交还模型；连接级重试 2 次 |
| 响应解码 | 未知字段一律拒绝 | 元数据宽容，语义严格 |
| 上下文 | 规定指纹；Worker 滑动窗口 | 规定线上顺序；追加加批量折叠 |
| 工具声明 | 每次调用按动作变化 | 角色固定，另给允许列表 |
| 沙箱 | 逐文件封存一档 | `standard` 与 `strict` 两档 |
| 协议 | Responses 一种 | 三种，按能力表选择 |
| 并行 | 服务化后再做 | 每请求一库加团队线程，不依赖服务化 |
| 计费 | 签名收据或停批 | 冻结单价估算；收据可选 |
| 清理 | 默认关闭 | 回执后默认清运行态 |
| 接口 | 约 40 个细粒度子命令 | 增加 `wls run` 等高层命令 |
| 验收 | 内部不变量 | 增加用户可感知的 U1–U10 |
| 文档 | 目标与进度混写 | 蓝图只写目标 |

采纳本提案时需要新增的决策记录：错误分级与重试、宽容解码、线上布局与折叠、工具集稳定、沙箱两档、多协议适配、每请求一库、清理默认值、合并权限。
