# 02 优化方案

依据 `01-audit-report.md` 的发现和仓库内的用户原话 T01–T21。本文回答三件事：往哪里优化、哪些必须保留、哪些需要 owner 拍板。具体改法在 `04-fix-list.md`，排期在 `05-development-plan.md`。

## 1. 对需求的理解与排序

用户要的是一个**能实际干活**的通用多 Agent 系统。按原话归并后的优先级：

| 顺序 | 需求 | 原话 | 为什么排这里 |
| --- | --- | --- | --- |
| 1 | 四角色架构跑通真实任务，不乱 | T02 T03 T04 T09 | “不乱”已经做到；缺的是用真实模型跑通 |
| 2 | 各角色模型、思考等级单独设置 | T05 | 配置已实现，真实调用后即可兑现 |
| 3 | 默认工具和基础包，Worker 真能干活 | T10 T11 | 不能跑命令的 Agent 做不了多少事 |
| 4 | 支持主流端点 | T06 | 决定用户能不能用自己手头的模型 |
| 5 | 高缓存率 | T06 | 直接决定费用和速度；改起来便宜，越早越好 |
| 6 | 并行、快 | T09 | 用户提出四角色的初衷就是避免串行 |
| 7 | 用现有 MCP、Skill、插件 | T01 T12 | 生态接入 |
| 8 | 经验、Skill、统一记忆 | T13–T20 | 用户讨论最多的部分，依赖前面的闭环产出经验 |
| 9 | Agent 互调、工作流 | T01 T08 | 依赖稳定的单功能闭环 |
| 10 | 交付后清理 | T03 T09 | 机制已有，改默认值即可 |
| 11 | Windows | T01 | 用户已同意 Linux 先行 |

## 2. 核心判断

1. **项目不缺安全机制，缺的是一次真实运行。** 再加任何防护之前，先让真实模型把三个小任务跑完。真实运行暴露的问题，比继续推演反例更有价值。
2. **流程是当前最大的瓶颈。** 已经写好、CI 全绿的代码三天没有合并；个别简单功能的在途实现是 `04-fix-list.md` 所给最小方案预算的十倍以上。先改流程，其他优化才落得了地。
3. **“安全”和“可用”要分层。** 少数不变量必须守死，其余都应是可配置的默认值，并且默认值要偏向可用。

## 3. 五条优化主线

### 主线一：流程减负

- 合并标准只有三条：CI 通过、一页 PR 说明、改动在范围内。取消“配对 RED/GREEN 复现”“独立硬审”“资源采样”“源码身份清单”作为合并前置。
- 每项工作一个小 PR，直接基于 main，产品代码不超过 800 行；同时在制不超过 3 个；不堆叠。
- 测试只写三类：新功能的正向用例、被修缺陷的回归用例、安全不变量的反例。单个 PR 的测试行数不超过产品行数的 2 倍。
- 报告只写一页，写在 PR 说明里；除里程碑报告外不再往 `docs/reports` 加文件，压缩包、XML、长日志放 CI 制品。
- 合并权限见决定 D-1。
- 把构建和测试时间当作产品指标：增量构建 2 分钟内，PR 门禁 15 分钟内。

### 主线二：打通真实闭环

- 先收敛：合并 PR #48、#49；G1-3 取小改动重开；G1-5、G1-6 按最小方案重做（`04-fix-list.md` F-07、F-08）。
- 再补 G1 没覆盖、但真实模型必需的三项：工具说明文字、提示词与工具对齐、环境卡片修正（F-03、F-04）。
- 提供一条命令跑完一个请求的入口 `wls run`（F-10）。
- 然后进入 G2：owner 给出端点和预算，跑三个小任务，写一页报告。

### 主线三：缓存与成本

- 重排实际发出的请求：稳定内容在前，历史只追加，易变状态放最后（F-05）。
- 工具集按角色固定，用“本次允许的工具”来限制，不再增删工具定义（F-05）。
- 来源元数据、哈希、base64 副本留在宿主侧，不发给模型（F-06）。
- 历史用“追加 + 到阈值批量折叠”替代每回合滑动的窗口（F-06）。
- 记录每次调用的缓存读取占比，按角色汇总，作为固定报表。

### 主线四：工具与沙箱可用化

- 沙箱分两档（决定 D-5）：`standard` 档用 bwrap 只读挂载系统目录、默认断网、限 PID 和内存，能跑 Python、git、常用命令行工具；`strict` 档保留现有逐文件封存。
- 环境卡片真正执行检查命令，把结果告诉模型。
- 接通 `/input` 只读输入；放宽单文件和提交体积上限，改为可配置。

### 主线五：并行、生态、记忆、互调

- 并行分两步：先做请求级并行（每个请求一个独立数据库文件和一个进程，不需要改 Store）；再做请求内团队级并行（同一进程多线程推进不同团队，模型调用在锁外等待）。
- 多端点：增加 Chat Completions 适配器（覆盖面最广），再加 Anthropic Messages；能力表和价格表外置。
- MCP：先做客户端，让 Worker 能用现有 MCP 服务器的工具；再做服务端，让别的 Agent 能调用本系统。
- Skill：读取 Agent Skills 格式（`SKILL.md`），按功能模板固定加载或按标签检索。
- 记忆：从已有的经验报告作业起步，先做“写入、标签、关键词检索、按版本加载、反馈”这个最小闭环，再做权重、合并、撤销。
- 互调：MCP 服务端落地后，功能之间的调用走同一入口；A2A 按需再加。

## 4. 必须保留的不变量与可以放宽的默认值

### 保留（任何优化都不得破坏）

1. 只有 Worker 执行业务工具；模型输出不是授权，工具调用要过 Schema、身份、版本、权限检查后才派发。
2. 请求、计划、任务、指令四套修订独立；状态变更带 CAS 和代次；迟到结果不能盖新版本。
3. AMEND 后每个任务显式 update/keep/cancel，遗漏的保持暂停。
4. 有副作用的操作先持久意图再执行；结果不可证明时标 UNKNOWN，核对前不重做。
5. 原请求、原响应、原用量不可变；未知用量不填 0。
6. 预算先预留后发送；余额不足不发；每次尝试都记账。
7. 凭据只经环境变量引用，不入库、不入日志、不进提示词。
8. 文件工具限定在工作区内；进程默认断网；控制数据库不放进工作区。
9. 交付先持久意图再发布；回执绑定包哈希；只删除登记过所有权的目录。
10. 测试不调用真实模型；不强推；不改写已发布的 SQL 和历史档案。

### 放宽（改为可配置，默认值偏向可用）

| 现状 | 建议默认 | 仍然保留的保护 |
| --- | --- | --- |
| 任何错误停整批 | 可识别的格式错误、已结算的工具失败作为反馈交还模型，同一目标连续 3 次后停 | UNKNOWN、权限、预算、取消、超时、存储错误仍立即停 |
| 每个响应恰好一个工具调用 | 允许一次返回多个只读工具调用；有副作用的仍逐个派发 | 每个调用单独过门禁 |
| 付费重试 0 次 | 仅对“未收到任何响应字节”的连接失败、429、5xx 允许带退避重试 2 次，每次重新预留预算 | 已收到部分响应的不重试 |
| 响应未知字段一律拒绝 | 元数据位置的未知字段忽略并记录；未知的输出项类型仍拒绝 | 原始字节照常保存 |
| 每次调用只声明一个目标的工具 | 角色工具集固定，另传“本次允许的工具” | 宿主侧仍拒绝越权调用 |
| 逐文件封存运行文件 | `standard` 档只读挂载系统目录 | `strict` 档保留；两档都默认断网 |
| 手写授权文件 | 配置文件里写端点和预算，命令行确认一次 | 预算上限、模型白名单仍强制 |
| 滑动窗口 4 次 | 追加式历史，到上下文 60% 时批量折叠旧回合 | 原始记录不删，可回读 |
| 签名计费收据 | 按冻结单价估算（PR #49） | 有收据时仍可核账 |
| 清理默认关闭 | 回执后默认清运行态，保留交付包、经验、回执 | 只清登记过所有权的目录 |

## 5. 需要 owner 决定的事项

每项都给了建议值。**没有明确决定前，本地 agent 按“未决定时”一列执行。**

| 编号 | 事项 | 建议 | 未决定时 |
| --- | --- | --- | --- |
| D-1 | 合并权限 | 满足全部四条时 agent 可自行合并 main：CI 全绿；产品代码 ≤800 行；不改数据库版本；不含真实或付费调用。其余情况由 owner 确认 | 维持现行规则：每次合并由 owner 确认；agent 每天列出待合并清单 |
| D-2 | 首个真实端点、模型、协议（原 P-01） | 用手头已有的 API。端点支持 OpenAI Responses 就直接用现有适配器；只支持 Chat Completions 就先做 F-12。首轮选便宜、不带推理或低推理的模型 | 不做任何真实调用；阶段 2 停在门口 |
| D-3 | 预算与重试（原 P-05） | 首轮每请求上限 1 美元，G2 合计 10 美元以内；允许上表所述的 2 次连接级重试 | 不做任何真实调用 |
| D-4 | 未知字段处理 | 采纳上表的“元数据忽略并记录” | 维持全部拒绝 |
| D-5 | 沙箱默认档 | 新增 `standard` 档并设为默认 | 只做设计和本地验证，不改默认 |
| D-6 | 证据流程 | 采纳主线一全部条目 | 只执行 11-06 已采纳的部分：一页 PR 说明、单 PR ≤800 行、在制 ≤3、不堆叠、证据文件不进 `docs/`。“取消配对复现与硬审”“测试行数上限”这两条新规则不生效 |
| D-7 | 清理默认 | 回执后清运行态；交付包、经验、回执保留 30 天 | 维持默认关闭 |
| D-8 | 阶段顺序 | 按 `05-development-plan.md`：G1 → G2 真实闭环 → G4 能跑命令 → G3 对照评测 → G5 多端点 → G6 并行 → G7 MCP/Skill → G8 记忆 → G9 服务化与互调 → G10 Windows 等 | 按该顺序 |

## 6. 冻结清单

首个真实闭环（G2）完成前不投入：Windows 原生、Store 411 与持久事件、异步协调器、DAG 审核存储、公平调度、新的证据或观测工具、私有行严格清除、签名计费扩展、Store 大规模重构。

两点修正：
- 11-06 的冻结清单里有“第二适配器”。如果 D-2 选定的端点不支持 Responses，Chat Completions 适配器就是第一适配器，不在冻结范围内。
- “沙箱 `standard` 档”是新工作，不属于被冻结的“强沙箱正向验收”。它排在 G2 之后。
