## 必须修复（P1）

这三项在现有 Fake 测试里都不会出现，但一接真实模型或真实工具链就会卡死团队或请求，建议下一批最先修。

### P1-1 `run` 非零退出一律记为 UNKNOWN，而 CLI 和运行器都没有核对入口

- **位置**：`src/worker_tools.cpp:461–462` 只有"退出码 0 + 强隔离 + 全部后代退出"才记 SUCCEEDED，其余派生过进程的结果一律 UNKNOWN；`src/store.cpp:1055` 同团队存在 UNKNOWN 就拒绝新业务；`Store::reconcile_operation` 只在测试里调用，CLI 没有对应命令。契约 `S1-worker-tools.md:114` 明确写了这一行为。
- **触发**：配置好强沙箱、启用 run 之后，任何测试失败、编译报错、grep 无匹配、超时或输出超过 64 KiB。
- **后果**：该团队此后所有业务都被拒绝（unknown operation requires host reconciliation），AMEND 不会清除它，清理也被 unsettled_operations 挡住。整个请求也无法交付（交付要求全部操作已结算），通过 CLI 只能取消。编码任务最基本的"跑测试→看失败→修改→再跑"做不到。
- **修复**：把两种结果分开。进程和全部后代已被 cgroup 证明退出的（非零退出、超时或输出超限被终止后 populated=0），记为 FAILED 或 INTERRUPTED，证据注明"副作用可能部分发生、已停止"，允许继续工作；只有后代未证明退出、结果未落盘时才保持 UNKNOWN。同时提供带证据、带事件的宿主核对命令（例如 `wls reconcile-op`）。

### P1-2 Store 写死的每请求容量，会在配置允许的范围内锁死请求（已复现）

- **位置**：`src/store.cpp:1081` 事件上限 4096（控制类 8192，两者共用同一个总数）；`2776` 操作上限 1024。同类写死的还有问题 128/32（`1774`）、提交 64/256（`1927`）、验收 256/512（`2083`）、交付 64（`2208`）、AMEND 100（`2631`）。它们都不来自冻结配置，准入时也不校验。
- **触发**：实测一次业务工具调用写 6 条事件（reserve、settle、feedback、prepare、start、result），最多约 680 次业务调用就会碰到 4096。配置却允许每张说明 200 次、每请求 4 个团队、每团队返工 3 次，理论上可达 3200 次。CLI 默认每请求只给 64 次模型尝试，默认参数下碰不到；但要跑满每张说明 200 次就必须调高 `--max-attempts`，这时就会撞上。
- **后果**（复现结果见"实际测试与复现结果"）：第 1024 次操作后报 operation capacity exhausted；事件总数到 4096 后，issue_instruction、publish_plan 等非控制动作全部返回 quota，只剩取消可用。请求再也无法提交、验收或交付。
- **修复**：上限进入冻结配置，准入时与 worker、团队、返工上限做一致性校验；接近上限时先发告警事件并转 WAITING_INPUT，不要中途硬失败；已消费的事件可归档，计数按类别或按任务计算。

### P1-3 每次写者重开都会让所有活动团队的说明失效，只能靠新的 TeamLead 调用恢复（已复现）

- **位置**：`src/store.cpp:1202–1211` 的 recover 给所有活动团队 execution_epoch+1、paused_for_change=1；`2727–2731` 的 ack 要求说明的 execution_epoch 等于当前值；`src/event_runtime.cpp:610–615` 发现说明不是当前的就调用 TeamLead。
- **触发**：CLI 的每条写命令都是新进程并接管写者，包括 pump-fake、answer、wait、wake、ack-delivery。
- **后果**：重开后对原说明 ack 返回 stale，业务 prepare 返回 not_ready；只有 TeamLead 重新下达第 2 版说明并 ack 后才能继续。接真实模型后，每条 CLI 写命令之后的下一次推进，每个活动团队都要多一次付费的 TeamLead 调用；新说明由模型重写，还可能偏离原意。
- **修复**：恢复时由宿主把同一份说明重新绑定到新代次（记录事件，Worker 走控制通路 ack），不要求模型重写；代次只用来围栏在途操作和迟到的旧调用。

## 蓝图优化建议

蓝图的方向和安全原则没有问题，需要优化的是"先做什么、做到多深、怎么写"。下面按重要性排列。

1. **把真实模型最小闭环提前到下一批（S1-13 先行）。** 6 个增量之后，真实模型调用仍为 0，路线图却仍把 S1-13 排在私有行 purge、强沙箱正向和 wlsd 之后。现有协议有几处只在 Fake 下成立：每次响应必须恰好一个工具调用（`offline_runtime.cpp:603`）；没有 Schema 纠错循环；没有上下文压缩，而上下文上限是 256 条消息、1 MiB，一张说明却允许 200 次工具调用。越晚接真实模型，契约和 Store 的返工越大。
2. **划清"MVP 必需保证"和"后续加固"。** 必需的是：业务操作幂等与 UNKNOWN、AMEND 显式处置、预算与未知费用、原文和工件不可变。可以后置的是：私有行 purge、清理所用的 birth time 和 mount id 代际、回执 TTL、多重指纹交叉校验。每个增量设复杂度预算（新增表、状态、计数器的个数），超出时在 ADR 里说明 MVP 为何需要。
3. **重写"操作结果"语义。** 在 §5.9 和 §9.5 增加"已结算的失败/中断"，与"结果未知"分开（对应 P1-1）。同时写清宿主核对的入口、证据格式和权限。
4. **容量、事件和工件存储要按真实任务设计。** 所有上限进入配置并在准入时校验，事件可以归档（对应 P1-2）。工件改为内容寻址存储；现在提交上限是 8 个文件、每个 64 KiB，交付包 4 MiB，单次写入 64 KiB，只装得下小文本。代码类任务应尽早定义"以 git 提交或 worktree 为交付物"的路径，§17 已经提到 worktree。
5. **执行环境要能跑真实工具链。** 强沙箱的根目录是空的，只能逐个挂载最多 128 个按 SHA 固定的单文件，跑不了依赖目录树的工具链（GCC 头文件、Python 标准库、npm 包）。工作区审计拒绝符号链接、硬链接和特殊文件，而 npm、venv 等常见工具都会产生符号链接，一次 `run` 之后工作区既不能再 `run`，也不能被清理。建议改为可校验的只读镜像根文件系统（例如 OCI 镜像 digest），加上 seccomp；链接类条目在不跟随的前提下允许删除。
6. **恢复与常驻。** 重启不应要求模型重新生成说明（对应 P1-3）。另外，现在的写租约是整个数据库一把锁，任何写命令都会围栏所有请求；设计 wlsd 时应改为按请求的租约或 strand。
7. **返工和升级要闭环。** 业务否决 → 有界返工 → 超限升级给用户。BLOCKED 要写清由谁、用哪个命令、解除什么（对应 P2 第一项）。
8. **文档结构三分离。** 目标规格只写目标；进度只放在一个能被脚本校验的状态矩阵；版本变化只进 CHANGELOG。现在 01 规格正文里有 35 处 S1.x 进度描述，07 任务卡每张都堆叠 S1.5、S1.4、S1.3、S1.1、S1.2 段落且顺序不一，已有几处过时。再补一页架构图和状态机图，把长句拆短。原始测试日志和逐文件 SHA 清单（`docs/reports` 共 43 个文件、792 KB）移到 CI 制品或 Release 附件。
9. **明确 M1 内核的去留。** `wls` 只复用 M1 的 `config.hpp` 和 `identity.hpp`；TaskEngine、Journal、Scheduler 及其 55 项测试不在 S1 路径上。建议在 ADR 里写明冻结为参考实现、移到 `legacy/`、不再计入进度；审核双容量等调度语义另行迁入 S1。
10. **调整协作流程。** 仓库只有 10 个提交，主要功能提交每个新增 3,700 到 20,700 行；S1.6 报告也自述由同一实现者复核、没有独立评审。建议每张卡拆成 800 行以内的 PR，独立审查作为合并门禁，CI 增加 ASan 和 clang-tidy，并把本报告的两段复现程序改成回归测试。

## 建议的下一批顺序与需要你拍板的事项

建议先修 P1，再接真实模型；拿到真实数据后，再决定 purge、wlsd 和执行环境镜像化的先后。

1. 修复 P1-1、P1-2、P1-3，把两段复现程序改成回归测试；合入附带的小补丁，并在 CI 打开 ASan。

4. 按真实数据修订协议：单工具调用约束、Schema 纠错、上下文压缩、业务否决后的返工。
5. 再决定 S1-11 私有行 purge、wlsd/API、执行环境镜像化三者的先后。
