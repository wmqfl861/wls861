- 审核日期：2026-10-23
- 审核对象：`wmqfl861/wls861` 主分支 `fcdbdd0`（`wls 0.7.0-s1.6`，蓝图 v0.4.1）

## 结论

**蓝图需要优化**：问题不在安全细节不够，而在优先级和关键接口。六个增量、约 1.4 万行 C++ 之后，系统仍未发生过一次真实模型调用；核心假设（四角色层级是否比单 Agent 更好、成本是否可接受）完全未验证，而最近两批的投入集中在清理/交付/回执的边角。上下文与模型接口的设计也与真实工具调用 API 不匹配，接入时会返工。

**代码需要修复，但基础扎实**：在与 CI 相同的条件下（umask 022）全部测试通过，生产代码 UBSan、ASan 均干净。需要修的有三类：① 3 个会在接入真实模型后直接卡死流程的问题（上下文无压缩、事件总量上限、拒绝后无出路）；② 5 个已复现的正确性/可移植性缺陷；③ 若干小问题。

## 二、代码需要修复的问题

### P1：接入真实模型前必须修（否则流程会卡死）

**1. Worker 上下文无压缩，几次大文件读取后永久卡死（已复现）**
- 每次 Worker 调用都把该 Worker 的全部历史尝试作为消息重放（`src/offline_runtime.cpp:497-505`），没有压缩或窗口；编译后上下文上限 1 MiB（`include/wls/context.hpp:51`）；历史另有 256 次尝试硬上限（`src/store.cpp:1672-1676`）。
- `fs_read` 结果同时返回 `content` 和 `content_base64`（`src/workspace_posix.cpp:575`），同一内容在历史里占两份。
- 实测：Worker 对一个 60 KB 文件做一页读取，**第 8 次调用即报 `context byte limit exceeded`**；之后再开新的 pump 也无法恢复，因为不可变历史本身已超限。真实任务读几个文件就会让该任务永久停住。
- 修复方向：实现蓝图 7.2/S1-08 的压缩（保留原文、约束、未决操作与绑定，摘要旧工具结果）；历史中工具结果只存一种编码并按需分页引用；超限应进入可恢复状态（例如新说明修订开启新的历史窗口），而不是永久阻塞；超限错误码应为 `quota` 而非 `invalid_input`。

**2. 每请求事件总量硬上限 4096，无归档；每次写命令都给所有活动请求追加事件（已实测）**
- `event()` 在请求事件总数达到 4096 后拒绝所有业务事件（控制事件 8192）（`src/store.cpp:1080-1081`），无压缩或归档。
- 以写者身份打开数据库会对库内**每个**活动请求执行 `recover()`：提升代次、暂停所有团队、围栏操作、追加事件（`src/store.cpp:634-635, 1202-1211`）。
- 实测：一个最小单任务流程（7 次 Fake 调用）消耗 34 个事件，约 5 个/调用；另一个无关请求在 20 次失败的写命令后多了 20 个事件。按蓝图默认额度（4 团队、每条说明 200 次工具调用）一个请求的生命周期内就可能触顶，触顶后只能做控制操作。
- 修复方向：上限从冻结配置推导；事件分段归档或快照；恢复事件只在确有在途工作时写入，且不占业务配额。

**3. 业务验收被拒绝或返工次数用尽后，任务进入 BLOCKED 且没有出路**
- `accept_candidate(passed=false)` 把任务和提交置为 BLOCKED（`src/store.cpp:2085-2099`）；TeamLead 返工达到冻结上限同样 BLOCKED（`src/store.cpp:2003`）。pump 只报告 `rework_blocked … requires controlled escalation`（`src/event_runtime.cpp:724`），但 Dispatcher 的 `change_task`、上报用户等出路都未实现；实现契约也写明否定决策"不是自动新 WorkOrder"。
- 结果：真实使用中最常见的"验收不通过 → 返工"路径会让请求停住，只能靠用户 AMEND 或重新规划。
- 修复方向：实现 Dispatcher `change_task`（新任务/说明修订 + 重新 ack，计入返工上限）与"上报用户"问题；补对应回归。

### P2：已复现的正确性 / 可移植性缺陷

**4. 受控工作目录分配被中断后，该请求的清理被永久阻塞（已复现）**
- `create_owned_workspace` 先 `mkdirat(envelope)`，再创建并写入 `owner.json`（`src/cleanup_posix.cpp:290-318`）。若进程在这两步之间崩溃，重试时目录已存在但没有（或只有半个）所有权标记：同键重试报 `open owned workspace entry: No such file or directory`，换新键报 `team already has an owned allocation`，资源永远停在 `PREPARED`，而 `cleanup_blockers` 把任何 PREPARED 视为阻塞（`src/store_cleanup.inc:55`），也没有放弃意图的命令。
- 修复方向：envelope 先以临时名创建，写入并 fsync `owner.json` 后用 `renameat2(RENAME_NOREPLACE)` 改为最终名再 fsync 父目录（标记先于可见名存在，不违反"不采用旧目录"原则）；另提供显式放弃 PREPARED 意图的命令，并让它不再永久阻塞清理。

**5. 测试和 README 依赖 umask 022，Ubuntu 普通用户默认 0002 下失败（已复现）**
- 运行时正确地拒绝组可写目录（`src/workspace_posix.cpp:221-232`），但测试夹具和 README 示例（S1.2/S1.3/S1.4 段用 `mkdir -p`，未指定权限）创建的目录继承 umask。
- 实测：umask 0002 下 `event_runtime/workflow_runtime/acceptance_runtime/workspace/sandbox/worker_tools/cleanup/cleanup_runtime` 8 个套件共 105 例失败、s15/s16 冒烟失败；README S1.2 示例照抄报 `workspace directory must be owned, linked and not writable by other users`。项目要求用非 root 用户跑测试，而 Ubuntu 普通用户默认 umask 正是 0002。
- 修复方向：测试入口统一 `umask(077)` 或夹具显式 `mkdir(…, 0700)`；README 一律用 `mkdir -p -m 700`（S1.5 段已这样写）；错误信息提示 `chmod go-w`；CI 增加 umask 0002 矩阵。

**6. 沙箱子进程没有设置 umask（代码推断，强沙箱未实跑）**
- `supervise()` 的子进程在 exec 前设置了进程组、no_new_privs、信号、core 限制等（`src/sandbox_posix.cpp:565-593`），但没有 `umask()`，bwrap 内命令继承调用方 umask。
- 后果：在 umask 0002 的主机上，`run` 创建的文件/目录是组可写的；下一次 `run` 的预检 `verify_workspace_tree`（`src/sandbox_posix.cpp:370-417`）和所有文件工具（写操作每次都会遍历全树）都会拒绝整个工作区，该团队的工作区实际报废。
- 修复方向：fork 后、execveat 前调用 `umask(077)`（异步信号安全）；补一条以 umask 0002 运行的回归。

**7. ASan 目标在参考工具链上无法编译；测试代码 2 处 use-after-free（已复现，修复已验证）**
- `make asan` 在 Ubuntu 24.04 / GCC 13.3 下因 `<regex>` 误报 + `-Werror` 编译失败；CI 只跑 UBSan，因此 ASan 从未把关。
- 降级该警告后 ASan 发现 `tests/config_loader_tests.cpp:105` 和 `:136`：持有 `models["fake"]` 的引用，再对同一对象插入 `models["alternate"]` 导致表重分配，引用悬空后被拷贝。Release 下"碰巧"能过。
- 修复：见附录 A5 补丁（先拷贝再插入）；`config_loader.cpp:584-618` 两处 `std::regex` 只校验 ≤64 字节的简单格式，可改为手写校验并去掉 `<regex>`；CI 增加 ASan job。

**8. 两处构建可移植性问题（已复现）**
- `Makefile:39` 用目标级 `CPPFLAGS +=` 追加 S1 头文件路径；若用户在命令行传 `CPPFLAGS=…`（例如指向非系统 Boost），这条追加被静默忽略，`schema.cpp` 找不到 valijson 而编译失败。改用独立变量（如 `S1_CPPFLAGS`）或 `override`。
- Clang 18：`src/main.cpp:285` 的 `for (const unsigned char c : string_view)` 触发 `-Wsign-conversion`；CMake 声明支持 Clang，但 CI 不覆盖。改为先取 `char` 再 `static_cast`，CI 增加 Clang。

### P3：小问题

9. **约束目录的输入错误被归类为内部错误（已复现）**：记录有 3 个键但键名不对时返回 `runtime_error` 并泄露 Boost 源文件路径（exit 1）；字段类型不对时返回 `corrupt`，看起来像数据库损坏（`src/store.cpp:1212-1227`）。应先显式校验键名与类型，统一报 `invalid_input`。
10. **金额换算两套逻辑不一致（已验证）**：CLI 用 `floor(dollars * 1e6)`（`src/cli.cpp:394`），Store 用精确十进制解析（`src/store.cpp:326-357`）。约 1.2% 的两位小数金额少 1 微美元（如 `max_cost_usd: 2.01` → 2,009,999）。CLI 应复用 Store 的解析函数。
11. **写命令在校验参数前就接管写者**：例如 `wait --task 错误ID` 也会先打开写者，触发对库内所有活动请求的围栏（暂停全部团队、需重新 ack）（`src/cli.cpp:624-641`）。应像 `answer`/`ack-delivery` 那样先只读预检。
12. **Worker 文件工具无法在新子目录建文件（已复现）**：`fs_write("src/main.py")` 在 `src` 不存在时失败（父目录必须存在，`src/workspace_posix.cpp:397-401`），也没有 mkdir/删除/移动工具；而 `run` 需要完整的强沙箱宿主配置。普通开发机上真实编码类任务几乎无法完成。
13. **交付包里的成果被改名为 `artifact-<节点>-<序号>.bin`**（`src/store.cpp:2230`），原文件名只在 manifest 中；用户拿到的是一堆 `.bin`。建议保留原相对路径（在安全名规则内）。
14. **12 个配置项只校验、不执行**：`max_wall_minutes`、`warn_at_fraction`、`stall_minutes`、`stall_same_error_repeats`、`compaction_at_fraction`、`schema_retry_max`、`max_active_dispatchers/workers`、`reserve_workers_for_review`、`max_concurrent_model_calls_per_endpoint`、`max_concurrent_ops`、`snapshot_decision_log_entries` 在运行时代码中未被使用，`config check` 却报 `valid: true`。至少应在 `config check/explain` 中标注"尚未生效"；墙钟上限与 80% 预算告警应在首次付费调用前落地。

## 三、蓝图优化建议

**B1. 调整优先级：先打通真实模型最小闭环，再继续清理细节。**
当前路线的下一批仍是私有行 purge，其后是强沙箱、wlsd/API，真实模型排在最后（ROADMAP §3、任务卡"下一批推进顺序"）。建议改为：真实适配器（S1-13 + S1-05）→ 上下文压缩（S1-08）→ 拒绝/返工闭环 → 同模型单 Agent 对照（现排在 S2，建议提前）。私有行 purge、严格清除可后移。真正的阻塞点是 P-01（供应商/模型）和 P-05（预算）尚未决定，需要项目所有者拍板。

**B2. 重做上下文/模型接口，再做压缩与缓存。**
`CompiledContext` 是自定义的分帧字节串（`WLS-CONTEXT/1` + 各段 + `{role, content}` 消息），`prefix_sha256`/`cache_identity` 也是对它计算的（`src/context.cpp:217-270`）。真实工具调用 API 需要独立 system、原生工具 schema、带 ID 的 tool_use/tool_result 多轮结构和缓存断点；适配器要么把整串当一条消息发送（模型效果差、工具非原生），要么把帧解析回结构（哈希就不再是"实际发送字节"）。建议把编译结果改为与供应商无关的结构化请求，缓存指纹基于其规范化形式，由适配器映射到具体协议。

**B3. 把散落的硬上限收敛到冻结配置，并让"触顶"可恢复。**
事件 4096、历史 256 次、上下文 1 MiB、提交 8×64 KiB / 总 256 KiB、交付包 4 MiB、问题 128 等上限写死在代码里，与 `limits` 配置无关，且触顶多为永久阻塞。建议统一由配置推导，配套归档/压缩/分页，并为每个上限定义触顶后的恢复路径。

**B4. S1 完成标准应覆盖模型做出的关键决策。**
AMEND 时逐任务的 update/keep/cancel 当前由宿主通过 `--dispositions-file` 提供（`src/event_runtime.cpp:208-218`），Dispatcher 模型并未做这个判断；拒绝→返工、返工上限→上报也未实现。"中途改方向准确落到执行"是用户的核心需求（B5），建议把"模型产出的处置 + 拒绝返工"纳入 S1 验收。

**B5. 给执行环境一条可用的开发路径。**
蓝图允许显式配置的弱隔离（9.7），但实现完全没有弱入口；强隔离又需要宿主预先委派 cgroup v2 并固定 bwrap 哈希。结果是普通开发机上 Worker 不能执行任何命令（不能编译、不能跑测试）。建议提供明确标注、报告中可见的开发模式（例如 rootless 容器或显式 weak 模式），或一键宿主配置脚本 + doctor 指引。

**B6. 收敛重复实现。**
M1 的 TaskEngine/Journal/Scheduler（`wls861 demo`）与 S1 的 SQLite Store 两套内核并行维护和测试，S1 运行时并不使用 M1；另有 638 行的 Python 参考 Store。建议冻结 M1（打标签归档、移出默认构建与测试），Python 参考只保留 Schema/契约测试。

**B7. 规格与进度分离，压缩文档噪音。**
每批都在主规格、验收计划、需求追踪、任务卡、路线图、README 中追加"S1.x 增量/进度"段落，内容重复五六处；任务卡中顺序已经错乱（如 S1-01 卡依次为 S1.5、S1.4、S1.3、S1.1、S1.2）；主规格 §0 记录了每批提交 SHA。大量"不证明/不代表"的免责句稀释了有效信息。建议：规格只写目标设计；进度集中到一个 STATUS/CHANGELOG；任务卡用状态字段；证据边界集中到一张矩阵。

**B8. 交付节奏：拆小提交。**
整个代码库 10 个提交、6 天完成，每个增量是单个 3.7k–2 万行的提交，人工实际无法评审。建议按模块拆 PR，每个 PR 附人可读的变更摘要和聚焦的审查清单。

**B9. 在做 wlsd/API 之前整理 Store 接口与资源打包。**
`Store` 是约 90 个公开方法的单一类，构造函数有 9 个位置参数（其中 7 个是逐代 SQL 资产，每加一代就再加一个参数），接口普遍返回弱类型 Json。建议拆分领域服务（请求/计划、操作、问答提交、验收交付、清理）、迁移改为注册表、API 边界用强类型结构。另外运行时从源码目录读取 SQL/Schema/提示词，并在数据库中固定迁移文件哈希——二进制必须在源码目录运行，迁移文件任何字节变化都会让已有库无法打开；守护进程安装前应把这些资源嵌入二进制或按版本安装到固定目录。

**B10. 把用户可感知的目标放回近期里程碑。**
用户原始需求中的"并行、快"（B7）、"高缓存率"（C2）、"支持主流模型端点"（A4）在 S1 实现中尚未触及：S1 运行器是单进程逐任务串行处理，并行只存在于 M1 的合成调度器；51 项产品验收全部"未执行"。另外提示词目前写成运行时协议条款（ack、幂等键、版本绑定等宿主已代办的事项），缺少任务方法指导，需要用真实模型迭代——这也是 B1 的理由。

## 四、做得好的地方

- 工程纪律强：`-Wall -Wextra -Wconversion -Wshadow -Werror`、UBSan、22 个套件 356 个 C++ 用例和 6 组真实 CLI 冒烟，在 CI 同等条件下全部通过；生产代码 ASan 干净。
- 文件/进程边界扎实：`openat2` + `RESOLVE_BENEATH|NO_SYMLINKS|NO_XDEV`、按 dev/ino/mnt_id/btime 校验文件"代"、运行文件复制到 sealed memfd、pidfd、`cgroup.kill`、放行前核验挂载与命名空间、无弱回退。
- 持久化语义清晰：WAL + FULL、逐行 CAS、命令幂等重放、UNKNOWN 不盲重试、迟到结果不盖新版本、交付先持久意图再原子发布（`RENAME_NOREPLACE`）。
- 文档诚实，始终区分合成测试、参考实现与真实能力。
