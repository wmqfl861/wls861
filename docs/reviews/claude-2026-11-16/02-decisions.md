## 3. 细则

### 3.1 D-31 原请求的导出

依据见 `01-audit-report.md` §5.2。步骤在 `04-plan.md` §3 的 R0。要点：

1. 先只读查看原请求目录，记录有没有 `output-intent.json`、`output-root.json`、`output/` 和临时文件。
2. 把整个请求目录完整复制一份并生成校验清单。这份副本就是“原样保留的现场”。
3. 用当前 main 构建的程序、原来的命令和原来的配置路径重跑。
4. 通过的标准：摘要的停止原因是 `completed_replay`；`output_path` 非空；调用数仍是 29；成果核对脚本通过。
5. `output/` 已存在但没有 `output-root.json` 时程序会拒绝。这时 `output/` 是空目录就用 `rmdir` 移除后再重放（这一步已授权，因为副本在先）；不是空目录就不动。
6. 不成功的处理：原样记录报错，原目录和副本都保留到 2026-12-16，报告里把这一项写成“已封存”。后续步骤照常进行。

这个决定取代 `AGENTS.md` 里“不重跑原请求、不重试 export”的说法。那句话来自 11-13 的停止规则，不是安全不变量。重放走的是产品自己的校验路径：意图先落盘、逐字节核对、不覆盖。

### 3.5 D-35 思考等级、单次期限、流式

- 授权在 owner 指定的端点和型号上使用 `max` 以外的思考等级。理由：U2 需要三个不同的等级；等级更低只会更省、更快。
- 探针确认端点接受之后的默认分层：Dispatcher `high`，TeamLead `medium`，Worker `low`。端点不接受其中某个等级时，选三个互不相同且被接受的等级。只接受一个等级时，U2 做不了，写明原因，问 owner。
- 为了和 11-15 的结果可比，U1 的复验（R2）三个角色仍然用 `max`。
- 真实运行的单次调用期限统一为 180 秒。profile 允许的上限是 300 秒（`src/provider_profile.cpp:377`）。
- 流式：探针确认中转支持就在 profile 里打开；不支持就保持现状。
- 自动重试保持 0，这是 owner 11-15 的指示。

### 3.6 D-36 缓存

探针：同一个不少于 2,000 token 的请求，10 秒内连发两次，做两组。两组的第二次都读到缓存，判“支持”；否则判“不稳定或不支持”。

| 结果 | 做什么 |
| --- | --- |
| 支持 | 做 E-4（缓存路由键）。在 R2 的报告里看 Worker 的缓存读取占比有没有回到 50% 以上 |
| 不稳定或不支持 | 在这个端点上不再为缓存做任何工作，布局保持不变 |

两种结果下都一样：合成缓存门槛只作为防止布局退化的回归检查保留。不再调它，不再把它写进阶段目标。

### 3.8 D-38 沙箱

依据见 `01-audit-report.md` §6。

1. **先核对。** agent 看托管原生作业证据包里 bwrap 的原始报错。是“Can't find source path /proc/…: Permission denied”就按下面做。不是的话，把实际报错写进日报，按实际情况处理。
2. **修法。** `src/sandbox_posix.cpp:1644` 和 `:1650-1651` 的绑定来源改为父进程解析出的绝对路径（读自己的 `/proc/self/fd/N`）。链接文本不是绝对路径、或带“(deleted)”后缀时拒绝启动。挂载后的身份核对（`:1689-1717`）不动。产品行预算 40。

4. **迭代上限。** 修法合并后原生作业仍不通过，最多再做 3 个修复 PR。还不过就停下这条线，写清楚报错，留给下一次审核。
