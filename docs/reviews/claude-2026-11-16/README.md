# 2026-11-16 审核、优化方案与到项目结束的计划

基线：`main@8d44256`（实现 0.12.0，Store 410）。上一轮审核在 `b7c10dd`，之后合入了 26 个 PR（#95–#120）。

## 结论

1. **过程通过。** 收敛按 11-14 的决定完整执行：远端只有 `main`，被删的 96 个分支全部找得回。26 个 PR 都符合行数和测试比例的规则。main 的完整 CI 28 次里通过 25 次，2 次失败都在 2 小时内修复。
2. **项目还没到 G2 出口，并且停了一天。** 第一次真实运行做了（41 次真实调用）。冒烟请求完整交付；三交付物请求模型做完了，内容核对 12/12，但最后的导出失败，记为 UNKNOWN，之后全部真实调用暂停。暂停是按我 11-13 写的一条停止规则执行的，那条规则只说了“停”，没说之后怎么办。本轮补上：原请求用修复后的程序重放导出（不调用模型），真实运行恢复。
3. **找到了“能跑命令”一直验收不了的根因。** 沙箱的启动参数让 bwrap 去读父进程的 `/proc/<pid>/fd/N`。bwrap 进入新的用户命名空间之后，内核不允许它这么做。这和主机的 AppArmor 配置无关。修法约 40 行。我 11-14 把原因归到主机配置，是不完整的。
4. **真实运行暴露的最大问题是开销。** 三交付物请求用了 29 次调用、57.5 万输入 token、13 分钟，Worker 一个角色占 81%。缓存读取只有 1.7%。已经合入的状态瘦身对 Worker 的帮助很小，Worker 的大头是历史，占请求体的 60%。
