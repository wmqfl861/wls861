# 03 优化方案

依据 `01-audit-report.md` 的发现。每一条写三件事：现状、做法、怎么判断有效。对应的决定在 `02-decisions.md`，排期在 `04-plan.md`。

## 1. 让运行恢复，并且以后不再因为同类原因停下

| 项目 | 现状 | 做法 | 怎么判断有效 |
| --- | --- | --- | --- |
| 原请求的导出 | UNKNOWN，搁置了一天 | 备份后用同一条命令重放，不调用模型（D-31） | 重放后 `output_path` 非空，成果核对通过 |
| 停止规则 | 只写了“停” | 每种停止都配上不用问就接着做的动作（D-32） | 下一次审核看停顿时长：从触发停止到恢复真实调用，不需要 owner 的情况应在 4 小时以内 |
| 导出失败后的提示 | “Reconcile file effects before continuing.”，没法照做 | 请求已经是 DELIVERED、失败发生在导出时，提示改成：重跑同一条命令即可，这一步不调用模型（N4） | 一个断言：这种情况下的提示含有“同一条命令”和“不调用模型”的意思 |

## 2. 真实运行的开销

### 2.1 现状

三交付物请求：29 次调用，57.5 万输入 token，13 分钟。Worker 占 81%。Worker 的平均请求体 96.6 KB，其中历史占 60%，契约 17%，工具定义 11%。缓存读取 1.7%。【报告】

### 2.2 做的顺序

1. **先出数据**：A-1（Worker 每次调用做了什么）、A-2（历史段的构成）。用已捕获的请求离线统计，不花调用。
2. **只改配置的**：思考等级分层、单次期限、流式（E-12、E-13）。
3. **小改动**：G2-7 从 E-1、E-10、E-11、E-14 里选最多 3 个。
4. **大改动**：一次应答多个工具调用（E-9），放在 G3，用对照评测量效果。

### 2.3 各做法的预期

按 Worker 的请求体字节估算。基线是 24 次 × 96.6 KB，约 2,319 KB；每次调用的固定部分约 38.6 KB，历史平均 58 KB。【推算】

| 做法 | Worker 输入的预期变化 | 算法 |
| --- | --- | --- |
| 调用次数减半（E-9 或 E-14） | 约减 50% | 12 次 ×（38.6 + 58）KB ≈ 1,160 KB |
| 历史每一步的增量减半（E-1、E-11） | 约减 30% | 24 次 ×（38.6 + 29）KB ≈ 1,622 KB |
| 契约减半（E-10） | 约减 8% | 24 次 × 8 KB ≈ 192 KB |
| 三项都做 | 约减 69% | 12 次 ×（30.6 + 29）KB ≈ 715 KB |
| 思考等级降低（E-12） | token 变化不大，耗时明显减少 | 现在平均每次调用 27 秒 |

这些是估算，不是承诺。实际数字以重跑为准。D-37 的目标（输入 token 降到 40%）和“三项都做”的估算是一致的。

### 2.4 Worker 为什么用了 24 次调用

报告没有写。A-1 出来之前不猜。出来之后看两件事：

- 有没有成片的多余调用，比如写完又读回来核对、反复列目录。有的话用 E-14 改说明，这是最便宜的办法。
- 有没有连续的同类调用，比如连着写几个文件。有的话 E-9 的收益就大。

### 2.5 缓存

按 D-36 用探针判定。端点不提供稳定缓存时，就不在这个端点上为缓存花任何工夫。请求布局已经是“稳定的在前、历史只追加”，换到支持缓存的端点时自然会受益。

### 2.6 不做的事

- 不为合成缓存指标调优。
- 没有 A-1、A-2 之前不动历史的格式。
- G2-7 不超过 3 个 PR。做不完的留到 G3。

## 3. 沙箱

根因和修法见 `01-audit-report.md` §6 与 D-38。要点：

- 改两处绑定来源，约 40 行。
- 用托管环境的原生作业反复验证，不依赖 owner 的机器。
- 通过之后把原生作业加进每夜运行。这样“能跑命令”这条能力第一次有了持续的正向验证。
- `/input`、环境卡片的执行检查这些依赖原生沙箱的功能，代码可以先写，真实验收等原生作业通过之后做。

## 4. 测试与 CI

| 项目 | 现状 | 做法 |
| --- | --- | --- |
| 测试夹具的内存错误 | 第三次出现；PR 门禁只有 Release 配置 | 改了 `tests/*.cpp` 的 PR 合并前运行一次 `asan-affected`（D-40） |
| 时限余量 | 最大占比 36% | 继续按 D-20 的规则，超过一半就分片。`run_cli_e2e` 在 ASan 下 432 秒，是最长的单个套件，超过 600 秒时拆 |
| 每夜作业 | 完整矩阵 | G4 通过后加原生沙箱作业；G6 加 TSan 作业 |
| 冻结配置的重复恢复（PERF-1） | 一次历史查询里恢复多次 | Store 内按 `config_snapshot_sha256` 缓存已恢复的配置对象。内容不可变，哈希在第一次恢复时已经核对。预算 80 行。看托管 CI 里 CMake ASan 的总耗时（现在 2,800 到 3,100 秒）有没有下降。优先级低，在 G6 顺手做，不为它单独开诊断 |
| 性能测量的依据 | 本机全量构建的几次单独测量在 472 到 1,900 秒之间【报告】 | 本机的单次测量不作为结论的依据。要比较就看托管 CI 同一作业的耗时 |

## 6. 两条产品层面的提醒

现在都不动，记在这里。

- **控制库的体积。** 每次调用的完整请求体都存进库，29 次调用就超过 16 MiB。G9 做“交付确认后清运行态”时一并处理。
- **四角色的固定开销。** 最小的请求（写一个三行的文件）也要 9 次调用。G3 的对照评测会给出它和普通单 Agent 的差距，快路径决定简单请求要不要走完整流程。评测之前不改架构。
