### 5.2 导出为什么失败，现在能不能补上

- **失败点。** 旧代码用业务工作区的写文件接口写 `output-intent.json`。这个接口会按文件工具的配额清点同目录的文件，同目录里的控制数据库超过了 16 MiB 的单文件上限，接口返回非成功，程序把它报成 `UnknownOutcome`（见 #111 的差异）。【静态】【报告】
- **失败发生在导出的第一步**，报告里的 `output_path=null` 与此相符。【推算】原目录里有没有留下半成品，要看一眼才能确定。
- **修复。** #111 把回执改由 `run_retain_receipt` 写入（`src/run_cli.inc:76`），不再清点同目录；文件已存在时只校验内容并补做同步。【静态】
- **重跑同一条命令会发生什么。** 请求在库里是 DELIVERED 时，程序把库以只读方式打开，跳过准入和模型调用，只做交付核对和导出（`src/run_cli.inc:616-626`、`:642-653`、`:668-676`）。交付已确认时 `run_delivery` 只核对、不写库（`:316-319`）。已有的输出文件逐个核对哈希，不覆盖（`:381-386`）。【静态】
- **结论。** 原请求的 UNKNOWN 可以用产品自己的恢复路径关闭，不需要调用模型。只有一种情况会被拒绝：`output/` 已经存在但没有 `output-root.json`（`:350-351`）。做法见 `04-plan.md` §3 的 R0。

## 6. 沙箱原生验收的根因

### 6.1 现象

原生验收在 owner 的机器上一直是 BLOCKED。11-14 按 D-22 在托管环境加了一个手动作业，先用 sysctl 放开用户命名空间再运行。结果仍然失败，退出码 77（运行 43558975976）。【CI 日志】收敛报告记录的现象是“bwrap 读取 `/proc/<pid>/fd/5` 被拒绝”。【报告】证据包在对象存储上，本环境下载不了。

### 6.2 原因

启动参数把工作区和运行时目录写成父进程的描述符路径：

```
--bind    /proc/<wls 的 pid>/fd/<工作区描述符>   /work     （src/sandbox_posix.cpp:1644）
--ro-bind /proc/<wls 的 pid>/fd/<运行时描述符>   /usr      （src/sandbox_posix.cpp:1650-1651）
```

1. bwrap 在 clone 出子进程之后才解析绑定来源，用的是 `realpath()`，失败时报“Can't find source path”。【查证】这时子进程已经在新的用户命名空间里。我查的是较早版本的源码，托管作业用的版本请以原始报错为准。
2. 跟随 `/proc/<pid>/fd/N` 需要对目标进程有 ptrace 读权限。手册页的草案写了默认规则的两条出路：调用者的能力覆盖目标，或者调用者在目标的用户命名空间里有 `CAP_SYS_PTRACE`。【查证】
3. 进入新用户命名空间的进程对外面的父进程两条都走不通，所以被拒绝。这一点文档没有直接写，由下面的试验证实。

我在本环境验证了这个内核行为（内核 6.18，`unshare`）：【实测】

| 做法 | 结果 |
| --- | --- |
| 同一个用户命名空间里的子进程读父进程的 `/proc/<pid>/fd/3` | 成功 |
| 进入新用户命名空间的子进程读同一个路径 | Permission denied |
| 同上，用 `realpath()` | Permission denied（errno 13） |
| 新命名空间里的子进程用父进程解析出的普通路径做绑定挂载 | 成功；父进程从 `/proc/<子进程>/root/...` 读到的设备号和 inode 与原目录一致 |

这说明：只要 bwrap 不是 setuid 安装，现在的启动参数在任何主机上都启动不了。托管作业里的 bwrap 就是按普通权限安装的（`.github/workflows/ci.yml:322`）。这和 AppArmor 无关。AppArmor 对用户命名空间的限制是 Ubuntu 24.04 上的另一道关，托管作业里已经用 sysctl 放开了（`.github/workflows/ci.yml:301`）。

本环境的内核版本和 Ubuntu 24.04 不同，证据包我也没有看到。请 agent 先核对证据包里 bwrap 的原始报错是不是“Can't find source path /proc/…: Permission denied”。

### 6.3 修法

把两处绑定来源换成父进程自己解析出的绝对路径：父进程读自己的 `/proc/self/fd/N` 得到路径，这一步总是允许的。

安全性不下降。代码在放行命令之前已经核对了实际挂载的目录：比较 `/proc/<子进程>/root/work` 与固定描述符的设备号和 inode，不一致就拒绝（`src/sandbox_posix.cpp:1689-1717`）。那段代码的注释也写了，bwrap 反正会用 `realpath()` 解析来源，防替换靠的是挂载后的核对。

不把目录描述符直接传给 bwrap 是对的（`:1646-1647` 的注释）：命令继承到宿主目录的描述符就可以向上走出沙箱。

原生路径从来没有跑通过，修掉这一处之后可能还有别的问题。托管的原生作业可以反复运行，用它迭代。细则见 D-38。

3. **把合成缓存占比当成真实效果的代理。** 11-11 的 G1 门禁和 11-14 的 D-28 都围绕它定了门槛。真实端点上它没有预测力（§5.5）。它作为防止布局退化的回归检查仍然有用，但不该再为它调优。
