## 1. 当前批次：审核修订与内核加固

本批完成四类工作：

1. 将角色行为、事件唤醒、结构化交接、计划 DAG、轻量记忆及环境卡片纳入 v0.4.1 目标蓝图。
2. 修正 AMEND 默认处置、版本绑定、控制门禁、UNKNOWN、副作用幂等、审核容量、配置快照、缓存依赖和收尾恢复规则。
3. 在现有 C++ 内核补齐有界确认、Worker 操作取消和生产说明变更后的候选失效；扩展多团队变更及饱和调度回归。
4. 引入修订后的 Schema／SQLite 契约和可运行的 Python 参考验证，验证返工消息容量、约束覆盖、记忆版本与修订、幂等及清理持久化等边界。

代码仍为合成内核。SQLite 参考事务没有接入 C++ TaskEngine，完整模型运行器、真实业务工具、沙箱、守护进程、记忆引擎和 MCP 均不因契约测试通过而变成已实现功能。

## 4. 必须随能力落地的约束

### 变更与控制

AMEND 后，每个活动任务需显式 update／keep／cancel，处置绑定当前请求版本，遗漏保持暂停。计划绑定需求，任务绑定计划和需求，Worker 确认独立的 TeamLead 指令版本。确认、取消、查询和核对使用各自控制门禁；新业务派发还需当前完整版本、可执行状态、权限和预算。

当前 M1 采用更保守的全局计划／逐团队确认屏障；未来 DAG 中的 keep 不得绕过上述版本关系。任何非幂等操作的 UNKNOWN 都先核对，包括工作目录中的写操作。

### 容量与恢复

审核所需的 Dispatcher 和 Worker 容量在普通准入阶段常态保护，同时明确等待态释放规则。异步任务不得占住普通执行槽同步等待同池子任务。S1 必须验证启动隔离、执行中崩溃、取消不冒充成功、UNKNOWN 不盲重试，以及已交付任务仍能恢复未完成的收尾。

### 配置、费用与验收

请求准入时冻结已解析 Root 默认、角色覆盖及完整配置版本。既有请求的新团队和恢复实例继续使用该快照。每次真实模型尝试纳入预算，未知用量保留未知，默认不自动付费重试。缓存测试只对全部前缀依赖相同的输入要求相同 hash。

结构化消息先校验形状，再核对身份、作用域、完整版本及业务要求。原文子串检查仅证明摘录忠实；初始需求抽取另有完整性判定。模板快路径执行确定性业务验收器，不能用 Schema 合格代替必需证据。

### 记忆与持久化

记忆采用轻量四态，同时记录实际加载版本、独立实例、反馈版本和修订基线。当前版本的分数默认与历史版本分开；可检索不等于已经独立验证。SQLite WAL 使用 FULL 起步，短事务内完成聚合版本检查和事件写入，模型或工具等待不进入事务。

## 6. 每批完成定义

每批必须交付源码／契约、蓝图或任务卡更新、可重复构建命令、实际测试报告和完整提交 SHA。报告区分内核合成测试、SQLite／Schema 参考测试、真实系统集成和供应商实测，不合并计算为一个已经完成的产品验收。

推送后核验远端分支与本地交付版本，并检查该提交的 CI。遇到远端前进先同步审核，禁止覆盖未见改动。任何真实能力的接入都必须继续通过已有身份、版本、幂等、审核和回执关口。
