G2 顺序：R0 原请求导出处置 → R1 探针及 A-1/A-2 → R2/U1 → R3/U2 → R4 同一报告 → R5 最多三个小优化及复验 → R6 出口。R6 负责六格式冻结、蓝图迁移、旧 ROADMAP 保留及入口同步、CHANGELOG 和版本记录；真实结果仍由 STATUS、报告和最新交接维护。
冻结值：`structured-v3`、`lean-v1`、`fixed-role-v1`、`append-fold-v1`、`guided-v1`、`bounded-v1`；旧 `framed-v1` / `structured-v2` 保持原解释。

真实运行线与代码线可并行，在制 PR ≤3；G4-N1/N2 不必等待 G2 出口。仅文件工具的 G3 任务可在 G2 出口后进行，不必等待 G4。
G7 依赖 G4 的命令能力；G9 依赖 G6；其他入口条件与切分以唯一前向计划为准。Store 不继续拆分，除非满足 D-44 的实际构建触发条件。
每个真实模型阶段先过朴素模型合成剧本；合成结果不替代真实验收，源码合入不替代阶段出口。
停止按 D-32 限定受影响请求/工作线；实际调用按 D-34 保留次数、token、墙钟额度，当前自动重试为 0。未知费用不等于零。
Strict 仍为默认，Standard 显式选用；托管与 owner 本机结果分别登记；本机配置不由 agent 修改。

每个阶段出口更新一页报告、STATUS、CHANGELOG、版本及计划 §1 状态；从 0.13.0 起在 main 上打带注释标签，不建 GitHub Release。
前向计划只有 §1 状态列和 §15 由 agent 维护；旧审核中的工作规则、任务文本和已完成记录保留，历史不改写。
v1.0 验收报告由 owner 过目；对外发布另行决定。Windows 目标为原生构建/文件流程，命令先经 WSL。

R2/R3/R5 未完成、失败或 usage UNKNOWN 时，阶段摘要只引用事实状态，不改写为通过；版本标签由 root 在实际出口条件满足后处理。
