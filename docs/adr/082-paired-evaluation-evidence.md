# ADR-082：固定小任务与单 Agent 对照的原账本评测框架

日期：2026-10-27。状态：本地框架实施；供应商实测另行验收。

## 决定

R3.3c 先交付 `scripts/evaluate_r3.py` 的 plan/report 两个离线入口。
计划在一个尚无模型 attempt 的已准入请求上生成，固定五项任务和两个条件，共十个样本位。
任务为原生文件工具往返、两任务部分 AMEND、否定验收返工、返工耗尽升级、原版本交付回执。
共同条件冻结精确模型 profile、reasoning、环境依赖、工具集合、初始约束、工作流政策、
逐维度预算、尝试数和墙钟上限。计划的规范 JSON 指纹绑定随后每项运行索引。

报告以只读 SQLite 事务读取原 `call_attempts`、请求预算、操作、问题、提交与交付记录。
新增 live attempts 的身份来自 `live_attempt_execution`，实际观察来自
`live_transport_observations`；追加用量来自 `live_usage_projection`，并核对原结算身份。
账本已花费值必须能从该请求的全部原 attempt/投影重建；原始结算不会因为报告而改写。

single_agent 条件必须只有同一个 principal/team 的 Worker 模型调用；multi_agent 条件至少有两种实际模型调用角色。
同一数据库/请求不能重复用于两个样本位，硬链接也不能绕过该检查。未提供的运行仍占据样本位，
失败、无效证据、未知费用、未结算调用和不完整对照分别记录，不能以筛掉样本制造优势。

## 准确边界

该框架不启动模型、不解析秘密、不自动重试、不提供新的执行权限。
Store 410 的实际调用必须经过独立宿主授权及原预约/发送/结算路径。
本地 Fake 或 loopback TLS 只标为 synthetic，不能通过修改报告模式改成 provider。
provider 标签表示保存的原执行类别与观察，仍不证明供应商底层模型身份或计费完整性。

结构化判据检查原工具状态、当前任务版本、不同原任务的 update/keep、同一任务的否定验收与后续接受、原升级问题及确切交付证据；
它们不证明任意文本需求的语义质量。领域质量评分与真实同模型比较继续单列，
框架始终不输出普遍质量/成本优势结论。墙钟值由宿主运行索引提供并明确标注来源，
不冒充供应商延迟或从数据库时间戳推造精确执行时间。

## 备选与取舍

不采用人工填写 token/费用/通过数的汇总表，因为它不能核对原样本与预算守恒。
不在评测工具中另建一个模型调用路径，因为这会复制并绕过 Store 的发送和计量关口。
当前单 Agent 执行器的未来宿主接入必须保持共同预算与工具授权，不能把多角色脚本换名为单 Agent。

## 验证要求

实际临时 CLI/SQLite 的已确认交付、失败模型调用、零预留未知费用、条件不一致、
同请求重用、计划/评分规则变更、缺失数据库、账本差额与只读前后原行一致。
新增框架结果与完整源码门禁见本批独立验证报告；不把空报告或 fixture 当作真实模型评测。
