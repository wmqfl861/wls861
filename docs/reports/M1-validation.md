## 4. 演示观察

两项独立请求使用不同的 Dispatcher 和团队身份；两个普通工作回调通过 latch 与原子计数确认实际重叠，`peak_parallel=2`。最终有 38 条实际提交事件，两项请求均为 `COMPLETED`，资源状态均为 `CLOSED`。

演示分别经过创建计划、build/review 团队、负责人说明、Worker 应用、一次 `test.echo` 合成操作、候选提交、独立审核、Dispatcher 验收、Root 合成回执以及资源状态收尾。输出的成果摘要由 Python 根据固定 `hello` 字节另行核对。

这证明了不同请求能通过调度器并行推进，以及各模块能按同一版本/身份契约连接。它不是模型质量测试、真实工具执行、通用工作流运行器或生产交付测试。

## 5. 独立审查与已修复问题

独立审查覆盖了最新需求与旧版冲突、TaskEngine 的变更/恢复/审核，以及帧和事件容量。以下问题均有对应源码修正与主测试回归：

| 问题 | 当前处理 |
| --- | --- |
| TeamLead 改说明后，旧 Worker 应用状态仍被视为有效 | 独立指令版本与应用版本；本团队旧 Prepared 取消、Running 转 Unknown；必须重新确认 |
| 重开 Journal 后调用方可能忘记手动隔离旧代次 | 构造时自动持久化新的执行代次，完成后才开放 API |
| 普通事件额度满后无法结束操作、取消或恢复 | 普通、诊断和必要控制事件分开；诊断有界；结算与收尾保留通路 |
| 切换候选后同一成果版本可被赋予新内容 | 成果版本高水位持久化，跨候选和 AMEND 仍不能复用旧版本 |
| 验收后、交付前的负面审核无法撤销旧批准 | 允许当前审核结果撤销批准，清除旧包/回执；预算满时仍可记录一次性撤销 |
| 候选/审核全豁免预算会无限增长 | 普通候选和审核继续计预算，仅已批准状态的负面撤销使用控制事件 |
| 超长状态触发 Journal 拒绝并毒化运行实例 | append 前检查硬帧与普通半帧额度，并按未结算操作预留空间；超限返回 QuotaExceeded，现有实例仍可取消/收尾 |

独立临时探针另核对了 13 个针对性断言；它属于审查证据，不另计为最终 49 个用例。更小帧配置的结算空间提醒已纳入动态预留：每个更新请求 64 KiB，加每个未结算操作 8 KiB，且证据引用限定 512 字节。

## 7. 已知限制与下一批

`Actor` 是受信宿主上下文，外部认证、操作系统沙箱及凭据管理未实现。运行时状态互斥区与同步写盘目前会短暂串行状态提交；模型或执行回调不会在该锁内等待。Scheduler 不抢占已经运行的回调，不能修复永久阻塞或同池循环等待。

Journal 存放完整状态快照与历史，没有压缩或生产保留策略。普通容量保护和结算预留不等于无限存储保证；重复宿主恢复/清理以及磁盘、设备故障仍需后续存储运维处理。未进行断电、介质故障、生产负载或 ASan 验证，不能用 UBSan 代替这些检查。
