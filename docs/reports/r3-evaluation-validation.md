## 已实现范围

`plan` 固定五项任务、两种条件和十个样本位，锁定材料、模型/推理、环境、初始约束、工具、
流程政策和等额预算。`report` 使用原 SQLite 只读事务，核对原调用、投影用量、请求预算、
任务处置、原拒绝/返工/接受、用户问题、提交字节及准确交付回执。没有新增执行器或模型入口。

单 Agent 条件要求同一 principal/team 的 Worker；多个 Worker 不能因角色名称相同而通过。
AMEND 必须有两个不同、当前已接受的任务，其原处置分别为 update 和 keep。返工成功要求同一
原任务有否定验收、较新修订接受及该团队的原返工计数。升级要求原 escalate_task 对应当前用户问题。

已知用量逐维度累计并与原预算重建比较；未知单列，零预留也不等于已知零用量。
失败、无效和未执行样本全部保留；fake/local TLS 不能改标为 provider。
输出明确声明没有建立一般性的质量或费用优势。

## 实际开发验证

测试调用真实 C++ CLI，在普通 UID/GID 65534 的一次性私有目录创建实际 SQLite、工作文件和交付。
模型决定均为固定 Fake 脚本，真实供应商及付费调用为 0。

开发首轮发现两项夹具假设错误：模型推理字段实际位于原 envelope 的 `context`，以及空原约束
目录不能搭配另一个 fixture 的约束引用。修正读取位置和夹具原约束一致性，没有弱化生产检查。

独立交叉复核又发现并修正三项框架问题：角色集合不能证明只有一个 Agent；跨任务分别满足的
返工/接受不能拼成同一任务成功；读取结果的 32 MiB 限额必须在逐行累计时生效，不能先取完再检查。
相应用例包括实际两个 Worker 的受控缩减证据、全部取消的真实 AMEND、无原拒绝的返工计数，
以及经原 CLI 完成的同一任务拒绝→纠正→再次接受正向流程。

交叉复核修正后的聚焦执行为 **23/23 通过，3.811 秒**；宿主命令总耗时 3.891 秒。
该结果使用本轮联合 Release CLI 的实际 Store 410；不拿先前 18 项在基线 CLI 上的开发结果充作最终成绩。
最终冻结源码再次通过统一门禁：Release0022为23/23、4.48秒，Release0002为23/23、3.88秒，
ASan/LSan为23/23、38.06秒。完整命令、最终输入清单和日志hash见五节点报告。

```sh
python tests/r3_evaluation_tests.py /path/to/build/wls /path/to/source
```

23 项覆盖原已确认交付正向、原拒绝/纠正/接受正向、未知费用、失败模型调用、缺失样本、
模型/预算/材料不一致、角色/主体错误标注、AMEND 取消误判、无原拒绝的返工计数、
计划与评分规则改写、重复样本/硬链接复用、超过墙钟、账本差额、只读前后全表相等、
特殊文件/重复 JSON 及逐行读取容量。方法数与 CTest 套件数分别统计，不累加重复执行次数。
