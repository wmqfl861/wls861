## 1. 两种有界入口

| 入口 | 当前行为 |
| --- | --- |
| `run-fake` | 保留原单任务显式脚本流程；404 数据库增加原始反馈持久化和跨运行历史 |
| `pump-fake` | 从持久角色待办领取工作，推进独立任务的计划、说明、确认和 Worker 工具；达到上限、等待、缺脚本或错误时返回 |

`EventRuntime` 是同步、有限次调用的宿主运行器，不在数据库事务中等待模型或工具，不建立长期线程或忙轮询。一次 pump 最多 1–64 次 Fake 调用，每任务最多 1–16 次 Worker 调用；默认分别为 12 和 1，管理调用还受冻结配置约束。达到本次上限后，尚未完成的待办仍在数据库中。

两个运行入口都不会为 WAITING 任务自动调用模型或业务工具：`pump-fake` 跳过该任务继续其它可运行任务，旧单任务 `run-fake` 在任何自动重绑定或重发说明之前返回 NotReady。允许的诊断与控制仍走独立通路。这里的验证范围是有限同步回调的释放与独立推进；全局 Dispatcher/Worker 审核双容量、公平并发调度、请求 strand、Asio 协程和只读连接池仍是后续工作。

## 2. SQLite 404 与升级

`006_event_runtime.sql` 在已知的 403 数据库上增加以下结构：

| 表 | 职责 |
| --- | --- |
| `event_runtime_metadata` | 分发迁移资产的 SHA-256 和实现版本 |
| `event_inbox` | 每个角色、任务主题的待办及 PENDING/CLAIMED/DONE 状态 |
| `event_actor_claims` | 当前领取 token、generation、捕获的具体 ID、原需求修订及执行代次 |
| `worker_waits` | 等待原因、generation、原始完整绑定以及 WAITING/AWAKE/SUPERSEDED |
| `model_tool_feedback` | 原 attempt、完整响应、原绑定、完整工具结果或错误和不可变哈希 |

升级在事务中执行，失败回滚，迁移指纹不符拒绝。既有请求、冻结配置、事件、操作、结果/输出和调用账本保留；已有请求通过一次持久启动事件建立当前待办，不把旧事件记录改成已经消费。原 `schema.sql`、004、005 资产保持字节不变。

Store 构造函数第六个参数为 006 资产。原 402/403 调用方可以继续使用原接口；打开 404 必须提供所需的已分发迁移资产。CLI 新建库和写者升级使用 404。ReadOnly 查询不升级、不取得写者租约、不增加执行代次。

仍不自动升级缺少完整请求快照的非空 401 参考库，也不把 M1 Journal 当 SQLite 导入。测试中的事务回滚和重开库不等于整机掉电实测。

## 3. 事件领取与逐项确认

状态与事件、对应的角色待办一起持久化。只有已实现的唤醒原因参与路由；模型预约和普通用量结算不会自行产生下一轮模型工作。

Dispatcher 是请求级身份，但 AMEND 的任务 A、B 分别有 `subject_task_id`。Worker 和 TeamLead 的 inbox 只对应自己任务。事件 ID、管理命令 ID、模型 attempt ID 和业务幂等键继续承担不同职责。

1. `claim_events` 在短事务中领取有界的具体 inbox ID，保存 token/generation、当前身份、需求修订与代次；领取不表示处理完成。
2. 模型和工具在事务之外执行。模型调用仍先持久化完整输入和预算预留，返回时先保存原响应与用量，再核 Schema、权限和原绑定。
3. `finish_events` 只确认调用方列出的、确实属于该次领取的 ID。未列出的已领取项回到 PENDING，领取期间到达的新事件不受影响。
4. 旧 token、旧 generation、旧需求修订或旧代次不能确认新工作。自己的计划/说明变更不会被误当成跨需求授权。
5. 缺脚本、模型/Schema/工具错误、等待和调用上限不会隐含批准。运行器返回阻塞原因，并保留未完成项。

重开写者首先围栏活动请求、旧模型调用和操作，然后释放遗留 claim 为可重新处理的待办。它不重新执行旧工具；运行中的副作用仍按已有规则进入 UNKNOWN。当前数据库写者租约是恢复领取的权威，不另加可能同时过期的分布式租约。

`pump-fake` 的 `pending` 汇总保留整个请求的未完成待办，包括终止团队留下的历史项；这些项可见不会使终态任务重新执行。宿主汇总读取有明确容量上限，超限直接报错；角色 `inbox` 则按其作用域返回有界页面。

## 4. 独立多任务与逐任务 AMEND

初始计划可以包含一个或多个独立 `team_task`，数量受请求冻结的 `max_teams_per_request` 限制。每个节点必须有合法 TaskBrief、已登记约束覆盖及可用模板。依赖边、跨功能调用和自动审核仍明确拒绝。

发布独立计划、初始任务及团队分配在一个 Store 事务中提交。失败不能留下“计划有两个节点、实际只建了一个团队”的半个结果。后续该入口保留已分配节点及模板身份，不隐式换团队、工作目录或模型配置。

AMEND 仍由 Root 追加不可变原文及整份当前约束目录。每个现有任务暂停，Dispatcher 得到逐任务待办。宿主在 `--dispositions-file` 显式给出本次决定：

```json
{
  "alpha": {
    "disposition": "update",
    "rationale": "按本次修改更新 alpha，并重新下达和确认说明。"
  }
}
```

每个值必须且只能包含 `disposition` 与非空 `rationale`；决定为 update、keep 或 cancel。TaskBrief 来自当前已提交计划，模型参数不能补写宿主身份、代次或 CAS。首次修订计划和本次选择的处置一起提交，审计保留被处置任务的原 state_version。

遗漏 beta 时，beta 的旧 applied 值不构成继续许可，它的待办仍保持未完成。之后单独给 beta 的 keep，可针对同一当前计划完成，不需要再调用 Dispatcher 发布另一份计划。keep 仍增加任务修订，要求新的 TeamLead 说明和 Worker ack；取消不会宣称撤销旧文件效果。

同一写者实例内，后补 beta 的处置不会改变 alpha 的状态、说明或代次。若通过新 CLI 进程补处置，打开写者仍先执行既有请求恢复围栏；这与重新发布计划是两个不同的状态变更。

## 5. 工作目录映射

`--workspaces-file` 是受信宿主输入，格式为节点 ID 到绝对目录路径的对象：

```json
{
  "alpha": "/path/to/demo/alpha",
  "beta": "/path/to/demo/beta"
}
```

CLI 在打开数据库写者前检查所有目录的实际 identity、相同/嵌套/别名关系以及数据库位置，避免先执行一个任务再发现另一个目录冲突。WorkerTools 和 Store 在绑定及派发时继续检查实际身份和策略；这项预检不取代派发门禁。

各任务持有各自的 WorkerTools。未提供任何目录时可以使用受控 note 流程；提供部分目录不会让未绑定任务隐式取得文件权限或混用兄弟目录。数据库必须在所有业务目录之外，已绑定目录和执行策略不随重启漂移。

## 6. 持久等待与唤醒

本批实现的是宿主 `wait`/`wake` 控制，不把它描述成完整 Worker ask、TeamLead/Dispatcher 逐级问题与用户 ANSWER 协议。

`wait` 保存任务、原因、当前完整绑定和新的等待 generation。WAITING 同时进入 Store 的新 Worker 调用及新业务派发门禁，不能通过绕开 EventRuntime 直接预约/prepare/start。允许的诊断、说明确认和取消仍使用各自控制通路。

`wake` 必须指定确切等待 generation，并使用当前有效的宿主身份。纯执行代次变化的恢复可以唤醒相同语义目标；需求、计划、任务或说明目标已经改变时，旧等待不能为新任务提供授权。原等待绑定作为历史保留。

唤醒只结束这一项等待，不修改 AMEND 处置、不伪造 applied 版本、不解除 UNKNOWN。新的说明、确认或宿主核对仍按原门禁执行。等待 task A 不会把整个多任务请求改成 WAITING_INPUT，也不会唤醒 task B。

## 7. 原始反馈与跨运行上下文

404 路径给模型尝试配对不可变反馈记录，涵盖业务、只读诊断、控制和显式错误。诊断结果保存的是当时实际观察到的字节和参数，不能在重启后重新读文件来冒充原观察。账本中的 `accepted=1` 仍只表示当时绑定资格，不等于工具已成功或业务已验收。

Worker 后续上下文按持久尝试顺序恢复自己任务的响应、完整结果、原绑定、调用序号及状态，不带兄弟任务的工具记录。不嵌入以前的完整 `request_envelope.context`，避免历史递归增长；原完整调用输入仍可用 `attempt` 记录追溯。

旧需求/代次的记录保持原标识，不重新盖当前版本。中断发生在响应、操作和反馈之间时，已经持久的事实保留；未保存的观察明确显示缺失/未知。已保存业务操作不会因补历史而再次派发。上下文仍有显式条数和字节上限；无法完整容纳时，在新 attempt 预约前阻塞，不静默截断或自动压缩。

重复接收同一已结算响应时直接返回其原反馈；同进程并发接收也按 attempt 串行等待同一份记录。若响应已经结算但反馈尚未持久化，重放明确拒绝，不再次读取诊断或执行业务来填补缺失。原操作事实仍可独立查询。

管理角色使用当前请求原文、计划、任务、说明、预算和待办快照。缓存前缀仍按实际文本与冻结依赖计算；添加动态历史不承诺供应商缓存命中。本批没有真实供应商调用。

## 8. CLI 与脚本

新增 `pump-fake`、`inbox`、`history`、`wait`、`wake`；原命令继续保留。`inbox/history/show/events` 使用只读 Store。`history --limit` 的不足是明确容量错误，不是静默丢弃较早记录。

Fake 脚本可以沿用数组，也可以分组：

```json
{
  "default": ["Dispatcher 的正常 FakeModelStep 对象"],
  "nodes": {
    "alpha": ["alpha 的 TeamLead/Worker FakeModelStep 对象"],
    "beta": ["beta 的 TeamLead/Worker FakeModelStep 对象"]
  }
}
```

上例只说明分组层次，字符串占位符不能直接运行。可直接使用仓库 `tests/fixtures/s13_fake_initial.json` 与 `s13_fake_amended.json`。每个逻辑角色/节点在一次显式 pump 中从调用序号 1 开始；attempt ID 和持久历史不重置。缺少所需脚本步骤时，该角色保持待办，不为它新增预算预约或擅用另一个节点的步骤。

本机 CLI 仍由数据库所有者操作，不提供远程认证或并发写者控制服务。第二个进程不能在一个持租约的长调用期间通过本 CLI 取消它；跨进程 socket/API 控制仍待 wlsd。
