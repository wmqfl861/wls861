## 02｜目标、范围与硬边界

建设可配置任意功能 Agent 的通用系统，C++ 为核心，Linux 首先可用，业务模块保留 Windows 迁移边界。MCP、Agent Skills、插件及外部 Agent 双向互通属于目标能力；兼容须按实际协议、版本、部署和权限测试，不承诺全生态无修改可用。

主流模型端点通过适配器接入。用户可独立设置各角色模型和思考等级，不因缓存或费用优化擅自替换。具体生产模型、接口版本、限额和首批清单未定。

只有 Worker 执行用户业务命令、文件变更及执行类工具。其他角色可以使用明确的管理接口、授权资料视图和证据视图；读取 Skill 不授予执行权限。接单、状态保存、队列、进程治理和受控清理由运行时承担，不属于上层 Agent 直接执行业务命令。

**三项权威边界：** 当前任务事实来自 TaskEngine；工具入口和参数来自 ToolRegistry；权限与强制规则来自 PolicyEngine。长期记忆可引用和解释这些内容，不能通过 RAG 的旧记录替换它们。



## 03｜四角色与请求级并发

| 角色 | 生命周期 | 负责 | 禁止或不承担 |
| --- | --- | --- | --- |
| Root 主入口 | 功能级长期逻辑身份 | 接单、消息路由、澄清转达、进度和最终交付 | 全局串行规划、业务验收、任意执行命令 |
| Dispatcher 请求调度器 | 每独立请求一个有效实例 | 明确目标、计划、分派、协调、处理变更、审核验收和汇总 | 绕过独立审核、越权审批、直接业务执行 |
| TeamLead 工作负责人 | 每团队一个 | 细化本团队任务、解释调整、指导 Worker、收集证据与经验报告 | 擅自改变全请求目标、越级控制其他团队 |
| Worker 执行者 | 每团队一个有效执行身份 | 在授权内使用文件、进程、MCP、Skill、专业工具 | 自行再生 Agent、扩大权限、代签审核 |

一个 Dispatcher 可管理多个 TeamLead＋Worker 团队。不同功能 Agent 使用相同结构；一个功能身份可以同时服务多个独立请求。逻辑层级不要求操作系统父子进程完全同构，所有临时进程由运行时监管。

接单快路径不调用模型理解和筛选，建议保留认证、格式、幂等、请求大小和资源准入。创建逻辑请求后即可回执；资源不足时排队，不无限启动进程。具体准入政策仍须配置。

**一个独立请求一个调度器，不是一条消息一个调度器。** 修改、查询、补充、取消路由到原请求；重复提交返回原状态。替换建立新旧请求关系并处理旧操作。

跨请求并行；同一状态对象的短提交有序。模型、远程调用和进程执行不在数据库锁或长事务内等待。运行时维护有效执行代次，恢复后旧进程和迟到模型结果不能继续派单或提交。

资源配额分为调度器、团队、模型请求、工具进程、内存、磁盘、费用和时限。等待不持续推理，审核与交付保留容量。修改同一分支、数据库或外部对象通过资源仲裁处理，不把冲突都推回 Root。

## 04｜任务契约、变更与状态

| 信息组 | 建议字段 |
| --- | --- |
| 归属与关联 | tenant_id、project_id、request_id、task_id、parent_task_id、team_id |
| 业务要求 | goal、scope、non_goals、acceptance_criteria、input_artifact_refs |
| 独立版本 | requirements_revision、plan_revision、applied_revision、state_version |
| 执行身份 | attempt_id、lease_epoch、command_id、idempotency_key |
| 运行约束 | permission_ref、budget_ref、deadline、reply_to、trace_id |
| 成果 | artifact_id、artifact_version、content_hash、validation_evidence_refs |

AMEND 修改原要求，REPLACE 替代原任务，NEW 新增独立任务。变更路径为：记录新要求→阻止旧版本新副作用→TeamLead 明确停止/保留/新增项→核对进行中的旧操作→Worker 应用→确认 applied_revision。

业务状态建议采用 RECEIVED、CLARIFYING、QUEUED、RUNNING、ADJUSTING、WAITING_INPUT、SUBMITTED、VERIFYING、ACCEPTED、HANDOFF_PENDING、COMPLETED 及异常终态。资源状态独立为 STARTING、ACTIVE、DRAINING、STOPPED、CLEANING、CLOSED/CLEANUP_FAILED。

**已接收不等于已执行；已发修改不等于已应用；已提交不等于验收；验收不等于交接；交接不等于完成清理。** 状态更新核对预期版本；消息去重与业务操作幂等分开。有副作用的未知结果先核对，不能盲重试。



## 05｜Agent 互调与工作流

AgentRegistry 登记功能身份、能力名、输入输出契约、认证、配额和版本。InvocationService 把所有本地或外部委派接入同一任务内核。Dispatcher 调用对方 Root，对方创建自己的请求调度与团队；调用方不能直接指挥对方 Worker。

工作流是可校验的计划与运行记录，不是额外的常驻总管 Agent。Dispatcher 提出业务计划，WorkflowEngine 校验并推进。固定外层审核与交付关口，内部允许受约束的动态拆分。

| 节点 | 必须明确的语义 |
| --- | --- |
| agent_task / local_team_task | 调用哪个能力或创建哪个团队，输入版本与责任归属 |
| branch | 使用已校验的结构化结果，不猜自由文本 |
| parallel / join | 汇合条件、失败策略、并发额度 |
| wait_event / wait_input | 等待事件、版本、超时与恢复位置 |
| task_change / bounded_loop | 修改原任务还是新任务，轮次、预算和退出条件 |
| acceptance / handoff | 验收主体、必需证据、正式成果、交付确认 |

开发任务提交固定候选版本即可触发 Review，不能等开发最终完成才启动审核。Review 的“不通过报告”可以是该审核任务的合格交付；开发据此修改并发起新轮次，避免相互等待闭环。模块汇合后还需按契约完成集成验证。

每次流程运行和节点执行都有独立编号；修改流程定义与修改业务要求分开。运行中的流程默认绑定定义版本，显式迁移才改变路径。循环受轮次/预算/截止时间约束；无法继续必须反馈，不能为了成功而跳过审核。

MCP/A2A/HTTP 只是适配入口，不建立绕开授权和版本的快捷通道。外部 Agent 未声明支持的修改、取消、推送或清除不得假装成功。具体协议和端点能力在实现前重新核验。

## 06｜通用基础工具、模型与缓存

通用基础包已获设计方向确认，尚未安装。采用公共成熟程序＋统一 C++ 工具接口＋角色能力包＋任务执行策略。基础工具包括目录/文件读取、搜索、写入/补丁、异步命令、输出/状态/取消、进度/问题/成果登记及能力发现。专业工具依功能包接入。

环境预装一次、版本固定，团队只分配私有工作区、会话与临时身份；不每次重装全部依赖。公共可复用程序不随团队删除。安装权限与执行权限分开，Shell、文件和外部工具遵守同一访问边界；进程资源限制不冒充完整沙箱。

各角色模型和思考等级逐字段独立设置；未设置直接采用所属 Root 的默认快照，不继承 Dispatcher 或 TeamLead 的覆盖值。未设置、明确关闭、供应商默认必须可区分。工具权限不套用模型继承规则，而按角色、功能模板和请求政策交集解析。

ContextCompiler 统一构造稳定角色规则、工具定义、公共资料快照、任务初始要求、追加历史和当轮变化。随机标识与动态目录不放公共前缀。按阶段压缩，不每轮重写全部历史；必要安全撤销不受缓存冻结阻挡。

模型输入缓存、检索缓存、环境复用和工具结果缓存分别计量。CachePlanner 记录端点支持、作用域、时长、最小门槛、字段与费用；未知标未知，不把本地内容命中当服务端命中。任务创建、终止和基础模板生命周期分离。优化目标为合格交付的总质量、耗时、费用，而非无条件追求固定命中率。



## 07｜统一记忆：类型、来源与权威

用户已明确把 Skill、规则和经验统一管理，以 Wiki＋RAG 支持任务推进中的逐步回忆；所有自产或下载内容带标签。统一的是知识身份、索引、关系、版本和使用方式，不是把可信度、权限和用途拉平。

| 类型 | 正式用途 | 关键边界 |
| --- | --- | --- |
| 事实与项目知识 | 理解环境、接口、约定 | 易变事实要核对，不覆盖运行时状态 |
| 经历与经验 | 成败记录、条件、方法比较 | 观察与根因推测分开；结果带范围 |
| 规则 | 强制要求与建议规范 | 强制规则由运行时确定性装载和执行 |
| 程序性记忆 / Skill | 完整步骤、条件、脚本、资源、验证 | 主说明不能随意切片后单独执行 |
| 成果和证据引用 | 可核对交付、测试、对比材料 | 引用明确版本，保留受授权范围 |

成功、失败、部分完成、未知是经验属性，不必建立互不相通的库。一套方法可关联多个正反案例；失败方法的执行推荐价值可以下降，而其风险提醒价值上升。

标签帮助搜索，适用环境、作用域、发布状态与权限必须是可检查字段。下载 Skill 保留原包、来源、版本和校验值；内部修订有独立版本，导入不等于可信发布。记忆粒度以可单独验证、撤销为准，完整操作方法仍保持必要条件与附属资源关系。

Wiki 为带来源与版本的选型解释层；全文、向量与关系索引为可重建查询层。正式记忆记录和 Skill 包是执行依据。不能让 Wiki 自动生成的总结覆盖原始规则和验证限制。

## 08｜发现、读取和工作记忆

建议组合明确绑定、角色常用入口、浅分类、多标签、关键词与向量检索，只有难以选择或复杂组合时调用模型。此组合的具体数据库、分类深度、top-k 和门槛尚未确定。

检索前限制可见范围和发布状态；名称、工具、错误码走精确/关键词路径，模糊表达走语义路径。类别主要辅助排序，不能强制选单一分支后漏掉跨类方法。候选卡片提供适用场景、反例、依赖、版本、证据与不可用原因。

激活指定版本时解析强制前置条件、依赖和严重警示；这些内容不能因为未进相似度前几名被省略。第三方 Skill 先读完整主说明，参考资料与脚本按需读取。发现不授予权限；无匹配时返回缺口，不能硬选最相似方法。

工作记忆属于当前任务/角色，记录目标、约束、阶段、已激活方法、未解决问题和成果引用。Dispatcher 提出任务级方法清单，TeamLead 按实际条件确认，Worker 获得自己需要的指令；不复制上级完整历史。

触发时机：明确任务、进入新阶段、选择新工具、发现异常、方向/环境改变、准备验收。不每步全库检索，不每条事件调用模型。压缩后恢复有效指令，禁止因为摘要遗漏前置条件而继续执行。



## 09｜经验生产、证据、权重与合并归档

借鉴 Hermes 的方向是执行中发现、交接时提炼、优先修订已有内容，而非按数量生成新 Skill。TeamLead 交接包含经验报告，以及可选候选 Skill/补丁；允许“无新增经验”。Worker 提供实际证据，Dispatcher 归类、去重并组织验证，运行时按政策发布。

新的观察及时记证据，正文有实质变化才发新版本。检索、加载、选用、实际动作关联和验证结果分别记录；不把“被用得多”当正确，不把同一次来源总结多遍算多次验证。任务整体成功不自动给所有加载记忆加分。

冲突先检查是否为条件不同、目标取舍或真正同条件矛盾。多方案可以长期并存；有明确危险先暂停，不等待达到失败次数。推荐先过权限、发布和适用性门槛，再比较证据、质量、成本；权重按场景，不预设单一全局分数。

晋升或淘汰看有效独立样本、范围覆盖、反例和风险等级，具体阈值待定。新方法做对照，测试材料避免提前泄露答案；模型、思考、环境与工具版本有必要时都登记。未执行方案不计失败。

合并生成新的带条件版本，不直接拼接冲突指令。旧案例作为来源依据，不把原版本的成功统计无条件转移成新版本验证成绩。无法安全合并时保留选型记忆分别引用各方法。下载包的脚本、模板也纳入比较。

归档退出正常推荐但保留受控历史；失效方法可提炼精简警示继续防错。撤销/隔离不同于普通归档，不能靠回滚恢复危险内容。新版本更新索引、Wiki、缓存及任务绑定关系；普通升级按快照，安全撤销阻止后续相关操作。

## 10｜记忆引擎与 Agent 内核的边界

**此部署路线是建议待确认：独立开发 MemoryEngine，Linux 首版以内置独立模块运行，使用 MemoryBridge 深度接入，后续按需求服务化。** 用户本次要求打包，不自动代表同意具体进程/数据库选型。

| 组件 | 负责 | 不应负责 |
| --- | --- | --- |
| Agent Runtime | 任务真实状态、角色、授权、工具、工作流、交付、进程清理 | 模型自由改公共知识、用 RAG 猜执行状态 |
| MemoryBridge | 传递身份/范围、阶段触发、激活与执行关联、变更通知、交接回执 | 另造任务调度或权限系统 |
| MemoryEngine | 记忆登记、检索、证据、关系、版本、发布/撤销与自身数据保留 | 自行执行 Skill 脚本、扩大权限、操作业务世界 |
| Wiki/索引层 | 可重建解释和查询加速 | 代替正式状态与最终权限检查 |

普通查询并行由程序处理，复杂判断才调用模型；不新增串行“记忆总管”。提炼与排序复用已有模型适配和预算，Embedding 独立配置。需实际复现时由正常 Dispatcher 创建验证团队，Worker 执行。

对外可通过 MCP/HTTP 提供能力，但对自身系统不能只靠模型主动调用；请求开始、阶段变化、操作完成、正式交接、撤销和清理有确定性挂接点。跨模块使用公开契约，不随意改对方内部表。后续转为独立服务时保留语义，新增认证和网络故障处理。



## 11｜验收、交付、经验保留与清理

正常业务路径为：候选成果→当前版本审核/验收→完整交付包写入受控交付区→Root 对外交付→约定的成功确认→停止临时调度与团队→清理请求私有数据。

交付包至少包含成果清单、版本/校验值、完成范围、验收证据、未解决事项、外部副作用说明、交付文档、经验报告和知识去向。报告提交不等于发布，内部成果就绪不等于外部接收成功。

**两项政策仍待选择。** 对外何种回执算成功；交付后是清理运行数据并保留获准交付/最小回执，还是导出后严格清除全部本地请求副本。零记录与无限期历史去重不可同时承诺。

知识沉淀必须是显式授权保留。候选在请求关闭前确定为：已发布、已移交有负责人/预算的验证任务、已导出待验证，或已清除。业务可交付而知识未通用验证时，不无限阻塞原团队；若知识正确性直接关系当前成果，则先解决业务验收。

清理范围包含工作目录、任务/事件载荷、日志、索引、向量、Wiki 派生页、缓存、快照与备份策略。归档属于保留，不等于删除；外部供应商副本按其实际能力处理，不承诺本地删除即可清除全部远端副本。

运行时负责结束进程树与清理，不让 Agent 删除自身状态。先停止新操作、处理在途消息与副作用、撤销临时授权、核对进程后代，再按白名单清理。清理失败单独标记和重试，不抹掉已经成功的业务交付。

**本次打包不执行任何上述清理。** 压缩包交付给用户，不推定用户已经接收，也不以此删除原件或现有资料。
