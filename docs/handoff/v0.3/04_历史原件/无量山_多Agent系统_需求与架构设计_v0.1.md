# 无量山｜通用多 Agent 系统需求与架构设计

**版本：v0.1　日期：2026-10-16　状态：尚未实施**

无量山 · Linux 优先 · C++ 核心

把所有功能 Agent 统一纳入三层架构：主 Agent 管理，子 Agent 明确与调整任务，孙 Agent 执行；多个临时团队并行协作，验收交接后自动回收。

## 02  已确认需求清单（上）

*已确认需求*

以下条款来自用户明确描述；后续建议方案应满足这些条款，不能通过简化实现改变其含义。

| 编号 | 需求 | 落地约束 |
| --- | --- | --- |
| R01 | 建设通用多 Agent 系统 | 开发、Review、资料整理等只是可配置的功能角色，不写死为产品唯一场景。 |
| R02 | C++ 核心；先 Linux，后续保留 Windows 支持目标 | Linux 为首个可用平台；业务核心与进程、路径、权限等平台差异分离。 |
| R03 | 方便配置独立功能的 Agent | 功能通过模板、职责、模型、技能与工具权限配置，不要求每次重写核心程序。 |
| R04 | 所有功能 Agent 采用统一三层结构 | 主 Agent → 子 Agent → 孙 Agent；不把三层结构仅用于某一个业务。 |
| R05 | 主 Agent 统一分配、记录、协调、验收和反馈 | 主 Agent 不直接执行用户业务命令；任务管理动作由结构化控制接口实现。 |
| R06 | 子 Agent 接收并明确任务，正确处理工作调整 | 子 Agent 不是原样转发器；不直接执行业务命令。 |
| R07 | 一个子 Agent 与一个孙 Agent 组成一个团队 | 孙 Agent 负责实际执行；并行工作通过多个一对子孙团队完成。 |
| R08 | 异步接收、反馈；执行中可调整或替换指令 | 接收、应用变更、实际完成必须区分；支持中途改变方向。 |
| R09 | 同一功能主 Agent 承接不同请求和并行模块 | 外部负责人保持稳定；不同团队和任务的上下文、工作状态分开管理。 |

> “不直接执行命令”限制的是主、子 Agent 对业务执行工具的权限，不禁止宿主程序保存状态、派发事件、管理进程或执行受控清理。主、子 Agent 仍可读取被授权的结构化任务记录和已交接成果视图。

| R17 | 可以调用其他 Agent，也能被调用 | 提供双向互通入口及异步任务映射，所有外部调用纳入任务与权限管理。 |
| R18 | 从系统架构上实现较高缓存复用率 | 缓存为公共基础设施；重点优化模型输入缓存，并可观测、可解释、可比较总成本。 |


### 02.1  当前不作出的承诺

不承诺模型判断永远正确、所有端点缓存必然命中、所有外部副作用只发生一次、所有插件天然跨平台，或某项远程操作收到取消消息就一定终止。需要由权限、状态机、幂等核对、证据验收和明确错误反馈控制这些边界。


### 02.2  兼容目标的验收方式

“覆盖主流端点”保留为产品目标；每次发布必须附具体兼容矩阵与测试证据。尚未实现、未取得测试权限、端点不支持和待验证必须分别标示，不能以一个“兼容模式”替代全部验证。

## 03  术语与统一组织模型

*建议设计*

| 术语 | 定义与边界 |
| --- | --- |
| 功能主 Agent / Root | 长期逻辑身份，负责某类业务；一个身份可管理多个项目、请求与团队，不代表只有一个模型会话。 |
| 子 Agent / Coordinator | 单个团队的任务负责人，负责澄清、计划、调整、状态解释和上报。 |
| 孙 Agent / Worker | 单个团队唯一有效的 Agent 执行身份；可启动受控工具进程，但不得再派生第四层 Agent。 |
| 团队模板 / TeamTemplate | 可复用的角色、模型、技能、工具、权限及资源设置；任务结束不删除模板。 |
| 团队实例 / Team | 一次临时工作的子孙组合；独立身份、状态、工作空间和资源预算。 |
| 请求 / Request | 外部提交的一次工作需求，具有唯一对外负责人，可拆成多个关联任务。 |
| 任务 / Task | 可明确目标、输入、版本、依赖、成果与验收标准的工作单元。 |
| 成果 / Artifact | 带版本、摘要、校验信息和访问权限的可交接结果；不等同于临时文件路径。 |


### 03.1  任意功能统一套用


```text
功能主 Agent A（长期身份）
  团队 A1：子 Agent A1 → 孙 Agent A1 → 受控工具
  团队 A2：子 Agent A2 → 孙 Agent A2 → 受控工具

功能主 Agent B（长期身份）
  团队 B1：子 Agent B1 → 孙 Agent B1 → 受控工具
  团队 B2：子 Agent B2 → 孙 Agent B2 → 受控工具

主 Agent 之间：通过有关联编号的任务与成果交接协作
公共运行时：持久化、调度、权限、模型接入、缓存、回收
```

建议一个活动团队负责一个明确任务范围。需要同时处理无关目标时新建团队；同任务的多轮修复可复用尚未关闭的团队。失败恢复时可以更换进程，但任何时刻只允许一个有效执行者代次。

## 04  总体架构与职责边界

*建议设计*


```text
用户 / 外部系统 / 外部 Agent
                 │
       API、CLI、MCP Server、A2A Server
                 │
       功能主 Agent 注册与请求路由
                 │
        主 Agent → 多个临时子孙团队
                 │
C++ 控制内核（确定性的状态与权限管理）
  任务状态 / 事件收件箱与发件箱 / 权限
  调度预算 / 成果验收与交接 / 生命周期
        │                         │
上下文编排 / 模型适配 / 缓存      孙 Agent 执行器
        │                         │
主流模型端点               MCP / 脚本 / 插件 / 命令
        │                         │
任务数据库与成果存储       Linux 平台隔离与进程管理
```


### 04.1  三种不同的职责平面

业务判断层由 Agent 负责理解、计划、冲突处理和验收判断；确定性控制层由 C++ 程序负责身份、版本、状态变更、持久化和授权；执行层负责在明确边界内运行工具。控制内核不是第四个 Agent，也不需要依赖模型维护一致性。


### 04.2  不能只靠提示词维持的约束

| 主体 | 允许 | 拒绝 |
| --- | --- | --- |
| 主 Agent | 派单、查询、协调、审核、确认交接 | Shell、业务文件写入、绕过子 Agent 直接给孙 Agent 下执行指令 |
| 子 Agent | 接单、澄清、修改执行要求、查看结果、上报 | 直接执行业务操作、绕过主 Agent 改变请求目标 |
| 孙 Agent | 按当前有效版本执行已授权工具 | 未经批准扩权、接收其他团队直接指令、自建第四层 Agent |
| 宿主内核 | 结构化管理进程、状态、授权与清理 | 把模型输出字符串直接当可信管理命令 |

机械进度传递、心跳、计费与状态同步由程序完成，不必每一层都调用模型；确需理解变化或作出业务决定时，才唤醒对应 Agent。

## 05  任务契约与事件数据模型

*建议设计*


### 05.1  任务必须先有可追踪的契约

| 字段组 | 建议字段 | 用途 |
| --- | --- | --- |
| 归属 | tenant_id、project_id、request_id | 隔离权限域，关联外部请求。单用户部署也保留隔离域概念。 |
| 层级 | task_id、parent_task_id、root_agent_id、team_id | 确定任务负责人、父子关系和执行团队。 |
| 目标 | goal、scope、non_goals、acceptance_criteria | 明确做什么、不做什么、以什么证据验收。 |
| 版本 | task_revision、applied_revision、state_version | 区分目标要求、已应用要求和并发状态写入版本。 |
| 执行身份 | attempt_id、lease_epoch、command_id | 控制重试、旧执行者和重复指令。 |
| 输入与依赖 | input_artifact_refs、dependency_edges | 记录依赖的是哪份输入、哪版成果。 |
| 运行边界 | permission_ref、budget_ref、deadline | 执行授权、费用/资源限制和超时处理。 |
| 输出与反馈 | artifact_refs、reply_to、correlation_id | 可交接结果及正确的回复路由。 |


### 05.2  所有控制事件使用统一信封


```text
event_id / event_type / schema_version
request_id / task_id / team_id / root_agent_id
command_id / causation_id / correlation_id
expected_state_version / task_revision / lease_epoch
sender_identity / recipient_identity / payload_ref
created_at / deadline / trace_id
```

事件载荷保存结构化内容或不可变对象引用，避免队列反复携带大日志。command_id 用于同一指令去重，event_id 用于消息去重；不能只用 task_id 去重，否则会错误丢弃同一任务的合法后续修改。


### 05.3  完成报告最少字段

执行版本、实际完成范围、成果版本/校验值、验证证据、尚未解决问题、外部副作用清单和交接建议。纯自然语言“完成了”不足以推进验收状态。所有字段由宿主校验，不直接采信模型自行声明的身份或权限。

## 06  任务与团队的双状态机

*建议设计*


### 06.1  任务状态与合法推进

| 阶段 | 建议状态 | 退出条件 |
| --- | --- | --- |
| 接收与准备 | RECEIVED → CLARIFYING → QUEUED | 持久化成功，任务目标与验收条件可执行。 |
| 执行 | RUNNING | 有效执行者按已应用版本工作。 |
| 中途调整 | ADJUSTING / WAITING_INPUT | 新要求明确、旧动作已处理，新版本得到应用确认。 |
| 提交与验收 | SUBMITTED → VERIFYING | 固定成果版本，审查证据；不通过返回执行或调整。 |
| 验收与交接 | ACCEPTED → HANDOFF_PENDING | 验收记录绑定当前需求与成果；等待接收方确认。 |
| 完成 | COMPLETED | 正式成果已持久化、交接已确认；不能仅因派单成功进入。 |
| 非正常结束 | FAILED / CANCELLED / SUPERSEDED | 记录原因、已发生操作和后续处理，走独立收尾策略。 |


### 06.2  团队资源状态单独记录


```text
资源状态：NEW → STARTING → ACTIVE → DRAINING → STOPPED
退出后：  STOPPED → CLEANING → CLOSED
清理失败：CLEANING → CLEANUP_FAILED；重试时回到 CLEANING
```

正常结束时，只有关联任务完成验收和交接，团队才能进入 DRAINING。清理失败不抹掉已完成的业务交付：界面应分别显示“业务已完成”和“团队待清理”。验收等待期间不持续调用模型。


### 06.3  必须保留的状态区别

已接收≠已执行；已发送变更≠变更已应用；孙 Agent 提交≠验收通过；验收通过≠交接成功；交接成功≠临时资源已清理。状态更新应带预期版本，过期写入拒绝并重新判断。

父任务的完成条件由工作流定义，检查必需的子任务、审查与交接记录；不以“所有进程都退出”推断业务成功。失败或取消团队的退出可按独立授权政策处理，不能伪造正常验收记录。

## 07  运行中变更与防止旧指令生效

*建议设计*


### 07.1  三类新指令必须明确区分

| 类型 | 处理方式 |
| --- | --- |
| AMEND：修改原任务 | 保留任务编号，提升需求版本；记录停止项、保留项、新增项和新验收条件。 |
| REPLACE：替换原任务 | 旧任务标记被取代，建立新任务及替代关系；核对旧操作，禁止混用成果。 |
| NEW：新增任务 | 新建独立任务；不默认取消旧任务，由主 Agent 决定资源和优先级。 |


### 07.2  建议的变更处理顺序

① 主 Agent 接收并记录新要求；② 运行时提升目标版本，阻止旧版本启动新的有影响操作；③ 子 Agent 结合当前进展形成调整方案；④ 处理正在运行的旧操作；⑤ 向孙 Agent 下发明确的新执行要求；⑥ 孙 Agent 确认已应用，更新 applied_revision 并逐级反馈。

界面同时展示 task_revision 与 applied_revision。例如“目标版本 4，执行版本 3，切换中”，不将收到消息误报为完成调整。


### 07.3  并发防线

模型推理或工具等待结束后，提交决策前再次检查 state_version、task_revision 与 lease_epoch；若已过期，结果保存为历史证据，但不得覆盖最新任务。执行器在每次工具启动前，以及成果登记前，均检查版本与授权。

对任务状态写入采用短事务或等价的条件更新；同一任务控制事件有序处理，不把模型调用放在持锁事务内。异步等待期间状态可能变化，这也是工作流消息处理中需要专门处理的并发情况。[S17]


### 07.4  不能取消的操作如何处理

取消采用请求、处理中、成功或不可取消的明确反馈；对于已经发生的外部操作，记录实际结果并按业务规则补偿或人工确认。A2A 的取消接口不保证目标任务一定可取消。[S03]

> 版本检查能阻止后续过期执行，不能让已经启动的外部操作自动消失。不得向用户声称“已撤销”，除非有实际核对结果。

## 08  多主 Agent 协作与并行模块管理

*建议设计*


### 08.1  一个请求只有一个明确的对外负责人

建议 request.owner_root_agent_id 指定完整请求的对外负责人。其他功能主 Agent 通过关联任务参与，并将结果交回负责人。纯审查请求可由 Review 主 Agent 对外负责；开发请求可由开发主 Agent 汇总开发与审查结果。该规则适用于任意功能组合。


### 08.2  依赖和共享修改由主 Agent 协调

同一功能主 Agent 可同时管理多个项目、模块和外部请求，但每个任务有独立上下文、预算和工作空间。跨团队依赖形成有向图，检查循环依赖；依赖成果变化时重新计算受影响任务，不无差别停止其他项目。

代码任务建议使用独立分支与工作树，主分支通过受控集成任务更新。Git worktree 支持多个关联工作树，但会共享部分仓库资源，因此不替代权限隔离或并发集成管理。[S16]


### 08.3  开发与 Review 仅作为通用机制的例子


```text
外部开发请求 → 开发主 Agent → 并行模块团队
模块成果提交 → Review 主 Agent → 审查团队
需要修复 → 开发主 Agent → 对应开发团队
审查与集成验证通过 → 当前版本验收 → 交接 → 反馈
```

Review 团队只把问题交给 Review 主 Agent，由它向开发主 Agent 发出关联修复要求，不直接指挥开发孙 Agent。审查记录绑定需求版本、成果提交、基线和验证证据；旧版本的“通过”不能直接放行新版本。


### 08.4  争议和循环的退出条件

设置返工次数、费用或时间上限；重复分歧升级给指定裁决者，而不是互相无限派单。模块各自通过后仍需检查集成成果；需运行验证命令时交给授权团队，主 Agent 只审阅证据和作出验收判断。

一份结论为“不通过”的审查报告，也可能是已验收的审查任务成果；其交接完成后审查团队可以关闭。之后复审创建新团队读取已保存的问题与代码版本，不依赖原进程。

## 09  模型、思考等级与配置继承

*已确认规则 + 建议机制*


### 09.1  按字段直接继承所属主 Agent

模型 model_ref 和思考设置 reasoning 分别解析。子、孙 Agent 的字段未设置时，直接使用所属主 Agent 已解析的对应字段；孙 Agent 不继承子 Agent 的覆盖值。主 Agent 自己未设置时，建议补齐系统默认值；仍缺少有效模型则拒绝启动。

| 角色 | 声明模型 | 声明思考 | 最终配置 |
| --- | --- | --- | --- |
| 主 Agent | 模型 A | 高 | 模型 A / 高 |
| 子 Agent | 模型 B | 未设置 | 模型 B / 高 |
| 孙 Agent | 未设置 | 中 | 模型 A / 中 |
| 另一团队孙 Agent | 未设置 | 未设置 | 模型 A / 高 |

上表假设模型支持所选档位，只说明继承语义。不同供应商的同名思考等级不代表相同能力、费用或延迟；适配器需校验模型实际支持的参数。[S04][S06]


### 09.2  未设置、供应商默认和关闭思考必须不同

建议 null 或字段缺失表示继承；provider_default 表示显式采用端点默认；off 表示请求关闭思考；effort 或 token_budget 表示指定等级或预算。reasoning 作为一份完整设置校验，避免把不同模型的等级与预算错误混合。


### 09.3  配置变更与快照

建议团队启动时生成 EffectiveModelConfig，保存模型别名、端点、模型版本、思考映射结果、来源和配置摘要。主 Agent 默认值变更仅影响新建团队；修改活动团队须经显式控制事件，在安全边界切换。权限撤销和紧急停止不受此快照延迟。

默认不静默降级：继承到不支持的等级、模型不可用或预算不足时，明确报错或暂停。备用模型和自动升级仅在有显式策略时启用，记录原因和缓存影响。跨端点切换通过已确认任务状态和成果摘要重建，不假设私有会话格式通用。

## 10  主流端点兼容与能力登记

*目标边界 + 建议设计*


### 10.1  端点不只是一个 URL

以“供应商 / API 家族 / 模型版本 / 区域或部署 / 鉴权范围”标识能力单元。统一内部消息、流式输出、工具调用、用量与错误结构；保留 provider_options 和必要的不透明续接字段，但不得绕过权限或参数校验。

| 候选覆盖范围 | 实现入口 | 发布时必须验证 |
| --- | --- | --- |
| OpenAI 原生及兼容服务 | Responses / Chat Completions 分别适配 | 模型能力、工具与流格式、思考参数、缓存用量。 |
| Anthropic Claude | Messages 等实际开放接口 | 内容块、工具结果、思考模式、缓存断点与签名续接。 |
| Google Gemini | 按模型选择受支持 API 家族 | 会话模式、工具调用和显式/隐式缓存支持。 |

| 其他主流服务与聚合网关 | 千问、DeepSeek、Kimi、GLM、MiniMax、xAI、Mistral 等列入登记候选 | 不能因为支持某种兼容格式，就标记全部高级特性可用。 |
| 本地推理服务 | vLLM、Ollama 等按实际接口适配 | 工具能力、资源限制、模型模板和推理服务缓存。 |

上表是兼容登记与研发覆盖候选，不是已完成清单；具体供应商顺序待定。主流范围持续变化，每版按实际需求、可用账号和测试结果更新。云托管缓存行为需独立核对，不能照抄原厂能力。[S08][S09]


### 10.2  能力表与状态

登记 streaming、tool_calling、structured_output、reasoning_modes、context_limit、cancellation、cache_mode、usage_fields、auth_scope、capability_source 和 verified_at。每项标记 supported、unsupported、unknown 或 experimental；另外记录实现状态与测试状态，不能把“文档支持”当成“本系统已验证”。

连接检查、流式工具往返、错误与限流处理、取消边界、模型设置校验和缓存统计均需单独验证。未支持的必要能力使任务准入失败；可选能力按显式降级政策处理。

## 11  MCP、Skills、插件与 Agent 互通

*建议设计*


### 11.1  MCP：工具与上下文接入

实现 MCP Client 接入已有服务；实现受控的 MCP Server 对外暴露适合的任务提交、查询和结果能力。协议版本、传输、认证、进度/取消及可选扩展分别登记，不将全部扩展捆绑为“支持 MCP”。MCP 定义了工具、资源等接口，也明确将扩展支持与安全控制作为独立问题。[S01]


### 11.2  Skills：指令包与执行依赖

标准 Skill 通过元数据发现、按需激活，再读取脚本和参考资料。SKILL.md 使用 YAML 元数据和 Markdown 正文，脚本语言可用性由宿主实现决定。[S02] 建议增加依赖检查、内容版本、来源审查和权限映射，区分“格式有效”“依赖就绪”“可运行”。


### 11.3  插件：按生态解包与适配

插件安装器解析包清单，将工具、Skills、工作流等映射到内部能力；特定平台的 hooks、agents 和 UI 组件单独适配。Claude Code 的插件清单包含多类组件，导入其中的 Skill 并不等于完整支持整个插件。[S19] 不允许插件自行声明权限后自动获得权限。


### 11.4  A2A：双向任务协作

建议 A2A Client 与 Server 作为 Agent 互通适配层，映射发现信息、任务、消息、成果和可用的异步更新机制。A2A 定义了 Agent Card、任务查询及流/推送等操作；应按对方能力选择具体交互方式。[S03] 内部三级调度不必套一层网络协议，使用内部事件即可。

| 互通边界 | 建议规则 |
| --- | --- |
| 外部调用进入 | 先认证、分配 request_id 与对外负责人，再执行任务准入和预算控制。 |
| 调用其他 Agent | 仅传所需上下文、成果引用和范围明确的授权，不转交全部历史或所有凭据。 |
| 异步通知 | 回调需认证、重试和去重；断线可查询状态，不能只依赖即时消息。 |
| 工具执行权限 | 执行类能力只给孙 Agent；主、子保留结构化管理接口。服务器端内置执行工具也受同一边界约束。 |

## 12  高缓存架构：目标与上下文编排

*建议设计*


### 12.1  先分清三种缓存

| 类别 | 内容 | 关键边界 |
| --- | --- | --- |
| 模型输入缓存 | 模型服务已处理的前缀或显式缓存对象 | 不是答案复用，也不是保存到本地就自动命中。 |
| 本地上下文存储 | 任务消息、模板、资料快照、成果引用 | 用于恢复和重建请求；与服务端缓存生命周期不同。 |
| 工具结果缓存 | 可复用的读取、解析和查询结果 | 按数据版本、授权和有效期核对；写操作不可泛化缓存。 |

前缀缓存主要减少重复输入处理；例如 vLLM 的自动前缀缓存并不直接加速新 Token 的解码阶段。[S12] 缓存设计的最终目标是合格交付的总成本和耗时，而非单独追求百分比。


### 12.2  所有角色共用上下文编排器


```text
稳定工具定义与系统规则
  → 当前角色模板与固定输出约定
  → 授权范围内的项目资料快照
  → 本任务初始要求
  → 已有消息与执行记录
  → 本轮新要求、工具结果与必要实时信息
```

这是逻辑排序；端点适配器负责按原生结构编码，不得把低信任资料提升为系统指令。原始用户消息、代码和工具证据保持语义与顺序；仅规范化宿主生成的 JSON、工具排列、模板和资料清单。

动态时间、随机团队编号、实际临时目录、剩余预算和全局运行状态不放在共享前缀开头。模型需要的动态信息放在任务后部；不需要的身份信息由运行时保存。工作目录可使用稳定逻辑路径，由执行器映射实际隔离目录。

> 共享的是稳定模板和被授权资料，不是把不同请求的私有历史合并。不同层级的职责和工具不同，不强行统一提示词来换命中率。

## 13  高缓存架构：会话、变更与工具

*建议设计*


### 13.1  两个主要复用维度

跨团队：相同角色、模型配置和公共资料形成稳定前缀，不同任务从后部开始分叉。同团队：多轮请求尽量追加新消息，复用已处理历史。只有前面的前缀也匹配，后面的相同段落才有机会复用；本地块哈希去重不等于模型能任意拼接 KV 缓存。[S04][S13]


### 13.2  任务变化优先采用追加式表达

对原任务小幅调整，追加带版本的变更内容，明确停止、保留、作废和新验收条件，宿主同步最新有效状态。不每轮改写早期任务描述。完全无关的新任务建立新会话，继续复用角色和项目公共部分，避免携带失效要求。

只在阶段边界、上下文预算触发或恢复需要时生成固定摘要；不要每轮重写历史摘要放回前部。出现权限撤销、敏感内容删除或严重语义冲突时，以安全和正确性为先重建，不因缓存保留不应继续使用的内容。


### 13.3  工具与 Skill 保持小而稳定

角色基础工具集固定版本，任务新增能力按需引入。支持原生延迟加载的端点可利用其机制；例如 Claude 的延迟工具定义在发现后进入消息历史，避免修改早期系统前缀。其缓存顺序为 tools → system → messages，修改工具定义会影响后续前缀。[S06]

不支持延迟加载的端点，团队阶段内锁定工具清单；确需改变时记录配置变化并接受必要重建。Skill 索引与正文分开，正文激活时加入合适的任务位置；不得为缓存把所有 Skill 和插件全文塞入每次请求。


### 13.4  模型设置变化不能一概而论

模型版本、思考设置、输出约束、工具选择和多模态设置等是否影响缓存，由能力表决定；不支持同会话更新时创建新的上下文阶段。供应商要求的续接标识和不透明字段原样保存并受权限控制，不作为可自由改写的通用文本。[S04][S06]

## 14  高缓存架构：管理、隔离与调度

*建议设计*


### 14.1  缓存生命周期独立于团队进程

核心服务集中管理模板、资料快照、前缀指纹、端点缓存引用与用量。销毁团队不删除仍被其他任务使用的公共内容；销毁本地目录也不代表已删除供应商侧缓存或日志。供应商删除与保留策略独立处理。


```text
内部复用分组 = 隔离域 + 端点/部署/鉴权范围
             + 模型版本 + 影响缓存的有效设置
             + 原生编码后的前缀结构与内容指纹

会话标识用于任务隔离；不默认把随机 team_id
加入公共前缀分组，也不假设这个分组键就是供应商缓存键。
```

缓存键不含明文凭据；按供应商的组织、工作区、部署等实际边界映射。不能把客户端 cache_key 当访问控制。自托管推理的隔离也要独立配置；vLLM 提供请求盐值机制来分隔前缀复用范围。[S13]


### 14.2  避免同时重复冷启动

对同一可共享前缀采用一次准备、其他请求短暂复用准备结果的机制。支持原生预热时按能力使用；其他情况等待真实请求满足该端点的缓存就绪条件，不推测“已发出请求”就已可复用。等待有上限，不得牺牲关键任务截止时间。

调度优先选择已获授权且配置匹配的稳定端点；端点不可用时按显式故障策略处理。缓存亲和性是软偏好，不能改变用户指定模型、绕过地区限制，或让一个大项目长期占满资源。


### 14.3  缓存时长与磁盘预算

依据真实重用间隔、预计复用次数、写入/存储费用和安全策略选择缓存时长。禁止用无意义模型调用长期保活。公共资料及缓存引用采用访问范围、引用计数和容量策略管理；删除不得破坏活动任务。隐式缓存的到期或驱逐可能不可观测，状态需允许 UNKNOWN。

> 本地只能管理上下文与缓存元数据；服务端真实命中以返回的使用量或服务端观测为准。不能把本地找到了相同指纹当作已经获得计费折扣。

## 15  高缓存架构：端点能力与降级

*建议设计 + 官方能力依据*


### 15.1  端点缓存能力表的最低字段


```text
mode: none | implicit_prefix | explicit_prefix | explicit_object
minimum_tokens / checkpoint_limits / supported_content
retention_options / readiness_condition / isolation_scope
cache_key_semantics / settings_invalidation_rules
usage_mapping / write_read_storage_pricing / deletion_support
source_url / verified_at / implementation_status / test_status
```

这些字段是本系统登记模型，不是供应商统一 API。能力不明确时标为 unknown；不发送猜测的私有参数。原生对象缓存与前缀缓存通过不同操作适配，不能假设每个平台都有创建、查询、删除缓存对象的接口。

| 端点族 | 已经核对的差异 | 本系统处理 |
| --- | --- | --- |
| OpenAI | 控制字段和缓存计费行为依模型代际而变。[S04] | 使用模型级能力表，不沿用跨代参数。 |
| Claude | 支持自动与显式缓存控制；用量区分缓存读取、创建和未缓存输入。[S05] | 映射断点、时长与完整用量，控制工具定义变更。 |
| Gemini | 缓存支持同时受 API 家族和模型约束，当前 Interactions 仅支持隐式缓存。[S07] | 不能把 generateContent 的显式能力套到全部接口。 |
| Azure / Bedrock | 托管模型、部署方式与接口能力需要独立判断；Bedrock 不保证每次命中。[S08][S09] | 分别维护能力和认证，不复用原厂结论冒充实测。 |
| DeepSeek / 千问 | 两者提供各自上下文缓存机制与用量规则。[S10][S11] | 通过专用映射保留原始用量和参数语义。 |
| 本地推理 | 缓存启用、隔离和资源管理发生在推理服务层。[S12][S13] | 登记服务配置与观测信息，而非仅检查客户端文本。 |

以上是 2026-10-16 查阅官方资料后的设计依据，不是本系统兼容测试结果。本文不固化各模型 TTL、最小长度或价格；实施时按所选模型重新核对并保存能力快照。

## 16  高缓存架构：指标与验收方法

*建议设计*


### 16.1  主要指标与口径


```text
输入 Token 缓存命中率 = Σ实际缓存读取 Token / Σ输入 Token
总体覆盖率 = 有可靠用量记录的请求数 / 所有请求数

同时报告：冷/热请求、写入量、未缓存量、首 Token 延迟、
端到端耗时、缓存与模型总费用、任务质量和返工次数。
```

按供应商、模型、角色、模板版本、项目和会话阶段分组；聚合时累加 Token，不对请求命中百分比做简单平均。用量缺失标为未知，不记作零；零输入或无可靠分母时不计算该比率。

缓存写入不是命中。适配器保存原始 usage，再转换为不重叠的统计口径；不能把供应商字段直接相加。Claude 的输入总量为读取缓存、创建缓存和其 input_tokens 三项之和，其他端点按自身定义处理。[S05]


### 16.2  一个明确标注的计算示例

假设每次输入含 12,000 个可复用公共 Token 和 3,000 个独有 Token，只有公共部分可缓存。热请求的理想命中率为 80%。20 次请求中首次完全冷、其余均命中公共前缀时：


```text
整体命中率 = 19 × 12000 ÷ (20 × 15000) = 76%
```

这只是计算示例，不是实测指标。


### 16.3  对照与异常诊断

| 验证场景 | 应观察什么 |
| --- | --- |
| 相同内容重复编排 | 宿主生成的前缀字节/结构指纹一致；无随机标识污染。 |
| 多团队共享 / 多轮追加 | 热请求读取量、就绪等待和总费用；与冷启动分开分析。 |
| 任务改向 / 工具更新 / 模型切换 | 失效范围可解释；新要求有效，不为缓存保留错误状态。 |
| 长时间等待 / 并发首轮 / 端点切换 | 过期、重复写入和未知原因有记录；不假造命中结论。 |
| 跨权限域隔离 | 不共享不允许共享的内容；缓存命中不能改变访问授权。 |

先建立代表性负载的质量、成本与延迟基线，再确定角色级缓存目标。禁止为达到 95% 等数字填充无用上下文。成本统计包含写入、读取、存储与输出；存在重复计费字段时由适配器去重。

## 17  Linux 执行隔离与安全

*建议设计*


### 17.1  权限由运行时强制执行

主、子 Agent 的工具注册表仅含管理接口；孙 Agent 获得任务范围内的最小执行能力。所有执行入口都检查身份、任务版本、有效执行者代次、工具授权、路径与网络范围。外部 Agent、MCP、Skill 和插件均不能自行提升权限。

不将工具自报的只读或安全标记当成唯一授权依据。MCP 官方明确要求对非可信来源的工具行为注解保持不信任。[S01] 外部文档、工具返回和 Skill 内容按来源分级，不升级为宿主管理指令。


### 17.2  进程隔离与资源限制是两件事

建议每个活动团队有受控的子 Agent、孙 Agent 进程，以及归属明确的工具进程。Linux 进程监管可结合 cgroup v2 做分组、资源控制和退出核对；该机制提供整组管理能力，但不替代文件系统、网络、系统调用与用户权限隔离。[S15]

具体部署可选非特权用户、受控容器或 namespace、seccomp、只读挂载、网络白名单与资源配额，按发行版和运行权限验证。禁止默认 root 运行第三方脚本，也不默认挂载整个宿主文件系统。


### 17.3  凭据与副作用

凭据只以 secret_ref 引用；模型和日志不得读取全部密钥。按工具调用临时提供必要凭据，限制继承环境变量。发邮件、发布、外部写入等操作按风险配置批准要求；批准绑定确切操作和版本，不允许旧批准授权新的变更。


### 17.4  文件与插件供应链

工作空间和成果路径按授权根目录限制，防路径穿越、符号链接绕过及校验后替换。插件与 Skill 记录来源、版本、依赖、摘要和安装审查状态；“能安装”不等于“允许执行”。已撤销权限在工具启动前再次检查。

> 缓存和日志都可能包含私有信息。对本地数据、供应商留存、诊断采样和导出建立独立策略；提升缓存率不得扩大数据共享范围。

## 18  验收、交接、退出与磁盘回收

*已确认条件 + 建议执行机制*


### 18.1  正常关闭必须经过两个业务关口

关口一是验收：主 Agent 根据当前需求、固定成果和证据作出接受或返工决定。关口二是交接：正式成果已保存至团队临时目录之外，接收方或指定系统确认可用。两者满足后，运行时才能关闭团队。

| 步骤 | 必要检查 |
| --- | --- |
| 固定提交 | 锁定任务版本、成果摘要与验证证据；提交后不原地修改待验收版本。 |
| 验收记录 | 结论绑定当前要求、成果和基线；发生相关修改时重新评估有效性。 |
| 持久化成果 | 写入正式位置并核对清单、大小/摘要、权限和可读性；原子发布与数据库引用协调。 |
| 确认交接 | 记录接收方、成果引用、依赖说明、未决风险与确认时间。临时路径不能作为唯一交付。 |
| 退出进程 | 停止新接单和新工具；请求正常退出；超时按政策终止，核对残留工具进程。 |
| 清理空间 | 仅删除归属该团队的临时目录和中间产物；保护正式成果、用户原件与共享依赖。 |
| 关闭登记 | 记录释放资源、清理结果和错误；失败进入待清理队列，保留重试审计。 |


### 18.2  清理不能由模型拼接任意删除命令

主 Agent 提交结构化关闭请求，生命周期模块核对条件后执行白名单目录清理。以受信任目录句柄和团队资源清单为边界，防止路径替换和跨目录删除；开发工作树通过受控仓库管理逻辑移除，不把任意 rm 命令交给模型。


### 18.3  保存什么、清理什么

清理团队缓存、下载副本、构建中间物和临时日志；保存正式成果、关键变更、配置快照、验收与交接记录。共享缓存按独立容量策略管理。日志轮转、失败保留期限、数据库归档和成果保留期均需明确，避免只删团队目录却仍持续涨盘。

交接失败禁止删除唯一成果。失败、取消、被替代任务由独立终止交接政策收尾，不伪装成成功验收。交付的是长期服务时先移交到正式运行环境；团队关闭后新请求建立关联任务，不给已退出进程继续派单。

## 19  持久化、恢复、预算与防卡死

*建议设计*


### 19.1  单机优先，状态是唯一事实来源

建议 Linux 首版使用一个核心服务管理任务数据库、事件收件箱/发件箱和成果引用，模型上下文不作为唯一状态存储。可采用 SQLite WAL，但它仍只有一个同时写入者；事务保持短小，不在数据库事务中等待模型或工具。[S14] 多机部署时再评估独立数据库与队列。

| 持久化对象 | 建议约束 |
| --- | --- |
| 任务与事件 | 同一事务提交状态变更及待发送消息；接收确认在可靠保存之后返回。 |
| 消息收发 | 可重试派发，收件箱按唯一事件/指令去重；无全局“恰好一次”承诺。 |
| 成果与数据库 | 先可靠保存成果，再发布可见引用；扫描孤立文件，不在活动写入期间清理。 |
| 执行代次 | 恢复先核对旧进程、旧租约与外部操作，再发新 lease_epoch；旧代次不能提交成果。 |
| 日志与回放 | 保留关键决策输入、事件与版本；恢复不重新调用模型重做已经提交的历史决策。 |


### 19.2  副作用重试必须可核对

区分安全重复、具备业务幂等键、结果未知待核对、不能自动重试四类操作。进程崩溃可能发生在外部动作已完成但反馈未保存之后；此时不能盲目重发。工作流活动的重试也需要幂等设计或等价业务保障。[S18]


### 19.3  并发配额与预算

配置系统、功能主 Agent、项目和端点的并发上限与公平队列；为关键协作角色保留容量，避免开发占满资源而审查无法启动。预算含已使用和已预留的在途消耗；不足时暂停或升级决策，不默认换弱模型。


### 19.4  健康状态不等于任务进展

分别记录进程心跳和最后一次有效进展；检测重复调用、相同错误、长时间无成果变化、无限等待与循环委派。阈值触发时生成待决策事件。取消、超时、最大返工次数和最大委派深度须有可配置上限，不能靠模型自行记住。

## 20  对外接口与管理命令草案

*建议设计 / 非已实现 API*


### 20.1  统一任务入口

| 操作 | 建议接口 | 关键语义 |
| --- | --- | --- |
| 提交请求 | POST /v1/requests | 指定功能主 Agent；支持客户端幂等键；保存成功后返回 request_id。 |
| 任务查询 | GET /v1/tasks/{id} | 返回目标/执行版本、状态、团队、成果与等待原因。 |
| 修改任务 | POST /v1/tasks/{id}/changes | 带 AMEND/REPLACE/NEW、expected_version 和修改内容。 |
| 取消任务 | POST /v1/tasks/{id}/cancel | 返回取消请求状态；不假定立即撤销外部操作。 |
| 订阅进展 | GET /v1/requests/{id}/events | 按授权输出事件；支持游标续传，超出保留期转状态快照。 |
| 验收与交接 | POST /v1/tasks/{id}/acceptance<br>POST /v1/tasks/{id}/handoff | 绑定需求与成果版本；验收、交接分别确认。 |
| 团队与配置 | GET /v1/teams/{id}<br>GET /v1/agents/{id}/config | 查询资源、清理状态及配置来源；敏感信息脱敏。 |

所有接口使用统一认证、访问范围、错误码和审计。MCP 与 A2A 作为此任务内核的协议适配入口；不能另外建立绕过版本和权限规则的快捷执行通道。


### 20.2  CLI 最小操作集


```text

wls requests submit --agent <id> --file <task>

wls teams show <team_id>

```

CLI 名称 wls 仅为示例。配置检查、权限验证和兼容性报告应支持不执行业务工具的检查模式。具体 HTTP 字段、错误码、认证和用户界面尚待接口设计阶段细化。

## 22  C++ 模块划分与内部接口

*建议设计*


### 22.1  建议代码边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| core / task_engine | 实体、状态机、版本检查、父子依赖 | 供应商 HTTP 细节与模型自由写数据库 |
| orchestration | 角色注册、团队调度、变更和交接 | 执行业务 Shell 命令 |
| model_adapters | 原生协议、流、工具事件、用量、能力校验 | 擅自改变模型、权限或任务目标 |
| context / cache | 上下文编排、配置指纹、缓存计划与诊断 | 将本地命中冒充服务端命中 |
| extensions / interop | MCP、Skills、插件、A2A 适配 | 绕过任务准入及授权 |
| execution / platform | 孙 Agent 执行器、进程隔离、工作空间 | 替主 Agent 作出业务验收结论 |
| storage / observability | 事务、收发件箱、成果引用、指标与审计 | 无界保留日志或泄露凭据 |


### 22.2  核心内部契约


```text
ModelAdapter:
  capabilities(model_ref) -> CapabilityProfile
  validate(effective_config) -> ValidationResult
  stream(model_request) -> ModelEvent stream
  normalize_usage(raw_usage) -> UsageRecord

ContextCompiler:
  compile(role, snapshot, task_events) -> ContextBundle

CachePlanner:
  plan(context_bundle, capability) -> ProviderCachePlan

TaskEngine / LifecycleManager:
  apply(command, expected_version) -> TransitionResult
  close_team(team_id, closure_authorization) -> ClosureResult
```

建议 C++20、CMake 与可锁定版本的依赖管理；JSON、YAML、HTTP/TLS、异步执行、日志和 SQLite 分别选择成熟组件，最终库清单待评审。协议实现可原生实现或封装辅助服务，保持接口可替换；C++ 核心不意味着所有第三方脚本必须改写成 C++。

Linux 相关代码集中在平台层，后续 Windows 更换进程、路径、凭据与隔离实现。业务状态机、配置解析、模型适配和缓存计划尽量复用，不以“同一可执行文件”作为跨平台目标。

## 23  建议实施阶段与完成标准

*建议规划 / 非已承诺排期*

以下按依赖顺序推进，不给尚无实现依据的工期估算。各阶段完成标准应形成实际验证报告；阶段一可交付 Linux 可用闭环，但不代表已经覆盖全部端点和插件生态。

| 阶段 | 主要产出 | 退出条件 |
| --- | --- | --- |
| M0 规格与契约 | 需求基线、状态机、模型继承、能力表、交接契约、权限边界 | R01—R18 可追踪；待定事项有负责人或安全默认值。 |
| M1 Linux 核心闭环 | 核心服务、数据库、配置、两种任意功能模板、多团队、真实模型适配 | 请求到执行、变更、验收、交接和清理完整贯通；有隔离与恢复测试。 |
| M2 扩展与互通 | MCP Client/Server、标准 Skill 加载、A2A 双向入口、插件适配框架 | 真实生态任务往返，版本/权限/取消边界和兼容状态清楚。 |
| M3 端点覆盖与缓存 | 按优先级增加原生/兼容/托管端点，缓存控制、用量与诊断 | 每个声明支持的能力有证据；代表性缓存与成本基线可复现。 |
| M4 可靠性与运营 | 故障注入、预算与公平队列、日志保留、监控、管理界面 | 异常场景通过，磁盘与进程可回收，质量/费用/延迟可观察。 |
| M5 Windows 与扩展部署 | Windows 平台适配；按实际需求评估多机 | 不改变业务语义，平台与端点矩阵分别验收。 |


### 23.1  从第一阶段就存在的能力

版本检查、权限强制、持久化、团队关闭关口、配置来源和稳定上下文编排不能拖到后期补丁式加入。后续阶段扩展的是覆盖范围和成熟度，而非第一次引入这些基本防线。


### 23.2  当前最主要的风险

供应商能力变更以版本化能力表和回归验证控制；外部操作结果未知以幂等或人工核对控制；模型误判以证据和复核控制；跨模块冲突以依赖与集成流程控制；日志与成果增长以配额、保留期和可观测清理控制。

### 26.1  后续文档维护

需求更新保留 R 编号并记录来源，新增条款分配新编号。架构建议批准后在决策记录中标记状态、批准人和日期；被替代方案保留原因。接口、配置和数据库均有 schema_version，变更附迁移与兼容说明。

### 26.2  本版基线总结

以可配置功能主 Agent 为入口，以临时一对子孙团队为执行单元，以确定性控制内核保证任务有序，以版本和证据完成调整、验收与交接，以独立缓存设施提高复用，以生命周期模块安全回收。本文已形成可用于开发拆解的设计基线，但所有模块仍待实施与验证。
