# 无量山｜通用多 Agent 系统

## v0.2 架构修订与工作流增补

**固定对外入口 · 每请求独立调度 · 多团队并行执行**

C++ 核心 / Linux 优先 / 后续保留 Windows 支持

| 文档信息 | 内容 |
| --- | --- |
| 文档编号 | WLS-MAS-SPEC-002 |
| 版本与日期 | v0.2 · 2026-10-16（Asia/Taipei） |
| 本版性质 | v0.1 的架构修订与工作流增补，不是完整重排版 |
| 实现状态 | 需求与设计阶段；配置、接口及用例均未实现或实测 |
| 阅读规则 | 与 v0.1 合并阅读；角色职责、互调、工作流、交付和清理发生冲突时以本版为准 |
| 依据 | 本轮用户明确提出的架构变更，以及已同意的互调与工作流方向 |

**本版核心决策**

每个功能 Agent 仍只有一个稳定的对外身份，但每个独立请求创建自己的调度 Agent。调度 Agent 负责规划、分派、协调和验收，可管理多个“团队负责人＋执行者”组合。固定入口不再承担串行的业务规划。

**两项必须显式选择的边界**

“无过滤直达”建议实现为不经模型筛选或拆解，但保留运行时身份、去重与资源准入；“删除所有记录”支持请求私有运行数据清理和更严格的交付后本地清除模式，中央回执是否保留须显式配置，不能视为已批准。

## 01  修订范围与需求追踪

**用户明确的新方向。** 不为每项工作新建对外主代理，而是为每个独立请求创建临时调度 Agent；原主代理的内部项目管理职责下移。该结构适用于所有功能 Agent，开发和 Review 仍只是例子。

| 变更编号 | v0.1 的表述 | 本版修订 |
| --- | --- | --- |
| C01 | 主 → 子 → 孙三层 | 主入口 → 请求调度 → 团队负责人 → 执行者，四个逻辑角色 |
| C02 | 主代理做分配、协调、验收 | 主代理只对外；上述业务职责由请求调度器承担 |
| C03 | 功能主代理管理所有请求的团队 | 每请求调度器只管理自己请求的任务图和团队 |
| C04 | 主代理之间主动规划互调 | 请求调度器发起委派，通过对方功能主入口接入 |
| C05 | 主代理验收团队成果 | 请求调度器验收；已配置的必需独立 Review 不得绕过 |
| C06 | 团队完成后回收 | 团队和请求调度器都须结束；正常最终清理以交付确认等条件为关口 |
| C07 | 主、子、孙独立模型设置 | 建议扩展到新增调度角色；未设置字段继续直接继承所属功能主代理 |
| C08 | 留存必要任务历史 | 最新要求强调删除记录；本版区分临时数据、交付物、回执与严格清除策略 |

v0.1 中 R04、R05、R09、R11、角色表、互调路径和关闭授权须按本版重解；其他目标继续有效：C++ 核心、Linux 优先、受控执行、模型端点兼容、MCP、Skills、插件、异步调整和高缓存复用。

**批准与建议分开。** 用户已同意统一任务内核及工作流方向，并明确提出请求级调度。具体限额、技术准入、回执保留期限、早回收策略、模型映射和独立审核政策仍是本版建议，不代表已经完成配置或获得生产授权。

## 02  四个逻辑角色与唯一职责

| 角色 | 生命周期 | 负责 | 不负责 |
| --- | --- | --- | --- |
| 主入口 Root | 长期逻辑身份 | 接收与路由、外部消息、交付及回执 | 模型级任务拆解、内部业务验收、执行命令 |
| 请求调度 Dispatcher | 每独立请求一个 | 明确目标、规划任务图、创建团队、调整、协调、验收、汇总交付 | 执行业务命令、越权审批、直接向外发布成果 |
| 团队负责人 TeamLead | 每团队一个 | 细化本团队任务、解释变化、指导执行、报告证据 | 直接执行业务命令、擅自改请求目标 |
| 执行者 Worker | 每团队一个有效身份 | 授权工具、文件、命令、MCP、Skill、插件执行 | 自行再生 Agent、绕过负责人接单 |

```text
功能主入口 A（稳定对外身份）
  请求 R1 → 调度 D1
    团队 T11：负责人 L11 → 执行者 W11
    团队 T12：负责人 L12 → 执行者 W12
  请求 R2 → 调度 D2
    团队 T21：负责人 L21 → 执行者 W21

功能主入口 B：同样采用本结构
公共 C++ 内核：状态、授权、调度、事件、交付和清理
```

原来的“工作子代理＋孙代理”团队配对不变。新增的是其上方的请求调度角色。为避免把两种子代理混淆，内部契约统一使用 Dispatcher、TeamLead、Worker；界面可保留用户熟悉的中文称呼。

**逻辑层不等于操作系统的父子进程树。** 进程由运行时监管，不能依赖某个模型代理活着才有人管理其子进程。C++ 内核和工作流引擎都不是第五层 Agent。

## 03  主入口的快速路径与请求身份

**设计目标：接单不等待模型推理。** 调用方已经指定功能 Agent 时，Root 不再先分析、打分或拆任务，而是完成确定性接入后创建请求及调度实例。接单确认用 RECEIVED，不使用表示业务验收通过的 ACCEPTED。

```text
认证与格式检查 → 幂等检查 → 保存请求和待启动事件
→ 返回 request_id 与 RECEIVED/QUEUED
→ 有额度时启动该请求的 Dispatcher
```

以上是建议的技术准入，不是由主代理做业务过滤。身份无效、报文超限、权限不足或系统过载时，仍必须有明确错误或排队反馈；直接无上限创建进程不应作为“立即分派”的实现。

| 到达的消息 | 路由规则 |
| --- | --- |
| 独立新任务 NEW | 新建 request_id 与唯一逻辑 Dispatcher |
| 同请求修改 AMEND | 用 request_id 找回原调度器，提升需求版本 |
| 替换 REPLACE | 旧请求标记被替代，按策略创建关联的新请求 |
| 查询、补充、取消 | 路由原请求；不另造调度器 |
| 重复提交 | 幂等键与内容校验一致则返回原记录；不重复启动 |
| 无法判断属于哪个旧请求 | 由客户端选择或返回待关联；不得猜错请求 |

“一个请求一个调度器”不是“一条消息一个调度器”。每个活动请求只允许一个有效调度代次；崩溃重启可更换进程，但不能出现两个同时有权派单的调度器。

Root 的格式化回复可按请求独立运行，默认回执和转交不必调用模型。最终交付已经就绪时，不应又排队等待一个全局主模型重复分析全部成果。

## 04  并发设计与新的瓶颈边界

一个固定逻辑身份并不必然把所有任务串行处理。例如 Boost.Asio 可以用线程池处理不同事件；strand 用于串行化选定的一组状态处理，而非要求所有请求共享一把全局锁。[N01][N02]

本版用请求级 Dispatcher 显式隔离重规划工作。建议每请求一条控制邮箱，跨请求并行；只在提交短状态变更时排序，不在锁或事务里等待模型、命令和远程 Agent。

**必须分开配置的额度：** 活动调度器、每请求团队数、全系统执行者、模型端点并发、输入/输出预算、工具进程数、磁盘与内存。请求记录可以立即创建，进程和模型调用按额度调度；收到一千个请求不等于立即启动一千套执行进程。

等待 Review、工具、外部输入时，释放模型调用和执行并发槽；逻辑任务状态继续保存。保留审核和交付的容量，避免所有资源被开发任务占满。主入口的输出格式化队列与规划队列分离。

**跨请求共享资源另有仲裁。** 不同 Dispatcher 同时修改同一仓库、分支、数据库或外部对象时，通过中央资源租约和版本比较处理。可以并行准备候选版本，但共享目标的提交或合并受控。Git worktree 提供多个工作树，同时仍共享部分仓库资源，不能代替仲裁和权限隔离。[N07]

没有现成合并规则时，冲突进入 BLOCKED，并交给指定请求调度器、显式集成任务或人工裁决；不得让固定 Root 重新承担全局逐项规划。

**性能验收看三个阶段：** 接单确认、规划开始、合格交付。并行度提升不等于线性加速；增加 Dispatcher 也会增加模型、上下文和进程开销。额度与阈值以真实负载测试确定。

## 05  请求调度器的计划、验收与总目标

Dispatcher 接收原始任务后明确 goal、scope、non_goals、验收标准、输入版本、风险边界和交付对象。需要用户补充时生成澄清事件，由 Root 对外沟通；不能为了“不筛选”而盲目执行歧义任务。

任务计划是版本化的结构化图，不只存在于模型对话。每个节点记录负责能力、输入输出契约、依赖、必需性、预算和验收关口。动态扩展计划必须由内核验证权限、循环、预算、依赖和当前版本。

**分工不重复。** Dispatcher 明确“整个请求做什么、模块怎样协作、什么条件算交付”；TeamLead 明确“这个团队接下来如何做、变化怎样落实”；Worker 实际执行。不要让三者每轮重复编写同一份长计划。

成功交付的建议谓词：

```text
当前 plan_revision 已冻结并满足交付条件
AND 所有必需节点已交接或被合法替代/跳过
AND 所有必需审核绑定当前需求与成果并通过
AND 没有未处理的方向变更、外部副作用或阻断问题
AND 最终成果和交付文档已提交到独立交付区
```

“全部任务”指当前有效计划中的必需工作；条件分支未选中的节点不应永远阻挡结束。失败、取消、超预算和需要裁决必须明确反馈，不允许为了凑齐成功状态而跳过必需审核。

Dispatcher 负责最终业务验收，但必需独立审核的签名或记录由相应审核主体产生，不能自行代签。验收政策在请求开始时确定；修改必需审核标准必须走授权变更，不由正在执行的团队单方降低。

## 06  Agent 注册、能力契约与双向调用

所有功能 Agent 注册稳定身份、能力名、契约版本、调用权限、接入地址、配额和配置版本。工作流调用“某个功能 Agent 的某项能力”，不直接调用模型品牌。

```text
调度 D1 申请 review.review_code
  → 统一 InvocationService
  → Review 主入口（不做重规划）
  → 本次审查请求的调度 D2
  → Review 团队负责人 → Review 执行者
```

D2 将已交接的审查结果交给 Review 入口，由调用适配层回送 D1 的运行上下文。内部同机可用事件队列，外部使用 A2A 或受控任务 API；协议必须进入同一权限和状态内核。A2A 提供 Agent Card、消息、任务、成果和能力相关的交互机制。[N06]

**关联不是控制权。** 跨功能委派保留 root_request_id、调用方和父任务关系，但 D1 不能直接命令 D2 的 Worker；D1 只能修改自己委派的任务要求。接收方有自己的权限、模型默认值与团队模板。

每次调用记录本地 task_id、远程 task_id、invocation_id、capability_version、reply_to、deadline、budget_root_id 和幂等键。只有必要输入和授权成果引用被传递，不复制完整私有聊天与凭据。

**避免等待闭环。** 审查返回“不通过”报告后，该审查任务即可交接完成，由原开发请求调整并发起下一轮审查。不要让审查任务一直等待开发最终完成，而开发又等待它完成。A2A 终态任务不能重新启动，跨端点复审应创建关联的新任务。[N06]

跨功能预算属于原请求的受限预算子树，不因多次委派无限增加。第三方 Agent 是否支持变更、取消和清除按能力声明核对；不能假设其内部也采用本系统的四角色架构。

## 07  工作流定义、运行实例与控制权

工作流引擎是确定性的 C++ 模块。Dispatcher 负责选择模板和提出业务计划，引擎负责校验、派发、推进、持久化和恢复。两者不建立两套派单机制。

| 类型 | 最小语义 |
| --- | --- |
| agent_task | 向一个已注册功能能力提交任务 |
| local_team_task | 由当前调度器创建自己的负责人/执行者团队 |
| branch | 根据校验后的结构化字段选择路径 |
| parallel / join | 并行运行；明示全部、部分或其他合法汇合条件 |
| wait_event / wait_input | 订阅特定任务和版本的事件或输入 |
| task_change | 对已有任务发版本化 AMEND，不重复创建 |
| bounded_loop | 显式轮次、预算、截止时间与退出条件 |
| acceptance / handoff | 验证审核证据，提交业务验收和持久化交接 |
| end / error | 区分成功、失败、取消、待裁决 |

**三个身份层次。** workflow_definition_id＋version 定义模板；workflow_run_id 表示一次流程；node_run_id 表示某节点某一轮执行。相同 node_id 出现在多个模块、多个请求时不能当成同一个节点运行。

建议支持固定流程、受控动态委派和混合流程。第一版以固定关口＋有限动态拆分为主：业务目标可由 Dispatcher 拆成多个模块，但审核、权限和交接不能绕过。

流程定义更新默认只影响新运行；活动流程需要显式迁移。分支表达式使用受限、无副作用的类型化表达式，不在配置中嵌入任意 Shell。可视化、YAML 和自然语言草案都编译为同一中间表示。

编译时检查能力存在、输入输出匹配、权限、可达性、等待环、循环上限、失败路径及唯一验收主体。运行时继续验证版本、额度和有效执行身份，不能仅靠启动前检查。

## 08  开发—审核流程示例与事件语义

本例不是产品唯一流程。开发和 Review 都是可配置功能主入口，各请求拥有各自 Dispatcher。

```text
开发入口 → 开发调度 D1 → 多模块开发团队
候选成果提交 → D1 委派 Review 能力
Review 入口 → 审查调度 D2 → 审查团队
审查报告交接 → D1
  不通过：修改原开发任务 → 新候选版本 → 新一轮审查
  通过：必要集成验证 → D1 最终验收 → 提交交付包
开发入口 → 对外交付确认 → 请求私有资源清理
```

**不能等开发任务最终完成才启动审查。** 开发完成可能依赖审查，因此应以 artifact.submitted 事件触发审查。提交事件携带不可变候选快照，不引用会持续变化的“最新目录”。

建议的报告字段包括 verdict、requirements_revision、candidate_ref、baseline_ref、findings_ref 和 evidence_ref。verdict 可为 pass、changes_requested、inconclusive；未知值、缺证据和版本不匹配不走默认通过分支。

审查报告交付成功不等于代码审查通过。一份“不通过”的报告可以是已合格交付的审查任务成果，其调度器与团队在交付确认后可以结束；开发请求继续存在。复审读取已经交接的问题和代码快照，不依赖旧审查进程。

**模块并行与集成分开。** 每模块独立运行开发—审核子流程，汇合当前有效版本；模块分别通过不替代必要的整体集成验证。合并产生新成果后，核对审核覆盖范围，必要时重新审核。

返回的消息只推动其关联的 node_run_id、候选版本和迭代，不使用“谁最后返回就听谁”。已经过期的审查可留作活动期诊断，不得放行新版本；关闭后的存储处理遵循第 14 章策略。

## 09  数据模型与一致性约束

| 实体 | 关键字段与用途 |
| --- | --- |
| Request | request_id、root_request_id、owner_root_id、需求版本、交付政策 |
| DispatcherInstance | dispatcher_id、request_id、lease_epoch、有效配置、状态 |
| WorkflowRun | definition_ref、plan_revision、workflow_run_id、当前节点集合 |
| NodeRun / Task | node_run_id、iteration、task_id、parent_task_id、目标/执行版本 |
| TeamInstance | team_id、lead_id、worker_id、execution_epoch、workspace_ref |
| Invocation | invocation_id、本地/远程任务映射、调用权与预算引用 |
| Artifact / Review | 固定版本、摘要、访问范围、验收证据和审核主体 |
| Delivery | delivery_id、成果包摘要、接收方、确认政策与回执 |
| CleanupJob | cleanup_id、资源清单、保留政策、清理进度与失败原因 |

使用独立的 state_version、requirements_revision、plan_revision、applied_revision 和 lease_epoch，避免一个“版本号”混担所有含义。模型输出身份、审核主体和权限均由运行时验证或补充。

**同一请求只有一个当前有效调度代次。** 调度器恢复时领取新代次；旧模型响应、旧进程派单和旧工具结果不能覆盖当前状态。模型调用前取得的状态，返回后必须重新核验。异步消息等待期间会发生状态变化，不能把进入处理函数时的状态当成永远有效。[N04]

状态更新与待发送事件同事务提交，收件箱按 event_id/command_id 去重。task_id 不能单独作为消息去重键，否则会误删同一任务的合法修改。最小唯一键和条件写入应纳入数据库约束。

成功接收之前先完成持久化。SQLite WAL 可作为单机候选，但仍一次只有一个写者，应使用短事务和明确的同步策略；模型与远程 I/O 不进入数据库事务。[N09]

## 10  中途调整、失败与恢复

Root 接收带 request_id 的修改并投递到原 Dispatcher。调度器明确停止项、保留项、作废项、新工作和新验收条件；涉及多个团队时沿依赖图更新受影响节点。

```text
CHANGE_RECEIVED → CHANGE_PLANNED → CHANGE_APPLYING
→ CHANGE_APPLIED（或 BLOCKED / REJECTED_WITH_REASON）
```

目标要求与实际执行版本并行显示。允许的已运行操作如何取消由工具能力决定；不能取消的操作先核对实际结果，需要时走补偿或人工确认。旧版本在启动新工具、提交成果和发布交付前都应被拒绝。

**调度器崩溃。** 运行时保存未完成计划和关键事件，失效旧租约，按策略让执行者在安全边界等待或暂停，再恢复同一逻辑调度器。恢复不是重新接单，更不是无差别重跑整个请求。

**重试与副作用。** 派单可去重，但“外部动作成功、确认未落盘”仍需核对或幂等能力。发布、发送消息和外部写入不能直接盲重试。Temporal 的活动设计同样强调重试边界与幂等性，这里作为语义参考而非强制采用其运行时。[N03]

**故障不是正常验收。** FAILED、CANCELLED、SUPERSEDED 走独立收尾流程，反馈原因、已有成果和未决副作用；不能无限等待“所有审核通过”。父子任务的关闭策略必须显式设置，父任务退出并不天然意味着所有子任务已妥善结束。[N05]

等待时间、无进展阈值、返工轮次、总调用深度和预算均有限。达到上限后返回待裁决或失败，不自动降低验收标准。主入口必须仍能反馈阻塞和澄清，即使成功成果只在全部通过后统一交付。

## 11  状态机：业务、交付和资源分别管理

| 状态维度 | 建议状态推进 |
| --- | --- |
| 请求业务 | RECEIVED → QUEUED → PLANNING → RUNNING → VERIFYING → READY_TO_DELIVER |
| 请求异常 | WAITING_INPUT / ADJUSTING / BLOCKED / FAILED / CANCELLED / SUPERSEDED |
| 最终交付 | PACKAGE_STORED → DELIVERY_PENDING → DELIVERY_CONFIRMED |
| 资源关闭 | ACTIVE → DRAINING → STOPPED → CLEANING → CLOSED |
| 清理失败 | CLEANING → CLEANUP_FAILED → 重试清理 |

正常成功语义要求：业务已验收、交付已确认。界面允许显示“交付已完成，资源待清理”，不要把清理状态与业务成败合并。

**交付包进入主入口不等于已经对外交付。** 请求调度器提交 PACKAGE_STORED 后等待交付事件。无确认时保留必要恢复信息与正式交付包，不允许按成功路径删除唯一成果。

Root 的外部确认方式按渠道配置：受认证 API 回执、用户确认，或事先约定的持久化交付区可用性检查。HTTP 已发送或模型说“已交付”不能自动等价于对方已接收。若采用“存入指定交付区即完成”，必须是明确的交付契约。

交付包就绪后又收到修改：运行时比较需求版本。若尚未对外发布，旧包不能继续放行；若外部操作已经发生，记录事实并新建修订交付，不声称已经撤销。派发确认和外部写入之间的不可原子间隙需由幂等键、查询核对或人工处理覆盖。

**等待不等于持续推理。** Dispatcher 可以保持轻量等待状态，不占模型调用槽。可选的休眠恢复优化需有持久化保证；不能将未经批准的“提前彻底关闭”当成默认行为。

## 12  最终成果包与审核证明

最终交付包必须独立于临时团队工作空间，不能只给一个即将删除的路径。建议包含：

| 内容 | 目的 |
| --- | --- |
| manifest | request_id、需求/计划版本、交付版本、文件摘要和访问范围 |
| deliverables | 实际代码、文件、报告或受控服务的正式访问方式 |
| handoff | 使用方法、部署条件、依赖、运行/验证步骤、接手说明 |
| acceptance | 验收标准、覆盖结果、审核引用和批准主体 |
| limitations | 未决风险、限制、未覆盖范围和明确非目标 |
| operations | 外部副作用、正式资源所有者、必要的恢复或回滚说明 |

所需业务文档由团队产出，Dispatcher 审阅并汇总；运行时提供结构化打包和登记能力。Root 可以格式化对外说明，但不能不经版本化审核就改动已验收的成果或证明。

独立审核的证据要绑定候选版本和当前要求。Dispatcher 能接受审核报告、提出复核和按政策裁决，但不能伪造审核主体或覆盖不可豁免的“不通过”。无需独立 Review 的低风险流程可采用其他预先定义的验收标准，不能把代码审查强加给所有业务。

“所有任务完成”不要求历史中被取代的每个尝试都成功。它要求当前有效计划中的必需成果、依赖、审查与交接都满足约定，且没有仍然有效的未完成义务。

正式长期服务要先转交到正式运行环境并确认管理主体。清理请求进程不能一并终止刚交付的生产服务；该服务不再属于临时请求资源清单。

## 13  安全退出与团队资源清理

**Agent 提出关闭申请，运行时执行关闭。** 不能让 Dispatcher 自己拼接删除命令，也不能只删除一个父进程就假设下属工具已退出。

建议顺序：确认交付关口；冻结新派单和新工具；核对未决外部调用；撤销临时执行授权；请求正常退出；超时按政策终止；核对进程树与打开资源；按白名单清理请求私有数据；登记清理结果并重试失败项。

Linux cgroup v2 可按请求及团队组织资源，并通过 populated 状态核对是否仍有活进程；cgroup.kill 可终止受控子树。它不替代文件系统、网络或系统调用隔离。[N08]

```text
请求资源组（只分配子组，不放内部管理进程）
  dispatcher 叶组
  team-A / lead 叶组
  team-A / worker-and-tools 叶组
  team-B / lead 叶组
  team-B / worker-and-tools 叶组
```

示意层级须按目标 Linux 的控制器、权限和“内部节点不放进程”等规则验证。[N08] 清理管理器位于请求资源组之外，因此 Dispatcher 已崩溃仍可恢复清理工作。

**所有权是删除边界。** 只处理当前请求独占的目录、会话、索引与缓存引用。公共模型模板、共享仓库对象、公共缓存、其他请求资料和用户原件不属于它。共享对象按引用/租约回收，不能按路径前缀粗暴删除。

默认按本轮要求在整个请求交付确认后进行最终回收。某个团队已经完成自己的验收交接时，可选“团队级提前回收”减少空占，但正式成果和所需复审材料须已转出；该优化不应默认为用户已批准。

## 14  “删除所有记录”的明确政策

用户的目标是请求结束后不再积累调度器和团队记录。建议把运行期可靠性与结束后保留拆开：活动期间保存恢复所需状态；交付确认后按选定策略清除，而不是边执行边删除唯一状态。

| 策略 | 清除什么 | 保留什么与代价 |
| --- | --- | --- |
| CLEAN_RUNTIME | 请求私有对话、临时日志、工作目录、中间产物、私有索引等 | 正式交付物；建议中央只留最小终态/去重/交付回执。回执保留需明确选择 |
| EXPORT_AND_PURGE | 交付确认后清除本地请求内容及本地交付副本；完成传输收尾后清除请求索引与回执 | 只由外部接收方持有交付；本地不再支持历史查询、续作和事后恢复 |

本版不将中央回执永久保存作为硬要求。严格模式可以选择最终零本地请求记录，但必须公开说明：没有剩余标识就不能继续识别该旧请求的重复提交，也不能在清除后证明历史交付或进行重放。

建议严格模式在清除之前先停止回调与重试、撤销临时凭据、处理在途消息，并使用有期限的消息有效性规则；等待必要收尾期间的最小状态不是永久留存。保留窗口与幂等保证窗口必须一致；没有通用的无限去重且零记录方案。

**删除范围不止工作目录。** 还包括任务数据库、事件载荷、收发件箱、搜索/向量索引、诊断采样、本地模型会话、快照和备份。保留备份时不能同时宣称本地所有副本已立即清除。可考虑请求级加密存储和独立密钥生命周期，但仍须验证全部副本和恢复路径。

逻辑删除不等于介质安全擦除。SQLite 的 secure_delete 也有虚拟表等边界，单条 DELETE 不能证明全系统不可恢复。[N10] 远程模型、MCP 与第三方 Agent 的日志/缓存按对方实际能力和留存政策处理，不能承诺本系统删除目录就连带删除第三方副本。

## 15  模型配置、上下文与高缓存率的继承

保留用户原规则：模型和思考等级分别配置，未设置字段直接继承所属功能主代理，不沿临时父级逐级覆盖。建议新增 Dispatcher 同样支持独立配置；TeamLead 和 Worker 不默认继承 Dispatcher 的覆盖值。

```text
功能主代理默认模型 A / 思考高
Dispatcher 设置模型 B / 思考未设 → B / 高
TeamLead 未设置                    → A / 高
Worker 设置思考中 / 模型未设       → A / 中
```

以上仅说明继承逻辑，假设模型支持档位；供应商映射由适配器校验。Root 即使接单时不调用模型，仍可持有功能默认值和可选的对外表达模型配置。不要因为入口轻量化就悄悄把全体默认值改成便宜模型。

建议请求创建时冻结该功能的默认配置快照；随后创建的团队从本请求快照解析，避免长流程中出现隐式混配。显式配置变更可在安全边界应用；权限撤销和紧急停止不受冻结限制。

新增请求不应把随机 request_id、team_id、时间和物理目录塞进公共前缀。按角色模板、固定工具集、项目资料快照、任务私有内容的顺序编排。不同请求共享稳定前缀，私有会话隔离；变化尽量追加而非每轮重写开头。

供应商前缀缓存有自己的内容匹配、时长和就绪规则，创建更多 Dispatcher 不自动获得高命中率；例如 Claude 要求相应前缀匹配，并区分缓存建立与读取。[N11]

请求清理删除私有上下文和其缓存引用，不删除公共角色模板或其他请求的可复用内容。严格隐私模式下的私有远端缓存禁用/清除能力必须登记，不为命中率扩大数据共享。

主流端点、MCP、Skills、插件的兼容目标继续沿用 v0.1；本版不新增未核验的“全部支持”承诺。工作流绑定能力，模型端点绑定角色配置。

## 17  工作流草案：节点、事件与返工

以下是当前请求调度器运行的片段。local_team_task 在自己范围创建团队；agent_task 经过目标功能主入口创建关联请求。引用语法及表达式尚待编译器实现。

```yaml
workflow:
  id: module_delivery
  version: 1
  authority: current_dispatcher
  max_review_rounds: 3
  on_limit: WAITING_INPUT
nodes:
  build:
    type: local_team_task
    capability: implement_module
  review:
    type: agent_task
    target: review.review_code
    input: "$event.candidate_snapshot"
  revise:
    type: task_change
    target: "$build.task_id"
    mode: AMEND
    expected_revision: "$build.current_revision"
    input: "$review.output.findings_ref"
  accept:
    type: acceptance
    evidence: "$review.output.evidence_ref"
  deliver:
    type: root_delivery
edges:
  - {from: build, on: artifact.submitted, to: review}
  - {from: review, on: task.completed,
     when: "verdict == 'pass'", to: accept}
  - {from: review, on: task.completed,
     when: "verdict == 'changes_requested'", to: revise}
  - {from: accept, on: acceptance.recorded, to: deliver}
```

每次候选提交或复审有新的 node_run_id；revise 修改原任务而非另造相同开发任务。交付节点必须等确认，错误、结论不明及版本失配进入独立处理分支。示例省略这些展开定义，正式发布时不得省略必需异常路径。

## 18  C++ 模块与实现顺序

| 模块 | 本版新增或调整的职责 |
| --- | --- |
| RootGateway | 快速接单、请求关联、对外消息、交付通道 |
| DispatcherSupervisor | 每请求实例、租约、唤醒、崩溃恢复与关闭 |
| AgentRegistry / InvocationService | 能力注册、受控跨功能委派、远端任务映射 |
| WorkflowCompiler / Engine | 定义校验、节点运行、事件推进、循环与迁移 |
| TaskStore / EventInbox / Outbox | 原子状态、指令与事件去重、活动期恢复 |
| ResourceArbiter | 跨请求共享对象租约、版本提交和公平配额 |
| TeamSupervisor / Executor | 一对一团队、四角色权限、工具执行与隔离 |
| DeliveryManager / CleanupManager | 正式成果、回执、权限撤销、按政策清除 |
| ContextCompiler / ModelAdapter / Cache | 稳定模板、角色配置、端点差异和缓存测量 |

第一阶段先实现不调用模型的接单与唯一调度实例，用可控的模拟任务验证多个请求并行、重复提交不重建、修改能找回原请求。第二阶段接入 Dispatcher 的计划和本地团队执行，并验证有限并发和故障恢复。

第三阶段加入能力委派、固定工作流、候选提交触发审查、版本化返工和独立审核证据。第四阶段实现真实交付回执、完整关闭与两种清理策略，并测试崩溃、网络中断和重复回调。

最后再完善自然语言流程草案、可视化编辑、动态计划、更多端点与缓存优化。不得在可靠交付和回收尚未验证时，仅凭正常路径演示宣布完成。

建议延续 C++20、CMake 和可替换依赖。Temporal 文档只用于说明可靠工作流语义；本版没有选定外部工作流产品，也没有声称其存在可直接替换本内核的原生 C++ 实现。

## 19  拟定验收用例（功能与并发）

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |

## 20  拟定验收用例（交付、恢复与清除）

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| V215 | 调度器崩溃恢复 | 恢复同一请求，新代次有效；旧调度器不能再派单 |
| V216 | 外部动作后崩溃 | 先核对幂等或外部结果，不无差别重做有副作用步骤 |
| V217 | 审核被绕过 | 缺必需审核、代签或擅改标准时拒绝最终验收 |
| V218 | 交付网络中断 | 保存交付包；按契约核对/重试，不因“已发送”清除唯一成果 |
| V219 | 交付时收到修改 | 过期未发包被阻止；已发结果明确记录并走修订，不伪装撤回 |
| V220 | 子进程残留 | 退出核对覆盖工具后代；清理管理器不依赖 Dispatcher 存活 |
| V221 | 清理失败重启 | 不丢业务交付结果；按进度幂等重试，仅清本请求资源 |
