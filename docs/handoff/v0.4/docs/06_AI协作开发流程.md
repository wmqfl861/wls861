# AI 协作开发流程（Claude + GPT）

## 1. 分工

| 谁 | 做什么 |
| --- | --- |
| 你（项目所有者） | 选任务卡并分配；裁决分歧；批准 ADR 提议；合并；更新卡片状态；运行需要 API Key 的 live 测试 |
| 实现者（Claude 或 GPT） | 按任务卡实现、写测试、写交接记录 |
| 审查者（另一个） | 对照规格和任务卡审查，输出审查报告 |

建议轮换：这张卡 Claude 写、GPT 审，下一张反过来。两个模型的盲点不同，交叉审查比自己审自己更容易发现问题——这和无量山自己"开发 + 审核"的设计是同一个道理。

## 2. 一次性准备

1. 建代码仓库（P-04，建议 GitHub 私有仓库），把本 S0 包作为第一次提交。
2. 两边的接入方式（任选）：
   - Claude：Claude Code（本机或网页版连接这个仓库）。Claude Code 会读仓库根目录的 CLAUDE.md，它已经导入了 AGENTS.md。
   - GPT：Codex（会读 AGENTS.md），或者在 ChatGPT 里上传仓库压缩包。
   - 不用代码托管也可以靠压缩包往返，但要自己保证每次给出去的都是最新版本。
3. 准备一台 Ubuntu 24.04（实体机、虚拟机或 WSL2 都行）用来构建和测试。

## 3. 每张任务卡的流程

1. **你：** 把卡片状态改为"进行中"，对实现者说："先读 AGENTS.md，然后做任务卡 S1-xx。"
2. **实现者：**
   - 读 AGENTS.md → 任务卡 → 卡片引用的规格章节；
   - 在分支 `s1-xx-短名` 上实现；
   - 运行 `scripts/ci.sh`，全部通过；
   - 按第 5 节写交接记录（PR 描述）。
3. **你：** 把分支、PR 链接或 diff 交给审查者："请按 docs/06 第 4 节审查 S1-xx。"
4. **审查者：** 输出审查报告（第 4 节）。
5. 有"必须修改"项 → 实现者修改 → 再审。两轮之后仍有分歧，由你裁决。
6. **你：** 合并，把卡片状态改为"已合并"。

## 4. 审查报告格式

```markdown
## 审查报告：S1-xx
结论：通过 / 需修改

### 必须修改
1. [文件:行] 问题 —— 违反了规格哪一条，或会导致什么后果 —— 建议改法

### 建议修改（可选）

### 规格一致性
- 字段名、状态名、表名与 schemas/、db/schema.sql 一致：是 / 否（列出不一致处）
- 任务卡"做"的每一项都已完成：是 / 否
- 没有超出任务卡范围：是 / 否

### 测试
- 任务卡要求的验收用例都有对应测试：是 / 否（缺哪些）
- 运行结果：…（审查者能运行时填写）
```

审查重点：正确性和规格一致性优先，风格问题放进"建议修改"。

## 5. 交接记录（PR 描述）模板

```markdown
## S1-xx 交接记录
- 改了什么：
- 怎么验证：（命令与结果）
- 对应的验收用例：
- 与规格的偏差：无 / 有（附 ADR 提议编号）
- 遗留问题，以及下一张卡需要注意的事：
```

## 6. 规格变更

- 规格是唯一权威。实现者或审查者发现规格有错、自相矛盾或做不到时：停下来，在 `docs/00_决策记录.md` 的"提议"区追加一条（编号、内容、理由、影响的章节），并在 PR 中说明；不要自行偏离。
- 你批准后，先改规格、再改代码，放在同一个 PR 里。
- 明显的笔误（错别字、编号错误）可以直接改，在交接记录里说一声。

## 7. 上下文传递

- 每次新会话都从"先读 AGENTS.md"开始，不依赖上一次会话的记忆。
- 卡片太大时，先让实现者给出拆分方案，你确认后再分几次实现。
- 需要真实 API Key 的测试（tests/live/）由你在本机运行，再把输出贴给 AI。
- 不要把 API Key 发给任何 AI；配置文件里只写环境变量名。

## 8. 节奏

- 第 2、3、4 批的卡可以并行：同时让 Claude 做一张、GPT 做另一张，再互相审查。
- 每合并一张卡，更新 `docs/07_S1任务卡.md` 里的状态表；每完成一批，完整跑一次 `scripts/ci.sh`。
