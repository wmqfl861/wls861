# 验收计划 v0.4

## 1. 原则

- 每个切片的验收 = 自动化测试（单元测试，加上用 FakeModel 的集成测试）+ 真实模型的端到端演示 + 从 S2 起的基准任务对照。
- 结果只有三种：通过、失败、未执行。未执行的必须写原因，不能当作通过。
- 证据写进各切片的验收报告：测试名、提交号、配置、输出摘要。
- 用例编号：`V3-xxx` 沿用 v0.3 矩阵（保留原编号便于追溯），其余为 v0.4 新增。

## 3. S2 并行与审核

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| GEN-01 | 通用性 | general 之外再加两个功能模板（首个正式功能 + 审核功能），不改核心代码即可运行 |
| CAP-01 | 模板化 Dispatcher | review_code 能力调用不产生 Dispatcher 规划的模型调用；输出不合 Schema 时不算验收 |
| EVAL-01 | 基准对照 | 每个功能 15–20 个代表性任务，记录通过率、费用、耗时；与 `--single-agent` 模式（同模型、同工具）对照，出报告 |
| NET-01 | 网络白名单 | 白名单内的域名可访问，其他域名被拒 |
| WT-01 | git worktree 工作区 | 代码类任务在独立分支上工作；交付分支名和补丁；清理后 worktree 被移除，分支保留 |
| V3-007 | 崩溃恢复 | 恢复后代次 +1，旧进程或迟到的模型结果不能再派单或提交 |
| V3-008 | 副作用未知 | 操作完成但结果未落盘时崩溃：标为 UNKNOWN，外部副作用类不自动重做 |
| V3-009 | 资源与公平 | 名额占满时排队有界；有审核待做时为审核保留名额 |
| V3-010 | 跨功能调用 | 经对方 Root；调用方不能直接指挥对方 Worker |
| V3-011 | 候选触发审核 | 提交候选即可送审，不出现开发与审核互相等待 |
| V3-012 | 审核不通过 | "不通过"的报告是合格的审查交付；开发任务不被误判通过 |
| V3-013 | 成果版本 | 审核通过 A 版本后提交 B 版本，旧结论不放行 B |
| V3-014 | 循环上限 | 返工到达轮次上限 → 任务 BLOCKED，运行时直接问用户（再给几轮 / 带问题验收 / 取消） |
| V3-015 | 并行汇合 | 多个模块有成功有失败，按"必需依赖全部验收"汇合，不以先返回者为准 |

## 8. 基准任务集（EVAL-01，S2 建立）

- 每个功能 15–20 个任务，覆盖常见、边界和容易出错的情况；每个任务带可以自动检查的通过条件（文件存在、内容校验、测试通过）。
- 每个任务分别用两种方式运行：四角色正常模式、`--single-agent` 模式（只有一个 Worker，同模型、同工具、同预算）。
- 记录：通过率、费用、耗时、各角色 token 与缓存读取占比、返工次数。
- 四角色模式没有在通过率或稳定性上带来收益时，在决策记录里提议调整（例如简单请求跳过 TeamLead），由你决定。
- S3 起增加"关闭记忆 / 开启记忆"两组，用于 MEM-P1。
