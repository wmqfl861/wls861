## 0. 结论

方向对，需求记录基本忠实，值得在这个基础上继续，不需要推倒重来。但它还不是一份能直接开工的蓝图，主要有六个问题：

1. **广而浅，关键决定全部悬空。** v0.3 的 12 项待定（Q01–Q12）只列了"要决定什么"和"影响"，没有一项给出推荐默认值。v0.3 的设计与交接文档约 2.7 万字，除了基础包里列出的 Bash、Git、ripgrep、Python 等候选工具，内核实现需要的技术一项都没定：构建系统、异步/HTTP 库、数据库、向量库、中文分词、沙箱方案、Linux 发行版全部待定，v0.1 曾建议的 C++20、CMake、SQLite WAL 也没有带过来。同一批文档里"不能/不得"出现 62 次、"不等于/不代表"27 次、"待定"类 23 次，大量篇幅在讲不要做什么，具体怎么做很少。
2. **重运行时、轻 Agent。** 状态机、版本号、权限写得很细，但每个角色收到什么、输出什么、什么时候调用模型、提示词长什么样，几乎空白。多 Agent 系统恰恰主要败在这一层。
3. **记忆系统按企业治理级设计**（8 类对象、12 个状态、6 段使用事件链），却没有一个可执行的打分公式、阈值或审批人。按现状很难落地，你最在意的"自我进化"闭环（T13–T20 连续 8 轮都在谈它）可能转不起来。
4. **三处跨模块冲突没有解决**：清理与记忆、缓存与动态回忆、四层结构与速度/成本。
5. **实施顺序横向分层**，最大的不确定性（模型在各角色上的实际表现）放到后面才验证，很长时间都没有你能拿来干活的版本。
6. **验收有缺口**：你的第一条需求（T01）里，MCP、插件、与外部 Agent 双向互调在 v0.3 的 51 个用例里一个都没有；Skill 只有"导入后不直接执行""缺依赖时报缺口"两条防错用例，没有"标准 Skill 包能被正确加载和使用"的正向用例。

## 2. 应该保留的设计

- **确定性内核与 Agent 分离。** 状态、版本、权限、清理由 C++ 程序负责，模型只做判断。这是整套设计最重要的一条。
- **请求级 Dispatcher。** 解决了你在 T09 担心的单点串行。
- **多个版本号分工。** requirements_revision / applied_revision / lease_epoch，迟到的旧结果不能覆盖新要求，这是"中途改方向不乱"（B5/B6）的基础。
- **模型配置逐字段直接继承 Root**，并区分"未设置 / 关闭思考 / 供应商默认"。
- **候选成果即触发 Review**；"不通过的审查报告也是合格交付"，避免开发和审查互相等待。
- **记忆的几条判断很准：** "加载≠使用≠导致成功"、"热度≠正确"、"同一份证据不重复计分"、"强制规则不靠检索碰运气"。作为对照，Hermes 的 curator 按"多久没被用"把 Skill 标为过期并归档，use_count 在 Skill 被加载进提示时就加一；在"用得多不等于有效"这一点上，你的设计比它严谨。
- **状态如实标注**，没有把设计说成已实现。

## 3. 问题与优化建议

### 3.1 补一份"角色行为规格"（优先级最高）

**问题。** v0.3 没有任何角色的提示词骨架、输入输出格式和唤醒条件。UC Berkeley 对 7 个开源多 Agent 框架、200 多条执行轨迹的分析（MAST）显示：失败中 41.8% 源于任务规格问题，36.9% 源于 Agent 之间不一致，21.3% 源于验证和终止问题；多 Agent 相对单 Agent 的提升"常常很小"。这些主要是设计与协调问题，正是这份蓝图空着的部分。在你的链路里，需求下行要经 Dispatcher、TeamLead 两次模型转述才到 Worker，结果上行同样要经过两层；每转述一次都会丢信息，最容易丢的是限定条件、否定结论和没写下来的决定。

**建议。**

1. **原始需求直达。** 请求原文和验收标准存成不可变成果，所有层级按引用读取原文；上层只能追加补充说明，不能改写原文。Worker 任何时候都能看到你的原话。
2. **结构化交接。** 用 JSON Schema 定义 6 种消息：TaskBrief（任务说明）、ChangeOrder（停止 / 保留 / 新增 / 新验收条件）、Submission（成果、自检结果、实际用到的记忆）、ReviewVerdict（pass / changes_requested / inconclusive）、Question（逐级上报）、ExperienceNote（经验条目）。模型输出不符合 Schema 就重试或报错，不进入状态机。
3. **唤醒表。** 明确每个角色在什么事件下才调用模型（见下表），机械的状态转发一律由程序完成。
4. **问题上报不转述。** 每一层先用自己掌握的上下文尝试回答，答不了就原文转发。
5. **提示词随代码管理。** 每个角色给出提示词骨架和 2–3 个正反示例，与代码一起做版本管理和回归测试。

| 角色 | 唤醒事件 | 不唤醒 |
| --- | --- | --- |
| Root | v1 不调用模型，纯代码路由；对外文字由 Dispatcher 写好、Root 原样发送 | — |
| Dispatcher | 新请求、变更、团队提交 / 求助 / 失败、全部完成、预算告警 | 进度心跳、Worker 的每一步 |
| TeamLead | 团队启动、收到 ChangeOrder、Worker 提问、Worker 提交（对照验收标准自检）、停滞告警 | Worker 正常的工具循环 |
| Worker | 持续的工具循环 | — |

### 3.2 运行模型：Agent 是协程，不是进程

**问题。** v0.1 建议"每个活动团队有受控的子 Agent、孙 Agent 进程"，v0.2 的 cgroup 示意也给 Dispatcher 和每个 TeamLead 分了独立叶组，等于按"一个 Agent 一个操作系统进程"来设计。但 Agent 本质上是"一个上下文加一串模型调用"，大部分时间在等网络，不需要独立进程。

**建议。** 所有 Agent 作为同一个 C++ 服务进程里的协程运行（C++20 协程 + Boost.Asio）。只有 Worker 发起的工具执行（shell、编译、脚本）才是子进程，按团队放进 bubblewrap 沙箱和 cgroup v2。"结束一个团队"就是：杀掉该团队 cgroup 里的进程、删除工作目录、丢弃内存中的上下文。这样省掉进程间通信，崩溃后从 SQLite 重建即可，同样满足你"结束进程、清理空间"的要求。

### 3.3 四层结构的速度与成本

**问题。** 没有快速路径。按 v0.2 的跨功能流程，一轮"开发 + 审核"至少涉及 6 个 Agent 上下文（开发侧 Dispatcher / TeamLead / Worker，审核侧 Dispatcher / TeamLead / Worker），多模块、多轮返工时成倍增长。低频唤醒的角色还会碰上缓存过期：Anthropic 默认 5 分钟（可付费延长到 1 小时），OpenAI 从 GPT-5.6 起为 30 分钟，过期后每次唤醒都是冷启动。

**建议。**

1. **Dispatcher 分两档。** 结构化的能力调用（例如 review_code，输入是候选版本加审查标准）走"模板化 Dispatcher"：不调用模型，按能力模板直接建一个团队，按 Schema 验收输出。自由文本请求照常由 Dispatcher 规划，但允许它直接给出"单团队"计划，不强制拆解。这样仍然经过对方 Root，不改变已经定下的结构，只省掉一次没有必要的规划调用。
2. **按唤醒频率选上下文策略。** Worker 用"追加式对话"：循环紧密，缓存命中高。Dispatcher 和 TeamLead 用"快照式唤醒"：每次唤醒的上下文 = 稳定前缀 + 从数据库生成的当前计划、团队状态和决策日志 + 新事件。低频唤醒时缓存大多已过期，快照式还能避免上下文无限增长，也符合"TaskEngine 是唯一事实来源"。
3. **推荐模型档位（可选预设，仍服从你的继承规则）。** Dispatcher 用强推理模型，TeamLead 用中档，Worker 用工具调用能力强的模型。

### 3.4 缓存与记忆注入：统一上下文布局

**问题。** 统一记忆引擎规格第 7 节写"阶段进入时注入必要规则、选中方法、约束和少量经验"，但没规定注入到上下文的哪个位置。主流端点的缓存都是前缀精确匹配：Anthropic 的顺序是 tools → system → messages，前面任何一层变了，后面全部失效；改工具定义三层全失效；改思考参数会使消息层失效，部分模型连 tools 和 system 也失效。OpenAI 同样要求整个渲染前缀一致，改 tools 或 reasoning.effort 都会断开前缀。如果把回忆出来的记忆插进 system，缓存会被频繁打断。

**建议：每个角色固定这样的布局。**

```text
[tools：按角色固定，顺序稳定]
[system：角色规则 + 环境卡片 + 常用 Skill 索引]      ← 同角色跨请求共享，可缓存
[项目资料快照]                                       ← 同项目共享，可缓存
[任务契约：原始需求 + 验收标准，不可变]
[messages：只追加；回忆到的记忆和 Skill 以工具结果或附加消息进入]
```

- 会话中途不改 tools 和 system；新 Skill 或记忆只在消息里通告，到下次上下文压缩时才并入 system。Hermes 就是这样保护缓存的。
- 每个 Agent 实例的模型配置（包括思考等级）在其生命周期内冻结。
- Skill 在大约 100 个以内时，把常用 Skill 的 name + description 放进缓存前缀，比检索更可靠，缓存命中后几乎不花钱；长尾再走检索。这其实就是你在 T17 提的第三种做法（"在根目录或每个子类别导入最常用的 Skill"）。"读全部 description"主要在规模很大或没有缓存时才成问题。

### 3.5 记忆系统：做一个轻量首版（保留你的全部概念）

| 你的概念 | v0.3 的做法 | 建议首版 |
| --- | --- | --- |
| Wiki | 抽象的"可重建解释层" | 记忆就是 Git 仓库里的 Markdown 文件（YAML 头），可以直接用 Obsidian 这类工具当 Wiki 浏览和手工修改；Git 自带版本、差异和回滚 |
| Skill | 自定义包结构 | 程序性记忆直接采用 Agent Skills 标准（SKILL.md）。自定义字段放进规范允许的 metadata（规范要求值为字符串），或放在同目录的独立文件里。下载的 Skill 直接导入，自产的也能导出给别的 Agent 用 |
| 分类 | 5 类加多种关系 | 4 类：rule（规则）、skill、experience（成功 / 失败）、fact（事实），其余靠标签 |
| 生命周期 | 12 个状态 | draft → active → archived，另加 blocked（危险内容） |
| 证据 | EvidenceRecord 加 6 段事件链 | 一张反馈表：memory_id、revision、task_id、是否真正用到、结果（成功 / 失败 / 未知）、来源键（去重用）、备注。"是否真正用到"取自 Submission 里声明的实际用到的记忆，并由运行时核对它确实被加载过 |
| 权重 | 4 个维度，公式待定 | 起步公式：得分 =（成功 + 1）/（成功 + 失败 + 2），排序时用置信下界（如 Wilson 下界），这样只成功过一次的新记忆不会压过久经验证的老记忆；失败多的记忆提高"警示"展示 |
| 合并 | 阈值待定 | 同一意图的两条记忆，一方在可比条件下 ≥3 次独立成功、另一方 ≥3 次失败 → 由模型起草合并版 → 回到 draft 重新验证（不继承旧成绩，沿用 GPT 的这条规则）→ 被淘汰部分归档 |
| 审批 | 审批人待定 | 治理档位：personal（默认：项目内经验在任务验收通过后自动生效，每天给你一份变更摘要，可一键回滚）/ team / strict。规则类和跨项目提升始终需要你批准；Skill 里的脚本未经审查不自动执行 |

**"像人一样逐步回忆"的具体机制，分四级：**

1. **规则**：按作用域确定性加载，不走检索。
2. **被动提示**：在触发点（开始任务、进入新阶段、换工具、方向变更、准备验收）由运行时检索，把前几条"卡片"（标题 + 何时使用，每条几十个 token）追加到消息里。
3. **主动回忆**：Agent 有 `recall(query)` 和 `load(id)` 两个工具，需要时自己展开全文。
4. **报错触发**：工具返回错误时，用"工具 + 错误码 / 归一化的错误信息"精确匹配失败经验，自动插入警示。这一级成本最低、命中最准。

**针对 T13（反复找工具怎么调用）**，收益最高的手段其实不是记忆，而是"环境卡片"：每个功能模板自动生成一张卡片，列出装了哪些工具、路径、版本和调用示例，放进缓存前缀。基础环境本来就是版本固定的，卡片很稳定，大部分"我先找一下这个工具在哪"会直接消失。

**经验提炼。** Worker 执行中可以随时调用 `note()` 记下发现（Hermes 式即时保存）；交接时运行时自动生成"轨迹摘要"（用了哪些工具、遇到哪些错误、怎么解决的），TeamLead 基于摘要写经验报告。有真实轨迹作底，比事后凭印象写更不容易编造。

### 3.6 清理政策：直接定默认值

**问题。** T09 的"删除所有记录"和 T19 的"多次验证后加权、合并"直接冲突，加权需要保留历史。GPT 设计了"清运行态 / 导出后严格清除"两套政策，外加安全擦除、备份、远端副本等讨论，全部列为待定。

**建议。** 按你在 T03 给出的理由（省硬盘），默认采用"清运行态"：

- 删除：团队工作目录、完整对话记录、工具日志、中间产物、私有缓存。
- 保留：交付包、经验报告、记忆反馈行（每条几百字节）、最小请求回执（编号、哈希、状态、时间；保留例如 30 天，用于防重复提交）。
- "导出后严格清除"作为敏感项目的可选模式。

这样既省空间，又不妨碍记忆演化。

### 3.7 实施顺序：改成纵向切片

**问题。** M1 先做"无模型内核"，真实模型到 M2 才第一次接入，你最在意的记忆到 M4 才开始。按这个顺序，很长时间都没有能用来干活的版本，而最大的风险（模型在各个角色上是否称职）验证得最晚。

**建议。** 每一片都是能演示的完整闭环。用假模型做的内核测试作为每一片的单元测试，不单独成为一个阶段。

| 切片 | 内容 | 演示标准 |
| --- | --- | --- |
| S0 定稿 | 合并成 v0.4 实施规格；拍板第 5 节的决定；角色行为规格与交接 Schema | 可以按文档直接开工 |
| S1 最小闭环 | 1 个功能 Agent、4 个角色、1 个团队、1 个端点；Worker 文件与命令工具 + bubblewrap；SQLite 状态；CLI 提交、查看、变更 | 提交一个真实小任务，中途改方向，收到交付，工作目录被清理 |
| S2 并行与审核 | 多团队并行、计划 DAG、Review 返工环（轮次上限）、崩溃恢复、预算；只读进度面板 | 两个模块并行开发，Review 打回一次后通过 |
| S3 记忆 v1 | 环境卡片、规则、SKILL.md 导入、note 与经验报告 → draft → active、recall / load、反馈统计 | 第二个相似任务明显少走弯路（工具调用数、报错数下降） |
| S4 互通 | MCP Client（用现成 MCP 服务）、MCP Server（被 Claude Code 等调用）、第二种端点适配器 | 外部 Agent 通过 MCP 给无量山派活并取回结果 |
| S5 优化与扩展 | 缓存实测调优、权重与合并、Wiki 浏览、A2A、更多端点、Windows | 用基线数据驱动 |

如果某个 MCP 工具对你的工作很关键，MCP Client 可以提前到 S2。每一片结束都跑一遍基准任务集（见 3.9），并和"同模型单 Agent"对照，确认四层结构真的带来收益。

### 3.8 互通与端点：按投入产出排序

- **被别的 Agent 调用：先做 MCP Server。** 暴露 submit_request / get_status / amend / get_delivery 等工具。主流编程 Agent 基本都是 MCP 客户端，这是成本最低的路。A2A 已于 2026 年 4 月发布 1.0 稳定版，支持的组织超过 150 家，适合作为第二步。
- **调用别人：MCP Client 优先**，直接复用现有 MCP 生态。注意 MCP 官方 SDK 没有 C++ 版（一级：TypeScript、Python、C#、Go、Rust、Ruby；二级：Java；三级：Swift、PHP、Kotlin），C++ 需要自己实现 JSON-RPC 加 stdio / Streamable HTTP 传输，或评估社区库。蓝图没有提到这一点，低估了这部分工作量。
- **模型端点：先做两个适配器就能覆盖大部分。** Anthropic Messages（Claude；DeepSeek、智谱 GLM（Z.ai）、阿里通义千问也提供 Anthropic 兼容端点）和 OpenAI Chat Completions 兼容（几乎所有国内厂商，以及 vLLM、Ollama、OpenRouter）。之后再按需加 OpenAI Responses、Gemini 原生。能力登记表的思路不变。
- **可选：Worker 执行引擎可插拔。** 除了自研的 C++ 工具循环，也可以把成熟的编程 Agent（Claude Code、Codex CLI、Gemini CLI 等）包装成 Worker，统一接入可以考虑 ACP（Agent Client Protocol，基于 stdio 的 JSON-RPC；Gemini CLI 原生支持，Claude Code 和 Codex 通过适配器）。好处是工具使用质量起点高；代价是对缓存、记忆注入、计费和沙箱的控制变弱。适合作为对照组或过渡方案。

### 3.9 验收矩阵补充

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| IO-01 | MCP Client：接入一个现成的 MCP 服务 | Worker 在授权范围内调用成功；未授权调用被拒 |
| IO-02 | MCP Server：外部 Agent 提交请求、查询、取回交付 | 全流程可用，关联编号完整 |
| IO-03 | 导入标准 SKILL.md 包 | 校验通过并进入 draft；包里的脚本不自动执行 |
| IO-04 | A2A 双向（S5） | 能发现对方 Agent Card，任务往返成功 |
| GEN-01 | 第三种功能模板（如"资料整理"） | 不改核心代码即可运行（v0.1 有 AC01，v0.3 没有带过来） |
| CHG-01 | 执行中途 AMEND | TeamLead 产出完整的 ChangeOrder；Worker 停止旧方向，applied_revision 更新，旧方向不再产生新的副作用 |
| HOP-01 | 约束保真 | 请求里写 5 条明确约束，交付物逐条满足（检测转述丢失） |
| MEM-P1 | 记忆的正向效果 | 相似任务第二次执行时，工具调用数、报错数、耗时下降 |
| EVAL-01 | 端到端基准 | 每个功能 15–20 个代表性任务，记录通过率、费用、耗时，并与同模型单 Agent 对照 |

现有 51 个用例中记忆占 19 个，主要在测"不出错"（隔离、越权、污染、撤销等），没有一个测"用了记忆之后任务做得更好"。补上 MEM-P1 这类正向用例，才能证明记忆系统真的有用。

### 3.10 文档、功能模板与流程

- **单一权威文档。** 把 v0.1、v0.2、v0.3 合并成一份 v0.4《实施规格》，历史原件只留作追溯。现在接手的人要在脑中合并三份文档，而且 v0.3 又声明 v0.1 部分作废。
- **需求编号映射。** v0.1 用 R01–R18，v0.3 改成 R001–R020，没有对照表，补一张。
- **每条待定项给推荐默认值**（见第 4 节），你只需回答"同意"或"改成……"。
- **免责声明集中**写在一个"边界声明"小节，正文只写要做什么。
- **新增功能 Agent = 新增一个目录**（对应 A6）：function.yaml（各角色模型覆盖、工具档、流程模板）、prompts/（角色提示词补充）、skills/（常用 Skill）、环境卡片生成规则。核心代码不动。
- **文档和代码放进同一个 Git 仓库**，架构决定用 ADR（架构决策记录）逐条登记状态。

### 4.1 Q01–Q12 建议默认值

| 编号 | 事项 | 建议默认 |
| --- | --- | --- |
| Q01 | Linux 环境 | Ubuntu 24.04 LTS x86_64，非 root 服务账户。注意 24.04 默认的 AppArmor 策略限制非特权 user namespace，需要给 bubblewrap 单独加一条 AppArmor 配置 |
| Q02 | 首批端点 | 先接你最常用的一家；适配器做 Anthropic Messages 和 OpenAI 兼容两种；密钥放环境变量或密钥文件，配置里只写 secret_ref |
| Q03 | 并发与预算 | 起步：同时活跃的 Dispatcher 4 个、Worker 8 个，每个请求设 token / 金额上限，超出排队；跑完基线再调 |
| Q04 | 审核与裁决 | Dispatcher 做业务验收；代码类必须经过 Review；争议和超限由你裁决 |
| Q05 | 交付回执 | CLI：交付包写入交付目录并发出通知即算交付；API / MCP 调用方：调用方取回交付包即为回执 |
| Q06 | 清理政策 | 清运行态（见 3.6）；严格清除为可选模式 |
| Q07 | 经验保留 | personal 档：项目内自动生效；跨项目和全局需要你批准 |
| Q08 | 记忆部署 | 同进程独立模块（memory_core 库）+ Git 仓库文件 + SQLite 索引；接口按以后可以服务化来设计（同意 GPT 的建议） |
| Q09 | 阈值 | 先用 3.5 的起步公式和"3 次对 3 次"合并触发，评测后再调整 |
| Q10 | 基础包 | bash、coreutils、git、ripgrep、fd、jq、python3、curl（经代理）、diff / patch；各功能再加专用工具 |
| Q11 | 指标 | 先跑基线再定目标；固定跟踪基准通过率、每任务费用、耗时、缓存读取占比 |
| Q12 | 后续路线 | 只读进度面板放在 S2；Windows 放在 S5 之后 |

### 4.2 技术选型建议

| 领域 | 建议 | 说明 |
| --- | --- | --- |
| 语言与构建 | C++20、CMake、vcpkg | C++20 和 CMake 与 v0.1 的建议一致 |
| 异步与 HTTP | Boost.Asio（C++20 协程）+ Boost.Beast + OpenSSL | 流式输出（SSE）、WebSocket、HTTP 服务都能覆盖 |
| JSON / YAML | nlohmann/json、yaml-cpp | 成熟、好用 |
| 状态存储 | SQLite（WAL） | 单文件，备份和清理都简单；短事务，模型和工具调用不放进事务（同 v0.2） |
| 中文全文检索 | SQLite FTS5 + 中文分词扩展（如 wangfenjin/simple，C++ 实现，支持中文和拼音），或自行集成 cppjieba | |
| 向量检索 | sqlite-vec（仍是 0.x 版本），或 hnswlib | 记忆在十万条以内，暴力检索即可满足 |
| 向量模型 | 端点自带的 embedding，或本地多语言模型（如 bge-m3） | 必须中文友好；换模型要重建索引 |

| 记忆文件 | Markdown + YAML 头，存 Git（libgit2 或直接调用 git） | |
| 日志与追踪 | spdlog + 结构化 JSONL；每次模型调用记录角色、模型、token、缓存读写、耗时、费用 | 调试多 Agent 和优化缓存都靠它 |
| 测试 | GoogleTest + 假模型适配器（FakeModel） | 可重复的确定性测试 |
