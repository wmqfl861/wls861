## 0. 阅读说明与边界

- 语义以本文为准；字段名、状态名、表结构以 `schemas/` 和 `db/schema.sql` 为准。两边不一致视为缺陷，按 AGENTS.md 提 ADR 修正。
- 边界声明（全文只说这一次）：本文是设计，尚无代码；涉及供应商的行为（缓存、兼容端点、SDK）依据 2026-10-17 的公开文档，实现时按所选版本复核；文中数值都是起步默认，跑完基线再调。

## 1. 目标与范围

**目标：** 一个自己用的 C++ 多 Agent 系统。任何功能都用同一套组织结构——Root 对外、每个请求一个 Dispatcher、若干 TeamLead + Worker 团队；中途改方向不乱；交付后清理；随着使用积累经验，越用越好。

**v1（S1–S4）包含：** 四角色运行时、计划 DAG 与审核返工环、Worker 沙箱执行、两种模型适配器、记忆 v1、CLI、本地 API、MCP Server / Client。

**v1 不做：** 多机部署、多用户 / 多租户、Windows、通用工作流 DSL 与可视化编辑、插件生态全面兼容、严格清除（S5 可选）、自动换模型或降级。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 功能（function） | 一类工作，如"开发""审核""资料整理"，由一个功能模板目录定义 |
| Root | 某个功能的固定对外入口；v1 是纯代码，不调用模型 |
| Dispatcher | 一个独立请求的调度者：规划、分派、协调、处理变更、验收、交付 |
| TeamLead | 团队负责人：把任务讲清楚、翻译变更、检查成果、写经验报告 |
| Worker | 执行者：唯一能执行命令和改文件的角色 |
| 团队（team） | 一个 TeamLead 加一个 Worker，负责一个任务 |
| 请求（request） | 一次外部提交的工作；修改、补充、取消都路由回原请求 |
| 任务（task） | 计划中的一个节点 |
| 能力（capability） | 功能对外提供的可调用工作，如 `review.review_code` |
| 成果（artifact） | 有哈希的不可变文件或文件包 |
| 交付包 | 请求完成时写入交付目录的成果与说明 |
| 任务契约 | 请求原文、修改原文、验收标准、TaskBrief、WorkOrder 的合集 |

## 3. 总体架构

### 3.1 组件

```text
 用户 ── wls（CLI）── Unix 套接字 HTTP ──┐     外部 Agent ── wls mcp（stdio MCP，S4）──┐
                                         ▼                                              ▼
┌──────────────────────────────── wlsd（单进程）─────────────────────────────────┐
│ RootGateway   接单、去重、额度准入、路由后续消息、对外事件与交付                  │
│ Engine        请求/任务/团队状态机、事件、计划调度、审核返工环、额度与排队        │
│ Agents        Dispatcher / TeamLead / Worker 运行器（协程）+ ContextCompiler      │
│ Model         ModelAdapter：anthropic_messages / openai_chat_compat / fake        │
│ Tools         ToolRegistry、权限检查、Worker 工具、管理工具                       │
│ Sandbox       bubblewrap 启动器、团队 cgroup、工具操作（op）生命周期              │
│ Memory（S3）  记忆仓库、索引、回忆、反馈、每日摘要                                │
│ Delivery      交付包、回执、清运行态                                              │
│ Store         SQLite（WAL）                                                       │
└─────────────────────────────────────────────────────────────────────────────────┘
                       │ fork + exec（显式环境变量）
                       ▼
             bwrap 沙箱里的工具进程（每个团队一个 cgroup）
```

### 3.2 进程模型（ADR-007）

- wlsd 一个进程：Boost.Asio `io_context` 加线程池，每个 Agent 是一个协程。
- 每个请求一条 strand：同一请求的控制事件串行处理，不同请求并行。
- SQLite：一个写连接（专用 strand 串行写入），若干只读连接。
- 模型调用和工具执行在 strand 之外异步进行；结果回到请求 strand 后，先核对版本和代次再生效。
- 只有 Worker 的工具执行是子进程。"结束一个团队" = 杀掉团队 cgroup 里的进程 + 删除工作区 + 释放 Agent 上下文。

## 4. 角色与协作（详见 02）

### 4.1 职责

| 角色 | 生命周期 | 调用模型 | 做 | 不做 |
| --- | --- | --- | --- | --- |
| Root | 常驻，每个功能一个逻辑身份 | 否 | 接单、去重、额度准入、路由后续消息、发出进度与交付 | 规划、验收、执行 |
| Dispatcher | 每个独立请求一个，清理时释放 | 按唤醒表 | 计划、分派、处理变更、回答或上报问题、验收、交付清单 | 执行命令、改文件、代替审核方下结论 |
| TeamLead | 每个团队一个 | 按唤醒表 | WorkOrder、翻译变更、答疑或上报、检查提交、经验报告 | 执行命令、改文件、改变请求目标 |
| Worker | 每个团队一个有效执行身份 | 连续循环 | 在沙箱内用工具完成任务并提交 | 再派生 Agent、越出工作区、改验收标准 |

### 4.2 唤醒表（ADR-009）

| 角色 | 什么时候调用模型 |
| --- | --- |
| Dispatcher | 开始规划；需求被修改；团队上报问题；用户回答了它的提问；任务进入 SUBMITTED（TeamLead 转交或审核通过）；审核结论不明；任务失败或受阻；全部必需任务已验收；预算用到 80% |
| TeamLead | 团队启动；收到 Dispatcher 的变更；Worker 提问；Worker 提交；上级回答了它的上报；审核要求修改；停滞告警；任务验收后写经验报告 |
| Worker | 连续的工具循环；提问后阻塞到有回答；因变更暂停时阻塞到新指令 |

某角色正在处理时又到达的事件，合并进下一次唤醒一起处理。

**停滞告警**（运行时判定，不调用模型）：Worker 10 分钟没有新的工具调用且不在等待长操作；同一 `error_signature` 连续出现 3 次；工具调用数达到上限的 80%。

### 4.3 交接消息（ADR-008）

| 消息 | 方向 | Schema |
| --- | --- | --- |
| Plan | Dispatcher → 运行时 | plan.schema.json |
| TaskBrief | Dispatcher → TeamLead（放在计划节点里） | task_brief.schema.json |
| WorkOrder | TeamLead → Worker | work_order.schema.json |
| ChangeOrder | Dispatcher → TeamLead；TeamLead → Worker；运行时（审核返工）→ TeamLead | change_order.schema.json |
| Submission | Worker → TeamLead → Dispatcher | submission.schema.json |
| ReviewRequest / ReviewVerdict | 调用方 → 审核功能 → 调用方 | review_request / review_verdict |
| Question | 任意角色向上一级 | question.schema.json |
| ExperienceReport | TeamLead → Dispatcher → 记忆 | experience_report.schema.json |
| DeliveryManifest | Dispatcher → 运行时 → 用户 | delivery_manifest.schema.json |

模型输出必须通过 Schema 校验才进入状态机。不通过时把校验错误回给模型重试，最多 2 次；仍失败记 `AGENT_ERROR` 并上报上一级。

### 4.4 原始需求直达

- 请求原文（rev 1）与每次 AMEND 的原文（rev 2、3…）存入 `request_texts`，只增不改。
- 所有角色都能看到全部原文：Dispatcher、TeamLead 每次唤醒时都在任务契约里；Worker 在实例创建时的任务契约里，之后的修改原文以消息追加（02 第 5.2 节）。Dispatcher、TeamLead 只能追加说明（TaskBrief、WorkOrder），不能替代原文。
- TaskBrief、WorkOrder、ChangeOrder 都有 `constraints_verbatim` 字段，逐字摘录原文里的约束。运行时校验每条摘录（去掉首尾空白后）确实是请求原文、修改原文或用户回答原文的子串，不是就拒绝这条消息。这条规则把"不许改写"变成了程序能检查的约束。

## 5. 请求、任务与团队

### 5.1 标识

| 对象 | 格式 |
| --- | --- |
| 请求 / 任务 / 团队 | `req_` / `tsk_` / `team_` + ULID |
| 事件 / 成果 / 工具操作 | `evt_` / `art_` / `op_` + ULID |
| 变更 / 提交 / 经验报告 | `chg_` / `sub_` / `rep_` + ULID |
| 问题 / 模型调用 | `q_` / `call_` + ULID |
| 计划节点 | Dispatcher 自定的 `node_id`（小写字母、数字、连字符），同一请求内唯一 |
| 记忆 | 见 03 |

### 5.2 版本与代次

| 字段 | 所在 | 含义 | 何时变化 |
| --- | --- | --- | --- |
| requirements_rev | 请求 | 需求版本 | 每次 AMEND +1 |
| requirements_rev | 任务 | 这个任务应当执行的版本 | Dispatcher 或审核返工对它发 ChangeOrder |
| applied_rev | 任务 | Worker 已确认执行的版本 | Worker 调用 `ack_change` |
| plan_rev | 请求 | 计划版本 | Dispatcher 提交新计划 |
| state_version | 每个可变行 | 乐观锁 | 每次写入 +1，写入必须带预期值 |
| dispatcher_epoch | 请求 | Dispatcher 实例代次 | Dispatcher 启动或恢复 |
| execution_epoch | 团队 | TeamLead / Worker 实例代次 | 团队启动或恢复 |
| review_round | 任务 | 审核轮次 | 每次送审 +1 |

"切换中"指任务的 requirements_rev 大于 applied_rev，界面显示为"目标版本 3，执行版本 2，切换中"。

### 5.3 请求状态机

```text
RECEIVED → QUEUED → PLANNING → RUNNING → VERIFYING → DELIVERING → DELIVERED
                       ↕           ↕           ↕
               WAITING_INPUT（等用户回答或追加预算；回答后回到原状态）
任意非终态 → FAILED | CANCELLED | SUPERSEDED
VERIFYING / DELIVERING 收到 AMEND → RUNNING（未确认的交付包作废）
```

| 状态 | 含义 |
| --- | --- |
| RECEIVED | 已持久化，回执已返回给提交方 |
| QUEUED | 等 Dispatcher 名额 |
| PLANNING | Dispatcher 首次规划 |
| RUNNING | 计划执行中 |
| WAITING_INPUT | 等用户回答问题或追加预算 |
| VERIFYING | 必需任务全部验收，Dispatcher 做最终检查、写交付清单 |
| DELIVERING | 交付包已写入，等回执 |
| DELIVERED | 回执已确认（ADR-026） |

交付状态 `delivery_status`（NONE / STORED / CONFIRMED）和清理状态 `cleanup_status`（NONE / PENDING / RUNNING / DONE / FAILED）单独记录。清理失败不改变 DELIVERED。

### 5.4 任务状态机

```text
PENDING →（依赖满足）READY →（团队启动）RUNNING
RUNNING →（TeamLead 转交，未配置审核）SUBMITTED
RUNNING →（TeamLead 转交，配置了审核）REVIEWING
REVIEWING → pass → SUBMITTED
REVIEWING → changes_requested 且未到上限 → RUNNING（返工）
REVIEWING → 到达轮次上限 → BLOCKED（运行时直接问用户：再给几轮 / 带问题验收 / 取消）
REVIEWING → inconclusive → BLOCKED（唤醒 Dispatcher）
BLOCKED → 用户选"再给几轮" → RUNNING；"带问题验收" → SUBMITTED（标记 accepted_with_issues）；"取消" → CANCELLED
BLOCKED →（Dispatcher 处理 inconclusive 等情况）RUNNING | CANCELLED，或 ask_user
SUBMITTED →（accept_task）ACCEPTED
SUBMITTED →（change_task，kind=rework）RUNNING
任意未结束状态 → FAILED | CANCELLED | SUPERSEDED；未选中的可选节点 → SKIPPED
```

带问题验收的任务，Dispatcher 验收时必须把未解决的审核问题写进交付清单的 limitations。审核结论"不通过"只有用户能豁免，Dispatcher 不能自行放行。

### 5.5 团队资源状态

`STARTING → ACTIVE → DRAINING → STOPPED → CLEANED`，清理失败为 `CLEANUP_FAILED`（可重试）。

- 任务 ACCEPTED 且经验报告写完后：团队 DRAINING → 进程全部结束 → STOPPED。验收时成果已复制到成果区；工作区保留到请求清理。
- 任务 CANCELLED、SUPERSEDED、FAILED 时同样 DRAINING → STOPPED。
- 已 STOPPED 的团队不再重启；需要返工时新建团队，以原成果为输入。

### 5.6 后续消息路由

| 消息 | 处理 |
| --- | --- |
| NEW | 新建请求。idempotency_key 相同且内容哈希相同 → 返回原 request_id（已清理的请求查 receipts，返回原回执）；哈希不同 → 拒绝（409） |
| AMEND | 写入新原文（rev+1），请求 requirements_rev+1，暂停该请求的所有活动团队，唤醒 Dispatcher |
| REPLACE | 原请求 → SUPERSEDED（取消操作、清理），新建请求并记录 replaces_request_id |
| ANSWER | 写入答案，唤醒提问链的下一级（02 第 6 节） |
| CANCEL | 请求 → CANCELLED，停止团队，执行清理 |
| QUERY | 只读，直接从数据库返回，不唤醒任何 Agent |
| 对已结束请求的 AMEND | 拒绝，提示改用 NEW 并带 parent_request_id |

### 5.7 中途改方向

1. Root 收到 AMEND：写入原文，请求 requirements_rev+1，所有活动团队置 `paused_for_change = 1`。Worker 在当前工具调用结束后暂停；正在运行的操作默认跑完，Dispatcher 或 TeamLead 可以显式取消。
2. 唤醒 Dispatcher。它对受影响的任务发 ChangeOrder（`change_task`）或取消（`cancel_task`）；需要增删节点时提交新计划。**本次唤醒结束时，没有被处理的暂停任务自动恢复**（视为不受影响）。
3. TeamLead 收到 ChangeOrder，结合 Worker 进展，写出 Worker 能直接执行的 ChangeOrder（`issue_change`）：哪些已做的保留、哪些撤销、接下来做什么。
4. Worker 先 `ack_change`（applied_rev = 新版本），再按新要求继续。
5. 运行时在 Worker 每次工具调用前检查：未暂停，且 applied_rev 等于任务 requirements_rev；否则拒绝并提示等待。
6. Submission 的 requirements_rev 低于任务当前版本时，存为历史，不进入验收。

### 5.8 一致性规则

- 状态变更与事件写在同一个事务里；提交后再由内存事件总线分发。
- 所有更新带 `WHERE state_version = ?`；更新失败视为过期，重新读取后再决定。
- Agent 的每个管理工具调用都携带 request_id 和当前代次（dispatcher_epoch 或 execution_epoch），代次不符直接拒绝。
- 每个管理工具调用生成 command_id（Agent 实例 ID + 模型返回的 tool_call_id）；`events` 表对 command_id 建唯一索引，重放不会重复生效。
- 不在事务中等待模型、工具或网络。

### 5.9 崩溃恢复

wlsd 启动时：

1. 读出所有非终态请求。
2. 每个团队：确认 cgroup 里没有残留进程（有就杀掉）；状态为 RUNNING 的操作改为 UNKNOWN。
3. dispatcher_epoch、execution_epoch 各 +1，旧代次的迟到结果一律拒绝。
4. Dispatcher、TeamLead 以快照式唤醒恢复；Worker 从 `transcripts/<team_id>.jsonl` 恢复：前缀 + 压缩摘要 + 一条通知"服务重启，以下操作结果未知：…，请先核对再继续"。
5. 副作用类别为 external 的 UNKNOWN 操作不自动重做，由 Worker 先核对（S1 的 Worker 工具没有 external 类，S2 起适用）。

### 5.10 额度与排队（ADR-027）

| 额度 | 默认 |
| --- | --- |
| 同时活跃 Dispatcher | 4 |
| 同时活跃 Worker | 8（有审核待做时为审核团队保留 1 个） |
| 每请求团队数 | 4 |
| 每端点并发模型调用 | 8 |
| 同时运行的工具操作 | 16 |
| Worker 每个 WorkOrder 版本最多工具调用 | 200 |
| Dispatcher / TeamLead 单次唤醒最多工具调用 | 12 |
| 每请求预算 | token 上限、金额上限、墙钟时间上限（必须配置，否则拒绝调用真实模型） |

排队先进先出。预算用到 80% 唤醒 Dispatcher；用尽时请求进入 WAITING_INPUT，问用户是否追加，不换模型、不降低验收标准。等待（提问、暂停、排队）不占模型调用名额。

## 6. 计划与工作流（ADR-012）

### 6.1 计划

Dispatcher 用 `submit_plan` 提交 Plan。节点有两种：

- `team_task`：本请求建一个团队，带 TaskBrief；可以配置 review（审核能力 + 最大轮次）。
- `capability_call`：调用另一个功能的能力（经对方 Root），带结构化输入。

运行时校验：无环；模板和能力存在；节点数超出额度的排队；TaskBrief 合规（含逐字摘录检查）。校验失败把错误回给 Dispatcher。简单请求可以只有一个节点，不强制拆解。

### 6.2 调度与汇合

- 节点的所有依赖都 ACCEPTED（非必需依赖也可以是 SKIPPED 或 FAILED）时变为 READY，按额度启动团队。
- 汇合规则只有一种：所有必需依赖已验收。需要别的规则时，由 Dispatcher 改计划来表达。
- 必需节点 FAILED 时唤醒 Dispatcher，由它改计划、问用户或让请求失败。

### 6.3 审核返工环（S2）

配置了 review 的节点：

1. TeamLead 转交提交后，运行时把工作区成果打包成不可变的候选成果（candidate），review_round+1，以 ReviewRequest 调用审核能力。
2. 审核功能的 Root 用模板化 Dispatcher（6.4）处理，返回 ReviewVerdict。
3. pass → 任务 SUBMITTED，等 Dispatcher 验收（Dispatcher 能看到审核结论）。
4. changes_requested 且未到上限 → 运行时把 findings 原文作为 `kind = rework` 的 ChangeOrder 交给本团队的 TeamLead，**不唤醒 Dispatcher**；TeamLead 翻译给 Worker。
5. 到达 max_rounds → 任务 BLOCKED，运行时直接问用户（再给几轮 / 带问题验收 / 取消），不经 Dispatcher；inconclusive → 任务 BLOCKED，唤醒 Dispatcher。
6. 只认绑定当前 candidate 和当前 requirements_rev 的审核结论；旧结论不能放行新候选。

### 6.4 模板化 Dispatcher（ADR-011）

功能模板里声明为 `dispatch: template` 的能力，Root 收到调用后不启动模型规划，而是：

1. 用能力的 `brief_template` 把结构化输入填成 TaskBrief；
2. 按能力指定的团队模板建一个团队；
3. 团队最终 Submission 里的结果必须通过能力的 `output_schema` 校验，通过即视为验收，自动交付给调用方，然后清理。

调用方看到的是一个关联请求（`origin = capability_call`）。

## 7. 上下文编排与缓存（ADR-010）

### 7.1 布局

每个 Agent 实例的上下文按以下逻辑顺序拼装，由各适配器编码成供应商的原生格式：

| 段 | 内容 | 稳定性 |
| --- | --- | --- |
| ① tools | 角色工具定义，按名称排序；S4 起 MCP 工具在实例创建时按名称追加 | 同功能同角色，跨请求不变 |
| ② system | 系统通则（prompts/common.md）→ 角色规则（prompts/<role>.md）→ 功能补充（functions/<id>/prompts/<role>.md）→ 环境卡片（Worker）→ 常用 Skill 索引 → 生效规则（记忆，S3）→ 输出格式要求 | 同上 |
| ③ project | 项目资料快照（可选） | 同项目不变 |
| ④ contract | 请求原文与全部修改原文、验收标准、TaskBrief、WorkOrder | 本实例私有，从这里开始分叉 |
| ⑤ messages | 对话（Worker 只追加）或快照（Dispatcher / TeamLead） | 变化 |

规则：

- 实例生命周期内 ①② 不变（压缩也不改）。期间新增的 Skill、规则只在 ⑤ 里通告，新实例创建时才进入 ②。
- 回忆到的记忆和 Skill 全文，只能以工具结果或附加消息的形式进入 ⑤。
- 随机 ID、时间戳、真实路径不进 ①②③；工作目录统一叫 /work、/input。
- ② 中各段的内容和顺序由代码固定拼装，不由模型生成。

### 7.2 两种上下文模式

- **Worker：追加式。** 上下文用到窗口的 60% 时，用同一模型生成"进展摘要"替换较早的消息，①–④ 不动。摘要必须包含：已完成步骤、改动的文件、关键决定、遇到的错误及解决办法、未完成事项。所有生效 ChangeOrder 和实例创建后追加的需求修改原文不参与摘要，原样保留在消息区。
- **Dispatcher、TeamLead：快照式。** 每次唤醒的上下文 = ①–④ + 一条运行时生成的快照消息（状态、计划、团队、待处理事件、最近 20 条决策日志、预算）。唤醒内部可以多步调用工具（追加式），唤醒结束即丢弃。决策日志来自每次管理工具调用必填的 `rationale`。

### 7.3 配置冻结（ADR-006）

Agent 实例创建时解析 EffectiveModelConfig（8.3）并冻结，配置文件的改动只影响之后新建的实例。原因：各家缓存都对模型参数敏感，思考或推理强度一变，缓存就失效。

### 7.4 缓存标记

- Anthropic：最多 4 个缓存断点，其中自动缓存占 1 个。v1 在 ② 末、③ 末（有项目快照时）、④ 末各放 1 个显式断点，再用顶层自动缓存覆盖 ⑤。
- OpenAI 兼容端点：依赖服务端的自动前缀缓存；可选传 `prompt_cache_key`（功能 + 角色 + 模板版本的哈希）。
- 缓存时长先用各家默认值；共享前缀是否值得用更长时长，S5 根据实测决定。
- 各模型有最小可缓存长度（记在能力表的 cache_min_tokens），前缀短于它时不会缓存，属正常现象。

### 7.5 计量

每次模型调用写入 `llm_calls`：输入、缓存读、缓存写、输出 token（供应商没给就记 NULL，不记 0）、延迟、费用、`prefix_sha256`（①② 的指纹）。缓存读取占比 = Σ缓存读 ÷ Σ全部输入，按功能和角色汇总。同功能、同角色、同模型的 `prefix_sha256` 必须完全相同（用例 V3-025）。

## 8. 模型适配

### 8.1 接口（C++ 草案）

```cpp
namespace wls::model {

struct ReasoningSetting {                 // 语义见 8.2
  enum class Mode { Inherit, ProviderDefault, Off, Effort, Budget } mode = Mode::Inherit;
  std::string level;                      // Effort：low / medium / high / max
  int budget_tokens = 0;                  // Budget
};

struct ModelRequest {
  std::string model;
  ReasoningSetting reasoning;
  std::vector<ToolDef> tools;             // ①
  std::vector<SystemBlock> system;        // ②③，带缓存断点标记
  std::vector<Message> messages;          // ④⑤
  int max_output_tokens = 0;
};

struct UsageRecord {                      // 缺失即 nullopt，不填 0
  std::optional<int64_t> input, cache_read, cache_write, output, cost_micro_usd;
};

class ModelAdapter {
 public:
  virtual ~ModelAdapter() = default;
  virtual CapabilityProfile capabilities(std::string_view model) const = 0;
  virtual Result<void> validate(const EffectiveModelConfig& cfg) const = 0;
  virtual asio::awaitable<Result<ModelResponse>> complete(ModelRequest req, StreamSink* sink) = 0;
};

}  // namespace wls::model
```

适配器：`anthropic_messages`、`openai_chat_compat`（S1-13 先做所选供应商对应的一种，另一种在 S4），以及测试用的 `fake`（按脚本返回）。

### 8.2 思考设置语义

| 写法 | 含义 |
| --- | --- |
| 字段缺失或 `null` | 继承 |
| `{mode: provider_default}` | 不发送任何思考参数，用供应商默认 |
| `{mode: off}` | 明确关闭；模型不支持关闭则启动时报错 |
| `{mode: effort, level: high}` | 按能力表映射成供应商参数；不支持该档位则报错，不静默降级 |
| `{mode: budget, tokens: 8000}` | 指定思考 token 预算；不支持则报错 |

在 YAML 里 `off` 要加引号写成 `mode: "off"`，否则部分解析器会把它当成布尔值 false。

### 8.3 继承解析（ADR-005）

```text
resolve(role, field):                    # field ∈ {model_ref, reasoning}
  v = 功能模板.roles[role][field]    非 null → 返回，来源 roles.<role>
  v = 功能模板.root[field]           非 null → 返回，来源 root
  v = system.defaults[field]         非 null → 返回，来源 system.defaults
  报错：没有可用模型
```

Dispatcher、TeamLead、Worker 只看自己的覆盖值，然后直接看 Root，绝不取其他角色的覆盖值。`wls config explain <function> <role>` 输出解析结果和每个字段的来源。

### 8.4 能力表

每个模型条目登记：streaming、tool_calling、parallel_tool_calls、structured_output、reasoning_modes（支持的档位）、context_window、max_output_tokens、cache_mode（none / implicit_prefix / explicit_breakpoints）、cache_min_tokens、usage_fields、source_url、verified_at。不确定的写 `unknown`。Agent 需要而模型不支持的能力（如 tool_calling）会使该 Agent 拒绝启动。

### 8.5 错误与重试

429、5xx、网络中断：指数退避加抖动，最多 5 次（模型调用没有副作用，可以安全重试）。400 类错误不重试，记 `AGENT_ERROR` 并上报。流式输出中断时整次重试。

## 9. 工具、权限与沙箱

### 9.1 工具注册

每个工具登记：`tool_id`、`version`、可见角色、`input_schema`、`output_schema`、`side_effect`（none / workspace / external）、默认超时、能否取消。工具定义按名称排序进入 ①。

### 9.2 各角色工具（参数详见 02）

| 角色 | 工具 |
| --- | --- |
| Dispatcher | submit_plan、change_task、accept_task、cancel_task、answer_team、ask_user、read_artifact、deliver、fail_request、recall、load_memory |
| TeamLead | issue_work_order、issue_change、answer_worker、escalate、read_workspace、forward_submission、return_for_rework、write_experience_report、recall、load_memory |
| Worker | fs_list、fs_read、fs_search、fs_write、fs_patch、run、op_status、op_output、op_cancel、ask、progress、ack_change、submit、note、recall、load_memory |

S3 之前，recall 和 load_memory 返回"记忆系统未启用"。

### 9.3 每次调用的检查顺序

角色是否有权 → 代次是否当前 →（Worker）是否暂停、applied_rev 是否等于任务 requirements_rev → 路径是否在允许范围内 → 网络是否允许 → 预算是否充足。任何一项不通过，都返回结构化错误给模型，不执行。

### 9.4 Worker 文件工具

- 路径一律用逻辑路径：/work（读写）、/input（只读）。
- 由 wlsd 直接执行，用 `openat2`（`RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS`）防止路径穿越和符号链接逃逸。
- `fs_read` 按行分页（offset / limit），单次最多 64 KB，返回 truncated 标志。
- `fs_write` 覆盖已存在的文件时必须带 `expected_sha256`，不符则拒绝。
- `fs_patch`：旧文本必须在文件中唯一出现，替换为新文本。
- `fs_search` 在团队沙箱里调用 ripgrep（`--json`），最多返回 200 条。

### 9.5 run 与操作生命周期

- 输入：`cmd`（shell 字符串）或 `argv`、`cwd`（/work 下）、`timeout_s`（默认 120，最大 600）、`background`。
- 前台执行：等到结束或超时，返回 exit_code、stdout 尾部、stderr 尾部（合计最多 16 KB，带截断标记）和 op_id。
- 后台执行：立即返回 op_id；`op_status` 查状态，`op_output` 分页读输出（输出写在团队的 ops 目录，不在 /work）。
- `op_cancel`：对整个进程组发 SIGTERM，5 秒后 SIGKILL；有 cgroup 时用 `cgroup.kill`。
- 每个操作记入 `ops` 表。非零退出时生成 `error_signature`：工具名 + 归一化后的第一条错误行（去掉路径、数字、哈希），供记忆的报错触发使用（S3）。

### 9.6 沙箱（ADR-024）

bubblewrap 参数（Worker 看到的文件系统）：

```text
--ro-bind /usr /usr  --symlink usr/bin /bin  --symlink usr/lib /lib  --symlink usr/lib64 /lib64
--ro-bind /etc/<白名单项> /etc/<白名单项>   （见下）
--proc /proc  --dev /dev  --tmpfs /tmp  --tmpfs /home/agent
--bind <团队工作区>/work /work  --ro-bind <请求输入区> /input
--unshare-pid --unshare-ipc --unshare-uts  --unshare-net（network: none 时）
--die-with-parent --new-session --chdir /work
```

- /etc 只读挂载白名单：alternatives、ssl、ld.so.cache、passwd、group、localtime；network 为 host 时再加 resolv.conf、hosts。其余 /etc 不挂载。
- 不挂载用户主目录；功能模板可以声明额外的只读目录（`sandbox.extra_ro_binds`）。
- 子进程用显式环境变量启动（PATH、HOME=/home/agent、LANG=C.UTF-8、TERM=dumb，加上功能模板声明的变量），**绝不继承 wlsd 的环境**——API Key 就在 wlsd 的环境里。
- 网络：S1 只有 `none`（默认）和 `host`（功能模板显式声明，启动时警告）；S2 实现域名白名单（评估复用开源的 sandbox-runtime，或自建代理）。
- Ubuntu 24.04 默认限制非特权 user namespace，需要给 bwrap 加一条 AppArmor 配置；`wls doctor` 负责检测并给出命令。

### 9.7 cgroup

- wlsd 作为 systemd 用户服务运行，设置 `Delegate=yes` 和 `DelegateSubgroup=daemon`（Ubuntu 24.04 自带的 systemd 255 支持）。wlsd 自身在 `<服务>/daemon`，各团队在 `<服务>/teams/<team_id>`。
- 在 teams 父组的 `cgroup.subtree_control` 启用 memory、pids、cpu；每个团队设置 `memory.max`、`pids.max`。
- 子进程在 fork 之后、exec 之前写入团队组的 `cgroup.procs`（或用 clone3 + `CLONE_INTO_CGROUP`）。
- 结束团队：写 `cgroup.kill`，等 `cgroup.events` 里 `populated=0`。
- 环境不支持委派时退化为进程组 + 超时，`wls doctor` 给出提示。

### 9.8 环境卡片（ADR-028）

功能模板的 env.yaml 列出工具：名称、检查命令（如 `git --version`）、一句话用途、调用示例。wlsd 加载模板时在沙箱里执行一遍检查命令，把结果渲染成 Markdown 卡片放进 Worker 的 ②。卡片按"模板版本 + 检查结果哈希"缓存——基础环境不变，卡片就不变，前缀缓存也不受影响。

## 10. 交付与清理

### 10.1 交付包

目录 `$WLS_DATA/deliveries/<request_id>/`：

- `manifest.json`：delivery_manifest.schema.json；哈希、大小、用量由运行时填写
- `README.md`：Dispatcher 写的说明
- `request.md`：请求原文与全部修改原文
- `deliverables/`：成果文件
- `experience/`：各团队的经验报告

`deliver` 的校验：所有 deliverables 都在成果区且哈希匹配；必需任务全部 ACCEPTED；配置了审核的必需任务，审核结论是绑定当前版本的 pass，或者用户已选择"带问题验收"（此时 limitations 必须列出未解决的审核问题）。

### 10.2 回执（ADR-026）

- CLI 发起：交付包写入后立即 CONFIRMED，`wls watch` 和 `wls ls` 中提示（可选桌面通知）。
- API / MCP 发起：调用方成功取回交付包时 CONFIRMED；取回失败就不清理。

### 10.3 清运行态（ADR-015）

请求到达 DELIVERED（或 FAILED / CANCELLED / SUPERSEDED）后：

1. 停止接受该请求的新操作，取消在途操作，杀掉各团队 cgroup 并确认为空。
2. 释放所有 Agent 实例。
3. 汇总：`memory_loads` 结合经验报告生成 `memory_feedback`（S3）；写入 `receipts`（含用量摘要），保留 30 天，过期由每日任务删除。
4. 删除：工作区、输入区副本、对话记录、追踪文件、op 输出；数据库中该请求的 events、tasks、task_deps、change_orders、teams、plans、questions、notes、ops、llm_calls、artifacts、request_texts、requests 各行（S3 起还有 memory_loads）。
5. 清理失败：`cleanup_status = FAILED`，按退避重试；也可以手动 `wls cleanup <req> --retry`。

失败、取消的请求同样清理，交付包里放"失败报告"：已验收的成果、失败原因、未决的副作用。

| 数据 | 处理 |
| --- | --- |
| 交付包 | 保留，直到用户删除（`wls deliveries prune --older-than 90d`） |
| 经验报告 | 保留（在交付包内；S3 起同时写入记忆） |
| 记忆仓库与 memory_feedback | 保留 |
| 回执 | 保留 30 天 |
| 其余请求数据 | 删除 |

数据库每周 VACUUM 一次回收空间。回执过期后，同一个 idempotency_key 再提交会被当作新请求。

## 13. 配置

- 位置：配置在 `~/.config/wls/`，数据在 `~/.local/share/wls/`（即 `$WLS_DATA`），套接字在 `$XDG_RUNTIME_DIR/wls.sock`。
- `system.yaml`：模型条目与能力表、系统默认、额度、沙箱、清理、记忆（样例：config/examples/system.yaml）。
- `functions/<id>/`：`function.yaml`（含常用 Skill 名单 pinned_skills）、`env.yaml`、`prompts/`（各角色的补充提示词）、`briefs/`（模板化能力的 brief 模板）。**新增一个功能 = 新增一个目录，不改代码。**
- 校验（`wls config check`，wlsd 启动时也执行）：Schema 合法；引用的模型、模板、能力、工具都存在；每个角色都能解析出模型；思考档位被模型支持；`dispatch: template` 的能力必须有 brief_template 和 output_schema。

## 17. 路线图（ADR-019）

| 切片 | 内容 | 演示标准 | 验收 |
| --- | --- | --- | --- |
| S0 | 本规格包 | 可以按文档开工 | — |

**S2 的代码工作区说明：** 代码类功能可以声明 `workspace: git_worktree`。wlsd 对用户仓库执行 `git worktree add`（每个团队一个分支）并挂载为 /work；交付物是分支名和补丁；清理时 `git worktree remove`，分支留在用户仓库里。同一仓库的多个团队各用各的分支，合并作为单独的集成任务。

## 18. 主要风险与对策

| 风险 | 对策 |
| --- | --- |
| 多层转述丢信息 | 原始需求直达、逐字摘录校验、HOP-01 约束保真用例 |
| 四层结构不如单 Agent | 从 S2 起每个切片都和单 Agent 对照；必要时调整唤醒表或合并职责 |
| 费用失控 | 每请求预算必填、80% 告警、用尽即停 |
| 沙箱逃逸或误删用户文件 | 不挂载主目录、openat2、显式环境变量、清理只按团队资源清单 |
| 缓存命中低 | 固定布局、配置冻结、前缀指纹测试、S5 实测调整缓存时长 |
| 记忆污染 | 记忆作为参考资料注入消息区；规则和含脚本的 Skill 需批准；Git 可回滚 |
| AI 协作写出的代码不一致 | 规格唯一权威、任务卡、交叉审查、ADR 流程（06） |
