# 角色行为规格 v0.4

本文规定四个角色**什么时候调用模型、看到什么、能调用哪些工具、必须产出什么**。系统提示词由 `prompts/common.md`（所有角色共用）和 `prompts/<role>.md` 组成（以那里的文字为准），功能模板可以在 `functions/<id>/prompts/<role>.md` 里追加。消息字段以 `schemas/` 为准。

---

## 1. 共同规则

1. **原文优先。** 请求原文和修改原文是最高依据；任何角色的转述只能补充，不能替代或删减其中的约束。TaskBrief、WorkOrder、ChangeOrder 的 `constraints_verbatim` 必须逐字摘录原文（请求原文、修改原文或用户的回答），运行时会校验。
2. **结构化输出。** 所有交接都通过工具参数传递，必须符合对应的 Schema；不合格会被退回重试（最多 2 次）。
3. **写理由。** Dispatcher 和 TeamLead 的每个会改变状态的工具调用都要填 `rationale`（一句话），自动进入决策日志。
4. **不编造。** 没有执行过的检查写 `not_run`；不确定的写不确定。
5. **工具报错是信息。** 工具返回的结构化错误（如"版本已过期""已暂停等待变更""路径不允许"）要按提示处理，不要原样重试。
6. **一次唤醒只处理待处理事件。** Dispatcher 和 TeamLead 处理完事件就结束本轮（不再调用工具），不做与事件无关的事。

---

## 2. Root（纯代码，不调用模型）

| 职责 | 做法 |
| --- | --- |
| 接单 | 校验格式与大小 → idempotency_key 去重 → 持久化请求和原文 → 返回 request_id 与 RECEIVED → 有名额就进入 PLANNING，否则 QUEUED |
| 路由后续消息 | 按主规格 5.6 处理 AMEND、REPLACE、ANSWER、CANCEL、QUERY |
| 对外进度 | 把事件渲染成一行人类可读的进度（`wls watch`、SSE） |
| 交付 | 发送交付包，按 ADR-026 确认回执，触发清理 |
| 能力调用 | 收到 `capability_call`：能力是 `dispatch: template` 时走模板化 Dispatcher（主规格 6.4），否则像普通请求一样建 Dispatcher |

## 3. Dispatcher（每个请求一个）

### 3.1 何时调用模型

开始规划；需求被修改；团队上报问题；用户回答了它的提问；收到 TeamLead 转交的提交（未配置审核时）或审核通过的提交；审核结论不明；任务失败或受阻；全部必需任务已验收；预算用到 80%。

### 3.2 看到什么（快照式，每次唤醒重建）

① 工具 ② 系统提示（prompts/common.md + prompts/dispatcher.md + 功能补充）③ 项目快照（可选）④ 任务契约：全部原文 + 验收标准 ⑤ 一条快照消息（格式见第 8 节）。唤醒内部的多步工具调用追加在快照之后，唤醒结束即丢弃。

### 3.3 工具

| 工具 | 参数 | 作用 | 运行时校验 |
| --- | --- | --- | --- |
| submit_plan | plan（Plan）、rationale | 提交或替换计划，plan_rev+1 | Schema；无环；模板 / 能力存在；逐字摘录；节点数（超出的排队） |
| change_task | task_id、change_order（ChangeOrder，from_role=dispatcher）、rationale | 对任务发变更或返工，任务 requirements_rev+1 | 任务未结束；逐字摘录 |
| accept_task | task_id、notes、rationale | 验收 SUBMITTED 的任务 | 状态正确；配置了审核的任务必须有绑定当前版本的 pass，或用户已选"带问题验收" |
| cancel_task | task_id、rationale | 取消任务并停止团队 | — |
| answer_team | question_id、answer、rationale | 回答团队上报的问题 | 问题当前由 Dispatcher 持有 |
| ask_user | question（Question）、rationale | 向用户提问，请求进入 WAITING_INPUT | 转发下级问题时原文不变 |
| read_artifact | artifact_id、offset、limit | 只读查看本请求的成果 | 属于本请求 |
| deliver | manifest（DeliveryManifest）、readme_markdown、rationale | 提交交付清单和说明 | 主规格 10.1 |
| fail_request | reason、rationale | 让请求失败并生成失败报告 | — |
| recall、load_memory | query / memory_id | 回忆记忆（S3） | — |

### 3.4 行为要点

- **规划：** 简单请求只给一个节点。只有确实能并行、或需要不同能力时才拆分。每个 TaskBrief 写清目标、范围、不做什么、验收标准、输入、预期产出，并把与该任务相关的原文约束逐字摘入 `constraints_verbatim`。
- **处理修改：** 读新的原文，判断哪些任务受影响。受影响的发 ChangeOrder（停止 / 保留 / 新增 / 验收标准变化）；作废的取消；需要新节点的改计划。没处理的暂停任务会在本轮结束时自动恢复。
- **答疑：** 能从任务契约判断的直接答；属于用户偏好或信息缺失的，用 ask_user 原文转给用户。
- **验收：** 对照验收标准和证据逐条判断。不合格用 change_task（kind=rework）写清具体问题。审核"不通过"只有用户能豁免：到达轮次上限时由运行时直接问用户；用户选了"带问题验收"的任务，验收时必须把未解决的审核问题写进交付清单的 limitations。
- **交付：** 必需任务全部验收后立即交付，不追求额外完美；未解决的问题写进 limitations。

### 3.5 限制

单次唤醒最多 12 次工具调用。唤醒结束时若仍有必须回应的事件未处理（如问题未答、提交未决定），运行时再唤醒一次并提示；仍未处理则在 `wls show` 中标记警告，等用户介入。

## 4. TeamLead（每个团队一个）

### 4.1 何时调用模型

团队启动；收到 Dispatcher 的 ChangeOrder；Worker 提问；Worker 提交；上级回答了它的上报；运行时转来审核返工；停滞告警；任务验收后写经验报告。

### 4.2 看到什么（快照式）

① ② 同 Dispatcher 的结构（prompts/team_lead.md）④ 任务契约：全部原文、验收标准、TaskBrief、自己已发出的 WorkOrder 与 ChangeOrder ⑤ 团队快照（第 8 节）。可用 read_workspace 只读查看工作区。

### 4.3 工具

| 工具 | 参数 | 作用 | 运行时校验 |
| --- | --- | --- | --- |
| issue_work_order | work_order（WorkOrder） | 团队启动时下达，Worker 开始工作 | `constraints_verbatim` 必须包含 TaskBrief 的全部条目 |
| issue_change | change_order（ChangeOrder，from_role=team_lead） | 把上级变更翻译成 Worker 能直接执行的指令 | 必须带 parent_change_id；`constraints_verbatim` 和 `findings` 必须覆盖上级 ChangeOrder 的全部条目 |
| answer_worker | question_id、answer | 回答 Worker 的问题 | 问题由 TeamLead 持有 |
| escalate | question_id、note | 把问题原文上报 Dispatcher，可附自己的判断 | 原文不变 |
| read_workspace | action（list / read / search）、path、offset、limit、pattern | 只读查看团队工作区 | 只读；路径限制 |
| forward_submission | submission_id、check（passed、notes、criteria_results） | 检查合格后转交（或带着问题转交） | — |
| return_for_rework | submission_id、feedback（具体问题列表） | 团队内退回返工 | 团队内最多 3 轮 |
| write_experience_report | report（ExperienceReport） | 任务验收后写经验报告 | Schema |
| recall、load_memory | query / memory_id | 回忆记忆（S3） | — |

### 4.4 行为要点

- **下达 WorkOrder：** 写清做法、步骤和每步的检查方式、完成定义；把 TaskBrief 的全部约束原样带上。不要替 Worker 写代码，但要把容易出错的地方提前点明。
- **翻译变更：** 先看 Worker 当前进展（快照、文件），再写 ChangeOrder：已经做了的哪些保留、哪些要撤销、下一步做什么。不能只转发原文，也不能漏掉原文中的任何约束或审核问题。
- **检查提交：** 对照验收标准逐条核对，必要时读文件。合格就 forward_submission；不合格 return_for_rework，写清具体问题和期望结果。团队内返工 3 轮仍不合格，就带着问题转交并在 notes 中说明。
- **经验报告：** 结合 Worker 的 note 和运行时的轨迹摘要写。没有新经验就设 `no_new_experience: true`，不要凑数。对 Worker 声明用过的每条记忆给出评价（worked / failed / irrelevant）和证据。

### 4.5 限制

单次唤醒最多 12 次工具调用；未处理事件的处理方式同 Dispatcher。

## 5. Worker（每个团队一个）

### 5.1 工作循环

```text
loop:
  若 paused_for_change：阻塞，直到收到新的 ChangeOrder 或被恢复
  若在等待问题答案：阻塞，直到收到答案
  调用模型（追加式上下文）
  有工具调用 → 按返回顺序逐个执行（每个都过第 9.3 节检查），结果追加到上下文
  只有文字没有工具调用 → 追加提示"请调用工具继续，或 submit / ask"；连续 2 次则触发停滞告警
  调用了 submit → 等 TeamLead 的结论：退回返工则带着反馈继续；转交后等待验收
  工具调用数达到上限 → 停滞告警并等待
  上下文用到窗口 60% → 压缩（主规格 7.2）
```

### 5.2 看到什么（追加式）

① 工具 ② prompts/worker.md + 功能补充 + **环境卡片** + 常用 Skill 索引 ③ 项目快照（可选）④ 全部原文、验收标准、TaskBrief、WorkOrder ⑤ 对话。之后到达的修改原文和 ChangeOrder 都以附加消息进入 ⑤：运行时先追加"【需求修改原文 rev N】…"，再追加 TeamLead 的 ChangeOrder。

### 5.3 工具

| 工具 | 参数 | 作用 |
| --- | --- | --- |
| fs_list | path、depth | 列目录（/work、/input 内） |
| fs_read | path、offset、limit | 按行分页读文件，单次最多 64 KB |
| fs_search | pattern、path、glob | ripgrep 搜索，最多 200 条 |
| fs_write | path、content、expected_sha256 | 新建或覆盖；覆盖已存在的文件必须带 expected_sha256 |
| fs_patch | path、old_text、new_text | 旧文本必须唯一出现，替换为新文本 |
| run | cmd 或 argv、cwd、timeout_s、background | 在沙箱里执行命令（主规格 9.5） |
| op_status、op_output、op_cancel | op_id 等 | 查询、分页读输出、取消 |
| ask | question（text、context、options） | 问 TeamLead，阻塞到有回答 |
| progress | note | 进度说明，显示给用户，不唤醒任何人（每分钟最多 2 条） |
| ack_change | change_id | 确认收到并将执行变更；applied_rev 更新为该变更的版本 |
| submit | submission（Submission） | 提交成果，然后等待结论 |
| note | kind（tool_usage / pitfall / method / fact）、text、evidence | 随手记下值得记住的发现，供经验报告使用 |
| recall、load_memory | query / memory_id | 回忆记忆（S3） |

### 5.4 行为要点

- 按环境卡片直接用工具，不要花时间找工具在哪。
- 每一步用工具实际验证，不假设命令成功。
- 收到 ChangeOrder 先 ack_change，再按新要求做；旧方向的工作立即停止。
- 同一个错误连续 3 次还没解决就 ask，不要死循环。
- submit 时如实填写：做了什么、成果文件、如何验证、每条验收标准的自检结果、已知问题、实际用到的记忆。

### 5.5 限制

每个 WorkOrder 版本最多 200 次工具调用（每次 ChangeOrder 重新计数）；单次 run 最长 600 秒（更长的用 background）。

## 6. 问题上报协议

1. Worker 调用 ask → 问题由 TeamLead 持有，唤醒 TeamLead。
2. TeamLead 能答 → answer_worker；不能答 → escalate（原文不变，可附 note）→ 问题由 Dispatcher 持有，唤醒 Dispatcher。
3. Dispatcher 能答 → answer_team；不能答 → ask_user（原文不变，附自己的 note）→ 请求进入 WAITING_INPUT，用户在 `wls watch` / `wls ls` 中看到问题。
4. 用户用 `wls answer` 回答。
5. **答案原文直接送达最初的提问者**，不经中间层转述；中间层在下一次快照里能看到这条问答，但不会因此被唤醒。
6. 回答只用于澄清。改需求要用 `wls amend`，CLI 会提醒。

## 7. 典型流程

### 7.1 正常请求

```text
用户 submit → Root：RECEIVED → PLANNING → 唤醒 Dispatcher
Dispatcher：submit_plan（1 个节点）→ 运行时：任务 READY → 团队启动 → 唤醒 TeamLead
TeamLead：issue_work_order → Worker 开始循环
Worker：…工具调用… → submit → 唤醒 TeamLead
TeamLead：检查 → forward_submission → 任务 SUBMITTED → 唤醒 Dispatcher
Dispatcher：accept_task → 任务 ACCEPTED → 唤醒 TeamLead 写经验报告 → 团队 STOPPED
运行时：ALL_REQUIRED_ACCEPTED → 唤醒 Dispatcher
Dispatcher：deliver → 交付包写入 → CLI 发起即 DELIVERED → 清运行态
```

### 7.2 中途改方向

```text
用户 amend → Root：写原文 rev 2，请求 requirements_rev=2，所有团队暂停 → 唤醒 Dispatcher
Dispatcher：change_task(n1, ChangeOrder：停止 A，保留 B，新增 C)，任务 requirements_rev=2
          （本轮未处理的暂停任务自动恢复）
运行时：给 Worker 追加"【需求修改原文 rev 2】…"；唤醒 TeamLead
TeamLead：查看进展 → issue_change（parent_change_id 指向上级变更，约束全覆盖）
Worker：ack_change（applied_rev=2）→ 按新要求继续 → submit（requirements_rev=2）
```

### 7.3 审核返工（S2）

```text
TeamLead forward_submission → 任务 REVIEWING → 运行时打包候选成果，review_round=1，调用 review.review_code
审核功能 Root：模板化 Dispatcher 建审核团队 → 返回 ReviewVerdict
  pass → 任务 SUBMITTED → 唤醒 Dispatcher 验收
  changes_requested → 运行时发 ChangeOrder(kind=rework，findings 原文) → 唤醒 TeamLead → issue_change → Worker 修改 → 再次提交 → review_round=2 …
  到达 max_rounds → 任务 BLOCKED → 运行时直接问用户（再给几轮 / 带问题验收 / 取消）
  inconclusive → 任务 BLOCKED → 唤醒 Dispatcher（可重新送审、改需求返工或 ask_user）
```

### 7.4 能力调用（S2）

```text
Dispatcher 计划里有 capability_call 节点（如 docs.summarize）
运行时 → 对方 Root：能力是 dispatch: template → 不规划，直接用 brief_template 建团队
对方团队完成 → 输出通过 output_schema 校验 → 自动交付给调用方节点 → 节点 ACCEPTED（Dispatcher 可在快照中看到结果）→ 对方清理
能力不是 template → 对方建自己的 Dispatcher，按普通请求流程处理，交付后结果回到调用方节点
```

## 8. 快照消息格式

快照由运行时按固定模板生成，放在 ⑤ 开头。

**Dispatcher 快照：**

```text
【系统快照】事件序号 1234
请求 req_01J…｜状态 RUNNING｜需求版本 3｜计划版本 2
预算：token 38%｜金额 $1.20 / $5.00｜时间 12 / 120 分钟
计划节点：
  - n1 [ACCEPTED] 数据清洗（team_01J…）
  - n2 [RUNNING｜目标 3 / 执行 2｜切换中] 报表生成（team_01J…）
  - n3 [PENDING] 汇总（依赖 n1、n2）
本次需要你处理的事件：
  1. REQUIREMENTS_AMENDED rev 3（原文见任务契约）
  2. QUESTION_ESCALATED q_01J…，来自 n2 的 TeamLead
     原文："…"
     TeamLead 附注："…"
最近问答：…
最近决策（新→旧，最多 20 条）：
  - submit_plan rev 2：把报表拆成两个节点，因为数据源不同
```

**TeamLead 快照：**

```text
【团队快照】team_01J…｜任务 n2｜状态 RUNNING｜目标版本 3 / 执行版本 2
Worker 最近进展（最多 5 条）：…
最近操作（最多 10 条）：run "pytest -q" → 退出码 1，错误签名 run:pytest:AssertionError …
改动过的文件：/work/report.py（3 次）、/work/out/summary.csv
Worker 的 note：…
本次需要你处理的事件：…
```

## 9. 错误处理

| 情况 | 处理 |
| --- | --- |
| 模型输出不符合 Schema | 带校验错误重试，最多 2 次；仍失败记 AGENT_ERROR，上报上一级（Worker → TeamLead → Dispatcher → 用户） |
| 模型调用失败（可重试类） | 指数退避最多 5 次，仍失败记 AGENT_ERROR |
| 工具返回"版本过期" | 说明期间有新变更，等待新的 ChangeOrder |
| 工具返回"已暂停" | 等待，不重试 |
| 预算用尽 | 请求 WAITING_INPUT，问用户是否追加，不降级 |
| 唤醒后事件未处理 | 再唤醒一次并提示；仍未处理则标记警告等用户介入 |
