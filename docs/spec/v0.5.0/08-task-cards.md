**目标：** 实现 Windows 的工作区/日志/交付/清理文件边界及受控进程监督，分别验收 W-FS、W-PROC 与相应 W-CLEAN。进程监督本身不提供完整沙箱；任意不可信 `run` 的放行依赖 P5。

**依赖：** P3 已采纳平台矩阵与原生构建基础，现有 workspace/owned capacity/delivery/process evidence/cleanup 契约。文件安全和进程监督可分子卡推进，但共享对象身份和恢复证据必须一致。

**拟修改模块：** `include/wls/workspace.hpp`、`journal.hpp`、`cleanup.hpp`、`sandbox.hpp`、`process_evidence.hpp`，对应新增 Windows 后端；必要的 `src/delivery.cpp`、`src/owned_capacity.cpp`、`src/worker_tools.cpp` 和 Store 证据校验；平台测试与能力报告。旧 POSIX 路径和已发布 SQL 保持原解释，新增事实若需版本升级另立兼容方案。

**设计约束：** 路径授权以受控根 Handle 和每级对象核验为准，拒绝不支持的 Reparse Point、别名与对象类型，检查 SID/ACL/继承及可替换权限；终态字符串路径不代替对象身份。严格处理 UTF-8/UTF-16、ADS/设备/UNC/保留名/尾点空格/大小写/8.3/硬链接及打开共享模式。创建进程用显式 executable、参数、环境、cwd，受控启动屏障、句柄白名单和 Job 子树；终止请求后等待实际退出，避免 PID 重用，不能把 HANDLE 数字跨重启当身份。清理仅用原库存、当前 claim、结算和原退出证据。

**失败反例：** **PLANNED / NOT_RUN**：祖先/目标替换与重解析、父目录允许删除子项、ACL 继承变更、ADS/硬链接别名、锁与 SQLite 连接继承、子进程逃逸或句柄泄漏、Job 终止返回但仍有后代、PID 重用、旧清理 claim/原对象被替换。既有 Linux 回归仅作契约参照。

**测试矩阵：** 原生 ACL/SID/继承与宽松父权限、Unicode/别名/文件类型、并发替换、锁/共享模式、durability 故障范围、Process/Job 后代和取消/等待、泄漏/崩溃/恢复/claim/CAS/终态；Linux 同业务回归、两 umask 与 sanitizer。合成进程记录和真实 OS 退出证明分别记录，未实测掉电不得宣称掉电耐久。

**目标：** 为明确支持的 Windows 档位建立不可信工具的实际文件、进程、令牌和网络限制，完成 W-SBX。必须证明组合机制的效果；机制名称或 Job 管理成功不等于沙箱成立。

**依赖：** P3、P4 的原生环境、Handle/ACL 边界、启动监督及原退出证据；协调者采纳的威胁模型和支持矩阵。真实产品 `run` 另依赖完整安全验收，不借本卡扩大模型/费用授权。

**拟修改模块：** 新 Windows sandbox/能力探测后端、`include/wls/sandbox.hpp`、process evidence、WorkerTools 派发门禁、doctor 与对应 Store 事实版本校验；沙箱/工作区/进程/清理测试。Restricted Token、低完整性、AppContainer、能力 SID、ACL 和网络策略作为待论证组件，不承诺单组件能实现全部边界。

**设计约束：** 最小权限、显式可访问对象与继承句柄，强限制必须在子进程开始不可信代码前成立；考虑宿主/代理服务、命名对象、令牌提升、现有句柄、网络代理与本机通道。网络拒绝覆盖 IPv4/IPv6、DNS、loopback、代理、已存在 socket 及 broker 路径；能力不足明确拒绝，不回落为无限制执行。有限取消、全子树实际退出、UNKNOWN 和原观察保留；既有 Linux 强隔离不降低。

**失败反例：** **PLANNED / NOT_RUN**：写受控根外、读取宿主凭据/控制库、继承高权限句柄、子进程/Job 逃逸、网络直连与代理绕过、低完整性仍可读敏感资料、限制尚未启用时抢跑、恢复/取消误判退出。测试不访问真实秘密或外部生产网络，使用合成文件和本地 canary。

**验收标准：** 支持矩阵内有真正强能力正向和逐通道负向证据；缺能力环境拒绝及原因稳定；效果前门禁、原隔离/网络/退出事实与 Store 结算绑定，失败保留 UNKNOWN/资源。独立安全复核明确威胁模型外与未验证通道，不能宣称对任意宿主或内核漏洞绝对隔离。

**测试矩阵：** Windows 普通非提升用户下文件/令牌/句柄/子树/网络/启动竞争/取消/超时/恢复/清理，多版本能力差异；Linux 原强模式与拒绝路径继续完整运行。每项记录实际 OS 配置、程序身份、首次派发与外部效果，CI 缺强能力不能代替支持环境中的正向测试。

## P6：Linux / Windows 一致性与跨平台证据

**目标：** 在各自原生平台证明共同业务和安全契约一致，并准确记录平台特有事实与不支持范围，完成 W-PARITY。源码可编译或相同返回值不足以证明一致。

**依赖：** P3–P5 相应能力完成、同一最终业务输入与兼容格式方案、已审核的 Store/恢复/结算/清理基线。若采用 P1 新协调模型，还必须完成其独立实现与验证；未采用则按既有写者模型测试。

**拟修改模块：** 双平台测试夹具/CI、资源打包/安装、平台事实 schema/兼容文档、来源与快照校验工具及发现的最小实现缺口。不得直接改历史 SQL、旧报告或把 Linux 进程事实解释成 Windows 事实。

**设计约束：** 同一业务输入比较 epoch、原字节、版本、账目、claim、首次派发数及终态；平台路径/对象/进程身份使用明确版本，不要求不同 OS 的数据库物理布局、PID 或 Handle 值相同。跨平台恢复不能自动接管原平台活动进程/目录；无法证明原所有权/退出时保留，不以目标平台新对象替代旧证据。

**失败反例：** **PLANNED / NOT_RUN**：平台字段误解释、大小写/Unicode 别名造成重放、原进程身份搬迁后被接受、损坏安装资源、旧快照/新格式不兼容、取消与恢复结果差异、同逻辑输入产生不同 UNKNOWN/费用处理。已有 Linux 报告不等于 Windows 一致性证据。

**验收标准：** 支持矩阵中原生运行通过共同契约与平台安全矩阵；差异逐项说明并在效果前拒绝不支持输入；历史已支持格式保留原解释；冻结源输入、构建/二进制和 CI 归档可对应到同一提交；未执行项显式保留。

**测试矩阵：** 两平台 Store/恢复/Actor/CAS/UNKNOWN/终态/claim/工具/进程/清理/计费/single-agent/E2E/历史兼容/安装与损坏资源；Linux 两 umask、ASan/LSan、UBSan、Clang，Windows 实际 ACL 与支持 sanitizer。产品质量对照另属 P2 执行，不用 FakeModel 比较宣称模型质量等价。

**风险：** 测试按 OS 大量 skip 导致虚假一致；文件系统行为差异；耐久事实被抽象抹平；转换旧事实扩大权限；用同名二进制掩盖不同输入；将原生支持误说成跨平台活动状态可迁移。

## P7：拆分 S2–S5 的后续实施卡

**目标：** 把五阶段路线剩余能力拆成可独立审阅、实现和回滚的卡片，保留各阶段退出条件。P7 不把 DAG、记忆、MCP、A2A 和服务化打包为一次大规模改造。

**依赖：** [02 五阶段路线](02-five-stage-roadmap.md)、[03 模块依赖](03-module-dependencies.md)、S1 产品验收结果及相应 P1/Windows 决策。各阶段资料/接口调查可提前准备；生产顺序按实际依赖与协调者派发，不因统一卡号预先批准全部实施。

**拟修改模块：** 本卡先形成子卡、ADR 和验收规格。后继范围按下表拆分；现有 Schema/参考契约/经验待办不等于生产能力已接入。

| 子卡组 | 最小业务目标与拟影响模块 | 前置与独立退出条件 |
| --- | --- | --- |
