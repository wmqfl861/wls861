状态：**PLANNED / 待审**。真实供应商验收为 **NOT_RUN**；本轮不发真实模型或付费请求。既有 [R3 评测框架](../../implementation/R3-evaluation-framework.md)、[原 live 工作流](../../implementation/R3-live-workflow.md)、[签名计费](../../implementation/R3-signed-billing.md)与[单 Agent 执行器](../../implementation/R3-single-agent-baseline.md)是已实现的工程基础，不能替代真实产品质量结论。

## 1. P2 准备与真实执行分开

P2 在离线范围准备固定任务、材料、验收器、人审表、实验计划、失败/未知样本规则、预算配置模板和原证据采集方法。缺少真实凭据不阻塞这些准备；也不能从已授权开发、推送、会员账户或配置文件存在推断付费授权。

另行真实执行前，必须具备绑定具体请求/配置/模型的明确授权和下列信息。缺项保持阻塞，不能让模型补写。

| 条件 | 必须保存的内容 |
| --- | --- |
| 端点与模型 | provider/中转身份、精确 base URL/path、模型 ID/ref、协议/适配器版本、reasoning、核验日期和能力来源 |
| 支持子集 | 实测文本/function_call、工具历史、流式、输出上限、usage和缓存；reasoning effort不等于支持reasoning输出item |
| 凭据 | 受信宿主引用与权限，真实值仅运行时解析；不进Git、公开日志、快照或任务资料 |
| 预算与停止 | 每请求/每尝试token与费用预留、调用数、墙钟、批次、重试政策、取消规则和剩余额度；不在本稿设置金额默认值 |
| 计费信任 | 账户/签发来源、公钥或另一经批准的verifier、原请求响应身份绑定、单位及未知维度处理 |
| 工具与环境 | 明确文件/进程工具、目录授权、执行策略、平台和实际安全能力；需要run先有该平台强隔离正向证据 |
| 审批身份 | 调用/费用责任方、授权范围、材料与数据范围、批准时间和版本；主协调者给出执行卡 |

本项目 Ed25519 账单协议是受信中转需实现的契约，不能假定某 Responses 服务原生支持。合成签名、profile声明、价格表估算或模型自报费用都不是实际账单来源。若来源只能确认部分维度，其他维度继续 null，保留预留并按原门禁停止后续 batch；不能为了做完演示绕过账目完整性要求。

## 2. 固定任务与模型决定来源

先复用现有 `r3-small-tasks-v3` 的五任务、multi/single两条件、每条件一次，共十个固定样本位。材料和判据来自版本化计划，变更样本数、重试或难度须生成新计划版本；不把一次试跑宣称为统计显著优势。

| 任务 ID | 实际业务场景 | 必须关联的原模型证据 |
| --- | --- | --- |
| `tool_roundtrip` | 读seed → 写result → 读回 → 提交/检查 | 原生tool-call/result顺序、同绑定原反馈、同份原提交字节与模型检查 |
| `partial_amend` | 两任务在中途修改后分别update/keep；分批处理仍可继续 | 原AMEND、捕获pending任务/CAS、实际模型处置、两个当前任务的提交/检查/接受；遗漏期间不能继续 |
| `rejected_rework` | 当前候选被否定后按原目标有限纠正，再提交接受 | 同任务原否定、模型change_task、共享计数、新工单/ack、新版本成果与接受 |
| `exhausted_rework` | 冻结返工额度耗尽，升级给用户 | 原失败、捕获时额度、模型escalate_task和真实当前问题；回答不增加额度或代签接受 |
| `delivery_receipt` | 当前必需任务完成，原字节包发布与精确回执 | 每项acceptance的原plan/order/submit/check/accept链，CONFIRMED包与同请求receipt |

宿主负责技术准入、AMEND输入、权限和发布/回执，不能替模型编造计划、处置、检查或验收来填满模型来源链。Fake脚本与宿主dispositions只作为离线/反例夹具，真实样本须标明实际执行类别和原尝试身份。

额外安全验收包括必要恢复、空闲重开、旧会话拒绝、取消、发送/结算中断、迟到费用与终态收尾；这些不能通过破坏生产服务制造。确定性故障优先在loopback/临时Store验证，真实运行遇到失败则如实保留。未证明退出/所有权/完整账目时资源继续留存，不为“最终交付完成”提前清理。

## 3. 同条件多 Agent / 单 Agent 对照

共同固定精确模型和reasoning、材料、初始约束、工具集合、执行环境、上下文政策、工作流/返工政策、逐维预算及验收规则。调度、缓存温度、顺序和时间差记录为可能混杂因素；准备可复核的运行顺序，任何新增重复/随机化设计先版本化。

单条件使用已冻结的 `single-agent-role-broker-v1`：一个逻辑执行者接续所有前序原响应和反馈，实际模型输入带完整跨角色历史；Store 的Dispatcher/TeamLead/Worker权限仍分开。多条件使用原角色隔离历史。唯一明确的实验变量是该拓扑，不能重命名多个 Worker、只写同一个logical ID、遗漏失败历史或由宿主完成第二任务冒充单 Agent。

沿用v3核验每步原envelope、全局序号/前链、原原生消息、原反馈及实际业务记录；保留v1/v2历史解释。恢复时只承认原工单/正文hash及完整连续recover见证，不给旧调用重新盖版本。来源完整性校验和独立语义质量评分分别报告，脚本的结构通过不能自行把`provider_quality_acceptance_established`变成已证明。

## 4. 原证据与指标

私有原资料至少保存：冻结配置和能力依据、授权/计费政策的原字节身份、全部call/attempt、原请求信封/逻辑与编码身份、唯一send claim、实际传输观察、原HTTP响应范围和provider response ID、原usage/结算、追加核账链、原工具反馈/操作/提交/验收/交付/回执。对外报告只列获准的ID/hash/状态和统计，不展开凭据、私有提示词、供应商原文或用户成果。

| 指标 | 计算与解释 |
| --- | --- |
| 质量/通过率 | 预先固定逐项语义标准，依据原成果评分，必要时盲审；分母保留所有计划样本位并单列未执行，不把Schema pass当业务正确 |
| 费用 | 原账本及可信追加投影的实际micro USD；已知合计与unknown/disputed样本分列，不用价格估算补实际值 |
| token/缓存 | 每次尝试与input/output/cache_read/cache_write独立可空；缓存子量不重复加到总token，定义不一致不混算 |
| 耗时 | 宿主实际端到端墙钟、模型/工具/等待/恢复分项；保留取消和超时，明确测量来源 |
| 返工 | 同任务冻结额度、实际检查/拒绝与纠正链、成功前轮数、耗尽/升级率；AMEND和重启不清零 |
| 稳定性与安全 | 失败、无效证据、UNKNOWN、迟到结算、未处理待办、保留资源及版本拒绝；不删差样本改善均值 |

缺原数据时报告`invalid_evidence`、`failed`或`not_executed`，不造零调用数据库或新“已知”账单。重复调用/Schema纠错/压缩/审核都计入原预算，额度不足不自动追加。超预留真实支出完整记录并停止新付费准入，结算不能截成预算内数值。

## 5. 产品验收结论

首先独立核验工程门禁、原来源链和安全条件；再依据真实任务成果判定语义质量；最后比较同条件质量、费用、耗时与返工率。报告允许“未见改善”“样本不足”“费用仍未知”及“需要调整策略”的结论，不为证明多 Agent 优势而改变用户的四层角色约束或挑选成功样本。

结论仅覆盖实际端点、精确模型、协议子集、平台/工具和预算条件。跨平台或第二供应商另行验收；Linux文件小任务通过不证明Windows沙箱、所有模型或生产负载通过。主协调 Agent 审查原证据后决定S1产品验收及下一阶段；本轮P2仍只是离线准备，真实执行为NOT_RUN。发布状态遵循 [09](09-release-governance.md)。
