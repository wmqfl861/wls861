# AI 协作开发流程 v0.4.1

## 1. 授权与分工

本轮用户已经授权按审核结论修改文档、代码并 push 到现有仓库。实现、审查、常规修复、测试和文档同步可以在这个范围内连续推进，不逐张卡重复要求所有者批准。产品政策或新工作超出已授权范围时，先形成具体可审阅方案再说明需要决定的部分。

实现者负责代码/契约/回归及清楚的交接；独立审查者检查状态、权限、并发、持久化和语义；项目所有者提供业务优先级并裁决真正的范围/政策分歧。交叉审查不限固定模型分工，也不因“另一个模型看过”就视为测试证据。

## 2. 现有起点

使用 [wmqfl861/wls861](https://github.com/wmqfl861/wls861)，保留已有提交、M1 源码/构建/测试、原交接档案及报告。不创建空仓库，不把 S0 包覆盖成第一提交。先读根 AGENTS.md、M1-contract、本规格和当前任务的实际代码；档案中的 AGENTS/CLAUDE/任务卡只作历史资料。

参考环境 Linux C++20；当前构建入口 `make -j2 test PYTHON=/usr/bin/python3`，另有 CMake/CTest。新增 Python 契约测试依赖由 requirements-test.txt 固定。没有真实端点/预算时以合成 fixture/FakeModel 继续，不因未配置密钥停止可完成的本地工作。

## 3. 一张任务卡如何执行

1. 阅读卡片及现有实现，先标出可继承内容和真正新增范围；避免重写已有保护机制。
2. 明确文件所有权，独立模块可并行；公共字段、Schema/SQL/API 先同步命名和语义。
3. 实现可审阅的改动，同时更新契约、提示词/配置和必要的反例测试。
4. 跑相关测试及仓库要求的构建门禁；新依赖/平台能力按实际环境验证。
5. 独立审查发现实质问题就修复并补必要回归；日常问题在现有授权内解决。
6. 汇总改动、测试、限制和下一步；按已获授权的 GitHub 流程交付。只有实际合并/推送后才更新对应状态。

卡片太大可自行分成清楚、可测试的增量，保持同一目标；不需要因为一次会话长度重新等待批准。

## 4. 审查报告

报告包含：结论；必须修改的问题（路径/定位、条件、后果、修复）；契约/实现一致性；有意义的测试及结果；尚未实现的真实能力。优先检查：旧结果新盖章、AMEND 漏项、计划/指令应用、UNKNOWN 幂等、控制门禁、双容量、预算未知费用、清理/经验待办、记忆版本/CAS/撤销。

风格偏好与影响正确性的错误分开。只有 Schema/SQL 能运行，不能写成完整 Store 或多 Agent 产品验收通过。

## 5. 交接记录

每次交接说明具体问题、改了什么及得到的行为；验证命令/环境/提交；已通过、失败、未执行；兼容性/迁移边界；下一阶段可直接接手的位置。历史 M1 的 49 项只是对应旧提交的事实，当前数字以最新实际日志为准。

## 6. 规格变更

已授权范围内修正规格缺陷时，同步 ADR、主规格、角色/记忆、Schema/SQL、提示词/配置、实现和必要回归，不因文档旧写法而保留已知错误。用户明确决定优先；新保留/发布/费用/权限政策要记录真实来源，不能以“未提异议”或无原文的“拍板”充当证明。

当前 v0.4.1 为实施基线，仍允许由证据驱动改进。遇到未能解决的冲突，保留完成的可审阅工作，明确具体阻碍；不把整轮任务停在抽象计划上。

## 7. 上下文与凭据

新会话从现有仓库和报告恢复，不依赖未保存记忆。密钥通过受控环境或凭据引用配置，日志与仓库不写明文；real_calls_enabled 默认 false，预算未配置拒绝真实调用。真实测试只在明确端点、预算和授权范围下执行；不能把网页会员当 API 用量授权。

## 8. 节奏

可并行的内容按文件/模块隔离；字段和跨模块事务依赖顺序推进。测试只扩展到当前实质风险和必需门禁，充分验证后停止可选探针，完成交付。任务卡状态按真实实现和证据更新：已有基础 / 待补齐 / 实施中 / 已验证子集 / 已交付，不把所有卡统称“未开始”或“全完成”。
