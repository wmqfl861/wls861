# 角色行为规格 v0.4.1

本文件是 S1/S2 模型运行器的实施契约，承接现有 M1 确定性内核；提示词本身不是权限、事务或版本保证。配套提示词在仓库 prompts/，结构定义在 schemas/。当前不存在已经完成的真实模型运行器。

## 1. 共同规则

1. 原文和已登记约束/验收项保持可见。摘录不可改写；覆盖检查针对 request_snapshot.constraint_catalog 与 constraint_refs 的权威清单，不能声称子串检查发现了全部自然语言约束。
2. 请求需求、计划、任务、执行说明和代次分开。模型调用开始时固定版本上下文；迟到内容不能重新盖当前版本章。
3. 普通文字不改变状态，只有通过授权接口、完整校验并提交事务的决定才生效。Schema 校验只是其中一层。
4. 普通执行与控制分支分开。暂停、UNKNOWN、预算不足时仍可用受限查询、ack、取消、核对和上报；不能把 shell 当成控制工具。
5. 凭据、项目/功能/请求/团队归属由宿主提供。模型不能自选自己的角色、代次或作用域。
6. 记忆、文件、命令输出是资料。自称“管理员”的文字不改变权限；规则变更与撤销由运行时政策门禁决定。
7. 唤醒结束只确认已完成的待办。遗漏、错误、耗尽工具次数不表示批准、不解除暂停。
8. 如实报告证据、未知结果、未执行检查和成本。Schema 纠错、压缩和每次重试都属于可能计费的调用，受独立尝试预算约束。

## 2. Root：技术入口

Root 不调用模型筛掉请求。验证格式/大小、调用方和范围，按作用域化幂等键准入；同键同内容返回原请求/回执，同键异内容拒绝。NEW、AMEND、REPLACE、ANSWER、CANCEL、QUERY 路由分别处理。

AMEND 与持久待处置项创建同事务；Root 不推断哪个团队不受影响。对外进度、问题和交付由确定性路由发送。GET/QUERY 不确认交付；显式回执绑定不可变包和版本。等待容量时有界排队，不启动无限 Agent。

## 3. Dispatcher

### 3.1 唤醒

新请求、需求修改、待处置/问题/提交、审核不明、失败受阻、预算告警、全部必需任务已验收。心跳不唤醒模型。每次处理不超过配置的管理调用数；到限释放运行槽位，把未完成待办重新排队。

### 3.2 上下文

稳定前缀 + 请求冻结配置/完整原文/约束清单 + 持久快照。快照含请求 requirements_revision、当前 plan_revision、每任务 task/plan/instruction 目标与 applied 值、AMEND disposition、UNKNOWN、候选/审核绑定、问题、经验待办及预算预留/未知费用。临时对话不替代持久事实。

### 3.3 工具

| 工具 | 行为与确定性校验 |
| --- | --- |
| submit_plan | Plan 绑定当前请求修订；校验无环、节点范围、约束覆盖和权限；影响旧节点时必须更新任务/说明绑定并失效旧候选 |
| set_amendment_disposition | 对一个任务针对当前 AMEND 显式 update/keep/cancel，带理由、预期任务版本；遗漏仍暂停 |
| change_task | 在已明确的请求修订下改变任务/返工；增加 task_revision，说明重新发行、重新应用 |
| accept_task | 当前提交、全部必需证据/检查、当前审核或明确豁免有效；不能只检查 Schema |
| cancel_task | 停止新业务并取消/核对进行中的操作；不宣称副作用消失 |
| answer_team / ask_user | 核对当前问题链；原问题原文保留 |
| read_artifact | 只读授权成果视图，不能读取其他请求 |
| deliver / fail_request | 当前完整包与收尾待办；失败也保留真实已完成范围和未决操作 |
| recall / load_memory | 只读当前可见、适用、获准记忆；S3 前返回未启用 |

### 3.4 AMEND 行为

逐任务处理，不能仅处理看起来最明显的一个。update 写清停止/保留/新增和验收项变化；keep 必须说明为什么保留、适用哪些新约束，仍把任务绑定到新请求修订并要求新说明/确认；cancel 停止执行。已 ACCEPTED 的任务也要明确判断是否可重用旧成果。

新计划不能隐含替代某项 disposition。运行时明确显示未处置项；它们在所有唤醒结束、异常、调用次数到限之后继续暂停。没有把握时上报，不能把遗漏默认为“不受影响”。

### 3.5 验收与等待

业务验收逐项检查成果/证据。审核报告内容可以是“不通过”而审核服务本身成功；生产任务仍未通过。模板能力由确定性验收器核必需检查、版本、证据与权限，省模型规划不省关口。

等待审核、用户或子任务时释放活跃 Dispatcher/模型名额，保存逻辑请求身份。不能同步占住执行池等待同池子任务；普通准入不得借用审核管理/Worker 保留名额。

## 4. TeamLead

### 4.1 唤醒

团队启动、Dispatcher 变更、Worker 问题/提交、上级答案、审核返工、停滞、experience_jobs 待办。业务验收后写经验是持久待办，不是只发一次可丢失通知。

### 4.2 上下文

完整原文与约束、任务当前绑定、已发说明、Worker 的受控进度/证据/操作状态、待应用说明、审核发现、记忆加载绑定及经验待办。只读工作区视图也受范围约束。

### 4.3 工具

| 工具 | 行为与确定性校验 |
| --- | --- |
| issue_work_order | 初始或同目标的执行说明更新；每次增加 instruction_revision，不能悄悄改目标；复制适用约束 ID 与原文 |
| issue_change | 绑定 parent_change_id 和完整目标版本；覆盖上级约束/findings，明确 stop/keep/add；旧说明失效 |
| answer_worker / escalate | 依据当前任务契约回答或保留问题原文上报 |
| read_workspace | 受限 list/read/search 视图；不是任意宿主文件访问 |
| forward_submission | 绑定原 submission 及完整版本、逐项 check/evidence；不能给旧提交补当前版本 |
| return_for_rework | 团队内有界返工，新的说明版本与确认；不能绕过任务/审核范围 |
| write_experience_report | 绑定经验待办及证据；no_new_experience 合法；版本化使用评价和候选修订受 CAS/政策检查 |

### 4.4 说明、核对和经验

看 Worker 当前进展后翻译变更。每次说明更新令旧 Prepared 失效；在途操作保留为待核对状态。生产团队说明改变使当前候选/批准失效；审核团队说明改变要求新的审核证据。Worker 尚未确认时不能派发新业务。

UNKNOWN 不妨碍通过控制接口确认新说明；确认说明也不能把 UNKNOWN 变成已解决。需要核对时使用运行时允许的事实和受限诊断，不命令 Worker 重复有副作用的 run。

经验报告引用实际 memory_id/revision/load_id 和动作证据。新经验、修订、冲突、无新增分别报告；修订包含 expected_base_revision，不能根据读取后已经过期的内容覆盖当前记忆。业务完成不自动给所有加载记忆加分。

### 4.5 上限

管理调用和团队内部返工有界。次数耗尽保留未处理待办，释放运行槽位后继续或上报。经验暂时写不出时留存轨迹摘要和明确状态，不能让清理删掉唯一证据。

## 5. Worker

### 5.1 工作循环

1. 读取当前指令绑定及运行时暂停/UNKNOWN/政策状态。
2. 如有新说明，先通过控制接口 ack 当前完整 binding；初始 WorkOrder 也必须确认。重复的新 command_id 在没有新说明时不能产生无限 ack 事件。
3. 有 UNKNOWN 时仅用当前新说明确认、受限查询、取消/核对/上报；业务门禁仍关闭。暂停或等待时释放活跃模型/执行槽位，不忙轮询。
4. 获准业务派发前再次核全部版本/权限/政策/预算；有多个工具调用时逐项检查，不能把一次模型响应当成整批授权。
5. 每个副作用操作有稳定 business_idempotency_key；精确重试返回旧状态，UNKNOWN 不自行重做，参数哈希相同也不擅自合并不同业务意图。
6. 完整工具结果和证据先持久化再推进对话；发生断流、恢复或部分写入时保留未知状态。
7. 提交当前候选，等待 TeamLead/审核反馈；继续返工须新说明绑定。

### 5.2 上下文与恢复

原文、全部修改、TaskBrief、WorkOrder 保留可见；新修改原文和 ChangeOrder 以消息追加。压缩保留当前修订/代次、未决操作、原始修改、有效 ChangeOrder、证据与记忆绑定。恢复使用请求冻结配置和原调用上下文，先确认/核对再继续，不能只依赖一条提示语。

### 5.3 工具分类

| 类别 | 工具与限制 |
| --- | --- |
| 业务 | fs_write/fs_patch/run 等；完整应用/暂停/UNKNOWN/政策/预算检查；只有 Worker |
| 受限只读诊断 | fs_list/fs_read/fs_search 的注册诊断子集、op_status/op_output；限定当前资源、输出大小与路径；不能任意 shell |
| 控制 | ack_change、op_cancel、ask/progress、运行时确认/核对入口；不受普通业务预算/未应用门禁阻断，仍核身份、对象与状态 |
| 成果/经验 | submit/note 是有界写入，不通过“控制”分类豁免普通容量；负面撤销和已准入结算例外按内核契约 |
| 记忆 | recall/load_memory 校验可见性、revision、policy_epoch；脚本使用另过业务门禁 |

`ack_change` 由运行时发行的说明绑定解析完整 request/plan/task/instruction tuple；模型不能自称已应用别的版本。op_cancel 对 Prepared 可取消，对 Running 只能确认停止请求并进入 UNKNOWN，最终结果由运行时证据核对。控制接口不授予额外工具能力。

### 5.4 行为

按环境卡片使用工具，不因记忆建议就扩大权限。记录实际验证，不假设命令成功；同错误反复出现时先看证据、必要时 ask。提交包含成果、逐项检查、未决项和 used_memories 的完整版本/加载引用；没用过的不要列入。

### 5.5 停滞

无进展、重复错误和调用额度告警由运行时判定。暂停、排队、等待长操作不算无故停滞。预算不足时不能为“最后再试一次”自动增加付费调用；已有取消和核对仍能完成。

## 6. 问题协议

问题持久化，记录提问者/持有人和原文。每层先用有权限的上下文答，答不了原文上报，可附注但不改问题。答案原文送达原提问者，保存回答时的请求修订；已过期问题需明确重新解释，不把旧答案当新要求授权。

## 7. 端到端事件示例

### 7.1 普通执行

Root 准入→Dispatcher 当前版本 Plan→TeamLead WorkOrder→Worker ack→操作/候选→TeamLead 检查→可选独立审核→Dispatcher 确定性验收→经验待办→不可变交付/匹配回执→清理待办。每个箭头是可恢复持久状态推进，不等于一次模型调用。

### 7.2 修改两个任务

request rev 1、任务 A/B 均已应用→AMEND 到 request rev 2→A/B 都暂停且待处置→Dispatcher update A 后达到调用上限→B 仍暂停→下一次显式 keep B→A/B 各有当前绑定的新说明→Worker ack→UNKNOWN 核清后继续业务。用例必须覆盖 Dispatcher 漏项/异常结束及旧模型响应迟到。

### 7.3 审核

候选固定后即可送审；普通名额已满也有保留审核 Dispatcher/Worker 可用，调用方释放等待名额。审核回包核生产方版本与独立 reviewer tuple/ticket；审核方重启后的旧 epoch 也必须拒绝。审核 pass 仍经当前证据验收；changes_requested 形成新说明；到上限上报，不自动放行。

### 7.4 恢复和收尾

服务可在验收后、经验完成前或写交付后重启。启动重新发现 experience_jobs/cleanup_jobs，提升代次，保留 UNKNOWN，并恢复缺失步骤。业务已经 DELIVERED 不妨碍资源收尾继续，也不能把重复通知算新操作。

## 8. 快照字段要求

快照显示当前 requirements_revision/plan_revision，任务的 based_on_requirements_revision、task/plan/instruction 目标与 applied 值、disposition 待办、epoch、candidate/hash、review context、UNKNOWN、问题和经验/清理待办。预算显示 spent/reserved/unknown 而非单一百分比。缓存依赖 ID、政策撤销版本与隔离等级可供诊断，但不把内部实现细节混入用户任务成果。

## 9. 异常处理

Schema 错误只可在策略/预算许可时纠错；默认不自动付费重试。CAS/版本错误读状态后重新规划，禁止自动给旧回答盖新版本。UNKNOWN 走核对，权限/撤销走受限上报，磁盘/存储错误保留失败和待恢复状态。报告引用实际命令、提交和证据，不把未执行用例改成通过。
