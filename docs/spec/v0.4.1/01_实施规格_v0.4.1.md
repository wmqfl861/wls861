用户明确指令优先，其次为当前仓库契约和本轮采纳的修订。原 v0.3/v0.4 位于 `docs/handoff/`，逐字节归档；档案内部 AGENTS、任务卡和待定政策不会自动执行。规格语义与 schemas/db 必须一致；实现缺口和实测结果记录在 `docs/reports/`。

## 1. 目标与范围

构建通用 C++ 多 Agent 系统：Root 对外，每请求一个 Dispatcher，若干 TeamLead/Worker 一对一团队；并发请求不串，中途修改准确落到执行，审核后交付，再按政策清理；经验有依据地积累和修订。

S1–S4 目标包括四角色模型运行器、Worker 沙箱、计划和审核环、记忆 v1、CLI/API 与 MCP。首版以单用户本机为工程默认，仍保留项目、功能、请求、团队和能力授权边界。多机、Windows、通用工作流 DSL、全面插件兼容、严格清除和自动换模型不在当前闭环中。

## 2. 术语

| 名称 | 含义 |

| 控制通路 | 查询、版本确认、取消、核对、回执、收尾等受限接口；不是绕过权限的业务工具 |

## 3. 架构与运行模型

### 3.1 模块

RootGateway 负责准入和路由；Engine 管状态、事件、计划与配额；Agents 包括管理角色与 Worker 运行器；ContextCompiler 编排上下文；ModelAdapter 负责模型协议；Tools/Sandbox 管工具权限和进程；Delivery 管不可变交付及收尾；Store 管事务；Memory 在 S3 接入。

### 3.2 进程与事务

S1 拟使用单 wlsd、Asio 协程及有界线程池。每请求控制事件串行，独立请求并行；数据库一个写连接与有界只读连接池。模型、网络与工具执行不在状态事务中等待。模型调用开始时捕获不可变调用上下文：身份、request/plan/task/instruction 修订、执行代次、配置快照、政策版本和预算预留。结果返回必须核对原始上下文，不能读取当前行后重新为旧结果填写“当前版本”。

Agent 是逻辑实例；进程业务工具才创建受控子进程，固定文件操作可由有界文件代理完成。恢复从持久事实重建，不依赖模型记住状态。M1 的同步 Journal/互斥提交和锁外调度继续作为语义及测试基础。S1.3 的 `pump-fake` 同步处理有界的持久角色待办，支持冻结数量内的独立任务，每任务最多 16 次 Worker Fake 工具往返，并从原始持久反馈恢复上下文。S1.4 进一步按持久问题/提交目标有界轮转；等待和遗漏项释放本次执行机会并保留待办。原单任务 `run-fake` 保留，但不能自动重发说明绕过未处理的工作流。请求 strand、协程、全局审核双容量并发调度、只读连接池与 wlsd 尚待后续接入。

### 3.3 切片

Store/config/engine/model/sandbox/tools/agents/delivery/API 是 S1 的完整闭环；多团队正式审核和跨功能调度在 S2；记忆 S3；MCP S4。S1 也必须具备基础恢复和 UNKNOWN 保护，不能等到 S2 才防真实工具重复副作用。

## 4. 角色与协作（详见 02）

### 4.1 职责

| 角色 | 职责 | 边界 |
| --- | --- | --- |
| Root | 技术准入、去重、路由、事件/交付 | 不做业务规划、验收或执行 |
| Dispatcher | 计划、每任务变更处置、问题处理、验收 | 不执行命令，不代签独立审核 |
| TeamLead | 当前执行说明、变更翻译、检查、经验收尾 | 不修改请求目标，不越级控制别的团队 |
| Worker | 当前契约下执行、提交、提供证据 | 不自行派生 Agent、扩权或改验收标准 |

### 4.2 唤醒与持久待办

Dispatcher 在新请求、AMEND、问题/答案、提交、阻塞、预算告警、全部必需任务验收时唤醒；TeamLead 在启动、指令变更、问题、提交、返工、停滞、经验待办时唤醒。Worker 连续循环，暂停/提问/依赖等待时不占模型或执行槽位。

事件先持久化，再通知。每次唤醒仅确认实际处理完成的事件；遗漏仍在待办中。每次最多 12 次管理调用是调度上限，耗尽后释放名额并重新排队，不能默许未处理任务继续或丢掉经验报告。反复无进展时转 WAITING_INPUT/告警。普通心跳由程序转发，不唤醒模型。

S1.3 已接入事件→逐角色/任务主题 inbox→有代次的具体项领取→显式子集确认。领取期间的新项及未完成项不会被高水位游标吞掉；重启只释放旧领取，不执行旧工具。S1.4 新增 Worker 发起的问题及逐级回答/转发、提交和 TeamLead 检查返工事件。每次管理调用在原输入中捕获一个目标及对象 CAS；候选就绪后的 Dispatcher 待办继续保留，不因已有计划/说明而确认。S1.5新增当前Dispatcher验收和原版本经验job唤醒，终态仅恢复报告；跨功能独立审核、全局审核容量和长期异步仍按后续卡实施。

### 4.3 消息

Plan、TaskBrief、WorkOrder、ChangeOrder、Submission、ReviewRequest/Verdict、Question、ExperienceReport、DeliveryManifest 使用 schemas/ 中的结构。模型参数只含其允许填写的字段；运行时在模型调用创建时保存身份/版本，响应封装使用这份调用上下文。完整持久记录须具备运行时字段；仅模型参数通过 Schema 不等于完整记录有效。

### 4.4 原文与约束完整性

请求原文和每次修改只增不改。所有角色可按引用看到原文，摘录不得取代原文。`constraints_verbatim` 子串校验只能证明没有改写，不能证明没有遗漏。

请求入口可接收用户明确给出的约束 ID/验收项；运行时保存权威约束清单及任务适用映射。request_snapshot.constraint_catalog 保存权威集合；TaskBrief/WorkOrder/ChangeOrder 的 constraint_refs 必须覆盖其适用的已登记 ID，并保留文本、来源 revision 和证据。自由文本中的隐含约束由语义提取与审查发现；系统不得声称可以仅靠子串检查自动证明全部用户意图已覆盖。HOP-01 同时测试已知约束漏项和真实成果保真。

## 5. 请求、任务、团队与版本

### 5.1 标识

请求、任务、团队、事件、成果、操作、提交、变更、问题采用带类型前缀的稳定 ID；S1.1 已实现 Linux getrandom 与进程内单调 ULID。ID 只是标识，不是权限。幂等键限定在入口作用域（项目、功能/Root、调用方）；内容指纹包含不可变输入及范围。

### 5.2 独立修订与应用

| 对象/字段 | 含义 |
| --- | --- |
| requests.requirements_revision | 用户需求修订；仅 AMEND 增加 |
| requests.plan_revision | 已提交计划修订 |
| plans.based_on_requirements_revision | 该计划据以制定的请求需求修订 |
| tasks.task_revision | 任务本地内容/返工修订；不是请求需求修订 |
| tasks.based_on_requirements_revision | 该任务已被明确处置到的请求修订 |
| tasks.plan_revision / applied_plan_revision | 任务绑定计划 / Worker 已应用计划 |
| tasks.applied_task_revision | Worker 已应用任务修订 |
| tasks.instruction_revision / applied_instruction_revision | TeamLead 说明高水位 / Worker 已应用说明 |
| state_version | 逐行 CAS 版本，每次变更递增 |
| dispatcher_epoch / execution_epoch | 请求管理实例 / 团队执行代次，恢复或替换递增 |
| review_round | 审核轮次；不代替需求、指令或候选版本 |

ChangeOrder 携带 `based_on_requirements_revision`、`target_task_revision`、`target_plan_revision`、`target_instruction_revision`。每次重新说明也增加 instruction_revision，即使任务目标没有变化。生产团队说明变化使当前候选和批准失效；审核说明变化要求新的证据。新团队不能复用旧 execution_epoch。提交、审核、操作和回执绑定相应版本，不能用“版本数字刚好相等”比较不同计数器。

业务派发要求：任务已针对请求当前修订明确处置；计划也基于该请求修订；Worker 已应用当前 task/plan/instruction；身份与代次有效。指令更新令旧 Prepared 操作失效；在途非幂等操作进入核对流程。M1 的 applied_revision/instructions_version 等旧字段由明确映射保留，不为了统一 SQL 名称破坏既有 Journal 格式。

### 5.3 请求状态

RECEIVED → QUEUED → PLANNING → RUNNING → VERIFYING → DELIVERING → DELIVERED。WAITING_INPUT 记录返回状态；失败、取消、替代为 FAILED/CANCELLED/SUPERSEDED。VERIFYING/DELIVERING 收到 AMEND 时旧验收和未确认包失效，回到调整执行路径。

业务状态、delivery_status 和 cleanup_status 独立。DELIVERED 不代表临时资源或经验收尾已经完成。

### 5.4 任务状态

PENDING → READY → RUNNING → SUBMITTED/REVIEWING → ACCEPTED。审核 changes_requested 进入有界返工；inconclusive 或轮次上限进入 BLOCKED；只有用户明确豁免可以带问题验收，交付 limitations 必须列出未解决项。失败/取消/替代/跳过分别记录。

计划新增/改写节点须校验其 task revision、依赖和约束；影响既有节点时更新相应绑定、失效旧提交/验收并重新下达说明。不能仅改 plan_revision 而继续使用旧 Worker 应用状态。已验收任务在 AMEND 下仍须被明确重用或重新处理，不能因已 ACCEPTED 就跳过新需求评估。

### 5.5 团队和经验收尾

STARTING → ACTIVE → DRAINING → STOPPED → CLEANED；失败为 CLEANUP_FAILED。验收写入与 experience_pending 待办创建在一个事务中。每团队每次已验收内容版本的 experience_jobs 以 request_id/task_id/team_id/task_revision/instruction_revision 唯一绑定；对应报告或“无新增经验”确认持久化后才算该版本经验收尾完成。单团队报告不完成整个请求，新版内容也不能借用旧版报告；模型失效时保留待办/轨迹摘要并明确未完成，不能默默省略。实际已接入范围、原始退出证据和受控目录删除边界见[STATUS](../../STATUS.md)，不由工作目录阶段完成推断私有行已清除。

停止业务工具不必等待新的付费模型调用。可先结束工具进程、保留必要成果和经验输入；需要后续说明时重新分配管理槽位。已 STOPPED 的执行团队不直接复活，返工创建新团队和新代次。

### 5.6 后续消息

NEW 按范围化幂等键创建或返回原请求；AMEND 留在原请求；REPLACE 原请求 SUPERSEDED 并创建关联新请求；ANSWER 绑定当前问题；CANCEL 进入控制及收尾；QUERY 只读。已终态请求的 AMEND 提示使用 NEW/parent_request_id。清理后的去重依靠有期限回执，过期语义公开，不承诺永久去重。

### 5.7 中途改方向：显式处置，遗漏暂停

1. AMEND 事务写原文、递增 requirements_revision，失效旧验收/待交付绑定，并为每个现有任务创建当前修订的 amend_dispositions 待处置项；活动团队暂停新业务派发。
2. Dispatcher 对每项提交持久 disposition：update（更新任务）、keep（有理由地保留）、cancel。决定携带当前请求修订和任务预期版本；旧模型响应不能替当前 AMEND 作决定。
3. update 下达新内容；keep 也显式把任务绑定到请求新修订，记录保留理由与适用约束。两个分支都更新计划/任务应用绑定，TeamLead 下达当前 instruction revision，Worker 明确确认后才能继续。cancel 进入受控停止。
4. 任何未处置项继续暂停。正常结束、异常、Schema 错误、12 次调用上限或第二次仍未处理均不自动解除暂停；可以继续排队处理或上报。
5. AMEND 不谎称已经撤销正在运行的副作用。分类记录已运行操作，显式取消或核对；UNKNOWN 未核清时禁止新的相关业务操作。受限诊断与取消仍可用。
6. 发布/提交/验收核对完整版本绑定。旧结果可以作为有标记历史证据，不能冒充新修订成果。可证明未受影响的成果也必须有显式重用决定及新验收绑定。

### 5.8 事务、幂等与派发

状态变更、命令回执和事件在同一事务。CAS 冲突读新状态后重新决定，但旧模型内容不得自动重新基于新状态提交。管理 command_id 的精确重试返回原结果；同键异内容拒绝。业务操作另有 `business_idempotency_key`，绑定 scope、参数哈希和完整执行版本；哈希相同不代表不同业务尝试应合并。

派发前先持久 PREPARED/意图，再启动工具；开始、结果、取消与核对各有状态。恢复不把 RUNNING 简单变回可执行。持久成功才回复成功；SQLite、文件成果复制和事件通知之间用可恢复待办/事务外盒衔接，不假装单一数据库事务包含文件或网络原子性。

### 5.9 恢复

启动不仅扫描非终态业务请求，还扫描 terminal-but-not-cleaned、experience_pending、UNKNOWN、未确认交付、未发布事件和独立 cleanup_jobs。先持久提升代次/失效旧调用，再对外开放接口。清点并结束残留受控进程；结果不能证明的操作标 UNKNOWN。

所有非幂等副作用均须核对，包括 workspace 文件追加、数据库变更和 external 行为。UNKNOWN 时普通业务门禁关闭；仅允许当前新说明确认、明确注册的只读诊断、op_status/op_output/op_cancel、上报及运行时核对。不能把任意 shell 作为“核对”工具绕过。准确重试返回既有状态；需要再次执行时先判定原操作未发生或明确处理已发生效果，再创建获准的新操作。

Worker 恢复保留原调用/工具结果绑定，不能仅靠“请先核对”的提示词；重新应用任务/计划/指令后恢复工作。恢复的配置来自请求冻结快照。

纯执行代次变化不得触发模型重写语义未变的说明。宿主事务内重绑定当前说明、记录原/新代次与正文哈希，失效 applied 状态；Worker 用新身份/CAS 走控制 ack。正文、语义修订、工具/返工计数不变，原事件和调用绑定保留。AMEND、等待、UNKNOWN、迟到响应的检查仍有效（[ADR-064](../../adr/064-audit24-recovery.md)）。

### 5.10 配额、审核容量与预算

| 项目 | 起步默认 |
| --- | --- |
| 活跃 Dispatcher / Worker | 4 / 8 |
| 为审核常态保留 Dispatcher / Worker | 1 / 1 |
| 每请求团队 / 每端点模型并发 / 工具并发 | 4 / 8 / 16 |
| Worker 每指令工具调用 / 管理每唤醒调用 | 200 / 12 |
| 真实模型预算 | 输入/输出 token、金额、墙钟上限必须配置 |

普通请求准入始终不能借用审核保留名额；不能等审核到达后才发现容量已满。排队有界、公平轮转；等待审核、工具、用户或依赖的逻辑 Dispatcher 不占活跃执行/模型槽位，唤醒时重新申请。资源键持有范围限于实际冲突操作，等待子任务前释放，避免父任务占满全部名额。

普通模型/业务预算与受限控制额度分开。每次真实调用前预留最坏可计费额；每个重试、Schema 纠错、压缩和审核尝试都登记，成功后按实际结算。失败/超时/断流而费用未知时保留预留额，不填 0、不自动退款。80% 告警，用尽阻止新付费调用/业务操作并等待；取消、查询、核对、回执和已准入资源收尾仍有受限控制通路及磁盘预留，物理磁盘耗尽仍可能失败。

存储容量来自冻结 system.limits；旧快照缺字段按原常量解释，配置更新不影响既有请求。新准入校验每说明工具数×团队数×返工轮次与事件/操作等容量一致。业务/控制独立计数，预留已准入工作的结算空间；接近上限告警，到限记录可恢复阻塞。检查点/归档保留幂等索引和全部审计，不重置业务额度或解除 UNKNOWN。具体实现状态见 STATUS，验收按 ADR-066。

## 6. 计划与工作流

### 6.1 计划

Plan 节点为 team_task 或 capability_call；经对方 Root 调用能力。校验无环、模板/能力存在、作用域/权限、约束覆盖、版本与额度。单节点计划完全合法。计划明确 based_on_requirements_revision，不允许旧规划结果覆盖新需求。

### 6.2 调度与汇合

必需依赖全部 ACCEPTED 才能汇合；可选依赖按显式策略处理 FAILED/SKIPPED。依赖失败唤醒 Dispatcher，不以先返回者当全部完成。审核子请求经正常身份和版本通路；同时保留管理和 Worker 容量。等待方释放活跃名额，不能因审核与开发互相等最终完成而死锁。

### 6.3 审核返工

TeamLead 转交即产生不可变 candidate 并送审。ReviewRequest 固定生产方需求/任务/计划/指令、candidate 哈希和审核轮次；返回 Verdict 绑定原始审核上下文。review_tickets 同时固定审核子请求的 reviewer_request_id/reviewer_task_id/reviewer_team_id、reviewer_requirements_revision/reviewer_plan_revision/reviewer_task_revision/reviewer_instruction_revision、reviewer_dispatcher_epoch/reviewer_execution_epoch/reviewer_policy_epoch；生产方代次不能替代审核方恢复围栏，回包同时核 ticket 和审核方当前 tuple。pass 进入待业务验收；changes_requested 形成有版本的返工 ChangeOrder；inconclusive/轮次上限受控上报。审核说明变化或候选变化使旧批准失效，交付前负面证据仍可撤销批准。

S1.4 当前接入的是生产团队内部检查：Worker 提交最多8个文件、每个64KiB、合计256KiB的完整实际快照；TeamLead 根据原提交/字节检查一致性，失败用冻结上限内的新任务/指令修订返工并要求重新ack。通过只产生 CANDIDATE_READY，不创建独立审核票据或业务 ACCEPTED/DELIVERED；正式跨功能审核仍按上述目标继续实现。

### 6.4 模板化 Dispatcher

模板可免模型规划，依能力输入形成 TaskBrief；但完整验收仍由注册的 deterministic acceptance validator 完成：Schema、当前版本/哈希、必需检查与证据、身份及权限、审核豁免范围。缺证据、必需检查 not_run/fail、pass 与 blocker 矛盾必须拒绝或给 inconclusive。输出合法的“不通过报告”可以是成功完成审核服务，不能转换成生产任务通过。

## 7. 上下文编排与缓存

### 7.1 布局

①稳定工具定义 → ②系统/角色/功能说明、环境卡片、常用 Skill 索引与获准规则 → ③项目资料快照 → ④当前任务契约 → ⑤追加消息或管理快照。动态回忆正文追加在⑤；随机 ID、时间和真实宿主路径不进可共享前缀。不能为缓存保留已经撤销的授权。

### 7.2 追加与快照

R1 的 Worker 窗口采用 [ADR-069](../../adr/069-worker-history-window.md)：仅新请求显式冻结启用；
完整当前契约不参加历史裁剪。过大轮次保留哈希引用，遗漏范围明确并可经作用域控制回读，
不是伪造摘要或删除审计。模型回读仍计尝试和预算；旧快照、UNKNOWN、等待及版本门禁保持。

Worker 在窗口阈值（默认 60%）压缩旧消息；保留有效 ChangeOrder 和修改原文，摘要含当前修订、步骤、文件、证据、未知操作、未决项与记忆使用绑定。管理角色每次从持久状态/待办生成快照，附有上限的最近决定；待办可分批读取但不丢失。原文/约束总量也有显式容量限制；无法完整容纳时采用有覆盖记录的分批读取或明确阻塞，不静默截断有效约束。不能依赖上次临时对话。

不可变历史与当前模型窗口分离：大工具结果保存单一无损编码及分页引用，窗口可用带原始hash/
范围的摘要。压缩记录含来源范围、格式版本和绑定；原文、有效约束、未决副作用/问题、当前计划/
指令与验收证据不能被摘要替换。超容量返回quota并保留明确恢复路径，不通过重新读取live文件
伪造旧观察；不能仅增加1 MiB/256常数作为压缩实现。压缩调用若收费也须预约预算。

原始历史的访问与模型上下文选择分开：宿主提供作用域绑定的分页事实索引及带哈希的原反馈
分片，窗口/压缩只引用这些原证据，不通过重读当前文件补造旧观察。索引固定插入高水位而不
冻结后续结算状态；原反馈须同时核对事实哈希、原调用绑定及原响应。具体边界见
[ADR-067](../../adr/067-paged-history.md)。窗口选择不得暗中丢弃需求、约束或未决副作用。

### 7.3 请求冻结配置

请求创建时复制功能模板、已解析 Root、角色覆盖、能力表/端点配置版本、提示词和环境模板依赖。后来创建团队、恢复实例继续用此快照；配置文件更新只影响新请求。紧急授权收缩/记忆封禁通过独立政策门禁立即生效。若需迁移活跃请求模型/工具，显式记录迁移、代次提升、上下文重编译和重新应用，不偷偷换模型。

### 7.4 完整缓存依赖

区分规范化结构化请求的逻辑指纹与适配器实际发送表示的wire指纹，二者不可互相冒称。
逻辑前缀身份由规范化system/tools/messages前缀及依赖决定：适配器/协议版本、模型、思考参数、工具定义及排序、系统/角色/功能提示版本、模板版本、环境卡片哈希、pinned Skill 的 ID/版本、规则及作用域政策快照、项目快照。`prefix_sha256`是带格式版本的逻辑稳定前缀指纹；`cache_identity`还涵盖模型/协议/思考参数。
适配器另记实际wire前缀/请求哈希及缓存标记；旧帧格式的哈希只表示旧帧字节，不改标为wire哈希。

只有上述依赖完全相同才断言可共享；同功能同角色却规则、工具版本或模板不同，指纹应不同。动态⑤消息变化不扰动未变前缀。适配器按实际模型能力添加缓存标记，不假定所有兼容端点支持相同断点、TTL、最小长度或 reasoning 行为；实施时验证当前版本并记录依据。

### 7.5 计量

每次尝试写调用、预留、结算和结果状态；供应商未给的 input/cache_read/cache_write/output/cost 为 NULL。缓存读取占比只对相同定义且用量可比的样本汇总；报告未知样本，不把缓存写计为读取、不把 NULL 当 0。前缀相同不承诺实际缓存命中，命中和质量需实测。

## 8. 模型适配

### 8.1 接口

ModelAdapter 提供 capabilities、validate 和异步 complete。编译结果采用供应商无关的结构化请求：
系统段、按顺序的原生工具Schema、带唯一call ID的工具请求/结果、多轮消息、模型/思考选择与完整绑定分开。
适配器负责协议字段、流式事件和缓存断点映射，不把自定义分帧字节串直接当作一条用户消息。
先定义并回放测试请求/响应映射，再接选定协议；P-01/P-05配置及明确付费权限只限制真实调用。
FakeModel与真实适配器共享结构化契约，未知usage保留NULL，原始wire与attempt分别留证。
格式选择属于请求冻结配置；缺字段的历史快照继续旧帧格式，不自动迁移。结构化历史只把完整、
已记录的工具往返表示为配对消息，缺失或未采用的响应明确标记为观察数据；历史工具名不授予当前权限。
逻辑工具ID隔离不同尝试中重复的供应商ID，原ID和原版本绑定保留（[ADR-068](../../adr/068-structured-model-input.md)）。

### 8.2 思考语义

缺失/null=继承；provider_default=供应商默认；off=明确关闭；effort/budget=明确档位或 token 预算。不支持的值拒绝，不静默映射。YAML 的 off 写成引号字符串；解析到布尔值时明确报错。

### 8.3 继承

每字段依次取请求冻结的角色覆盖、冻结 Root、创建请求时的系统默认；不沿 Dispatcher/TeamLead 继承。配置解释输出字段来源与快照版本。配置解释的目标与执行能力状态分列，不能用形状合法推断控制已生效。

### 8.4 能力表

记录工具、流式、结构化输出、思考、上下文、缓存、usage/计费字段、来源和核验时间；unknown 不能当 supported。缺少必需能力拒绝对应真实调用。

### 8.5 重试

默认 max_paid_retries=0。429、5xx、断流也可能计费；错误类型只决定是否值得重试，不授权重试。只有明确策略允许、预算再次预留成功且不存在未核清费用时，才按退避/抖动重试；每次尝试保留记录。模型输出的工具调用在完整验证和持久化后才派发；断流重试不能重复派发已提交工具。Schema 纠错次数和压缩同样受付费与预算策略控制。

## 9. 工具、权限与沙箱

### 9.1 注册与分类

ToolRegistry 注册角色、参数/结果 Schema、side_effect（none/workspace/external）、幂等属性、超时、取消、诊断/控制类别。只有 Worker 可执行业务命令。模型不能通过自行填写 tool class 或“只是检查”改变权限。

### 9.2 工具集合

Dispatcher：计划、disposition、change_task、accept/cancel、问题、read_artifact、deliver。TeamLead：WorkOrder/ChangeOrder、问题、受控只读视图、转交/返工、经验报告。Worker：文件、run、受限 op 查询/输出/取消、ask/progress、ack_change、submit/note、recall/load_memory。记忆未启用时返回明确不可用。

### 9.3 检查分支

所有接口先核真实宿主身份、作用域、角色、代次及预期版本。业务操作再核 disposition、request/plan/task/instruction 应用、暂停/UNKNOWN、路径/网络、最新政策/记忆撤销、工具允许列表及普通预算；派发前再次核验。

控制接口不套用“必须已应用/不能暂停/普通预算充足”这一组门禁，否则 ack/cancel 会被自身前置条件锁死。但控制接口仍只能读/确认/取消自己范围内的对象，有独立配额和状态前置条件。UNKNOWN 核对需运行时批准的专用诊断或可验证外部事实；不能给任意 run 免检。submit/新 candidate/普通 review 仍计普通额度，已批准状态的负面撤销及必要结算保留控制通路。

### 9.4 文件工具

逻辑路径 /work 读写、/input 只读。用目录句柄和 openat2 限定根、防符号链接/路径穿越；覆盖带 expected_sha256，patch 必须唯一匹配。读取分页/限量，搜索沿同一受限目录授权边界执行，可由固定功能的文件代理完成，不赋予任意宿主命令能力。文件写也是 workspace 副作用，须具备操作身份、版本、幂等与崩溃语义。S1.2 的真实 input 挂载尚未接入，进程 /input 为空只读目录。

### 9.5 操作生命周期

run 支持 argv 或 shell、/work 下 cwd、默认 120 秒/最大 600 秒、前后台和有界输出。先持久操作意图，启动后追踪进程树和输出。取消 TERM→等待→KILL，只有实际查验退出才能确认终止；超时/取消不自动证明副作用未发生。error_signature 归一化供检索，原始证据仍按政策保留。

目标结果语义区分已结算失败与 UNKNOWN：强隔离、network=none、cgroup证明全部后代退出且完整前后工作区清单及差异已记录时，非零退出、超时、输出超限可以结算为 FAILED/TIMED_OUT。清单不全/超限、退出未证明、执行器异常或结果未持久化保持 UNKNOWN。成功或失败均不推断没有文件副作用。

剩余 UNKNOWN 由 Root/受信宿主以 request/op、CAS、结论和证据专用核对，写原子事件并支持同键重放；任意 run 不获得核对豁免。核对不能冒充原始进程退出证据，不能把迟到普通结果自动升级为当前结论。详见 ADR-065 与[当前进程结算契约](../../implementation/S1-process-settlement.md)；强隔离正向与实际部署范围仍按独立证据验收。

### 9.6 bwrap

挂载只读系统运行文件、受控 /etc 白名单、/input，只读额外挂载来自可信配置；/work 独立可写，/tmp 与临时 HOME 隔离；PID/IPC/UTS/网络命名空间和清理按实际支持检测。显式构造 envp，不继承 wlsd 环境/密钥。默认网络 none；host 是显式高权限配置，不假装具备域名白名单。doctor 检查实际 bwrap/AppArmor/user namespace 支持，不靠发行版名称保证隔离。

### 9.7 cgroup 与弱降级

首选系统服务委派下的每团队 cgroup，fork/exec 前加入，设置进程/内存限制；结束写 cgroup.kill 并等待 populated=0。启动检测控制器、委派与 systemd 配置；权限缺失时默认拒绝需要强隔离的真实工具。

若用户显式配置 allow_weak_isolation，可使用进程组/超时作开发降级，但 setsid 等可逃离组，不能证明全部后代被杀或具有相同资源上限。doctor、运行状态和报告必须显示弱模式；残留无法证明时 cleanup_status 不能 DONE。打包的 service 是未安装样例，不会自动启动服务。

### 9.8 环境卡片

按可信模板在隔离环境执行有界检查命令，记录工具路径/版本/调用示例和未安装项。模板版本、检查结果、沙箱能力参与卡片哈希。卡片不是权限授予，也不能把缺工具当授权安装。

### 9.9 真实工具派发约束

工具由宿主静态注册，业务/诊断/控制类别不可由模型改变。新业务必须取得 Store 事务授予的一次性 `dispatch_claimed=true`；同命令返回 RUNNING 的重放不是第二次执行许可。原结果、原始十字段 tuple、stdout/stderr 和哈希持久化；AMEND/取消/恢复后的旧结果只保留为历史，不自动核清 UNKNOWN。结果存储失败立即阻止当前团队/代次的新业务，避免丢失结算后继续写入。

文件代理使用 openat2 限根、合作锁、旧 SHA、原子 rename 与同步；进程采用固定 SHA 运行文件、只读挂载、显式 env 和已委派 cgroup。生产入口没有隐式弱回退；取消根据明确的停止策略请求退出并确认后代。团队工作目录和完整执行策略第一次绑定后不可变，控制数据库不能进入业务 workspace。

doctor 只读观察前置条件，不执行模板检查或调整系统政策。同步运行器、结果分页和内部监督回归不能替代强环境正向/逃逸、后台 run、残留 cgroup 恢复或跨进程取消的产品验收。完整约束见 [Worker 工具契约](../../implementation/S1-worker-tools.md)。

### 9.10 问答与提交工具

执行策略保持，模型输入仅声明当前获准的Worker ask/submit；submit还要求fs_read授权和绑定目录。ask保留原问题并创建精确等待，普通wake不能代替ANSWER；管理调用按捕获目标仅声明answer_question/forward_question或check_submission，模型不填目标ID、版本或身份。提交字节、原binding、自检和检查分别不可变；本地检查通过需要证据一致性，不能与fail/not_run或已知未决问题矛盾。工作流接口详情见 [S1.4 契约](../../implementation/S1-workflow-runtime.md)。

## 10. 交付与清理

### 10.1 包与验收

交付包含 manifest、说明、完整需求原文、成果、验收证据、限制、未知副作用、经验报告/明确待办。运行时核完整当前版本、不可变哈希和全部必需任务及审核。先写临时包并 fsync 文件/目录、原子发布，再持久记录包引用；崩溃恢复能区分未完成/已发布包，不能丢失唯一成果。

### 10.2 回执

回执固定 package ID/hash、请求与计划修订、接收主体和方式。CLI durable_local 可在完整包持久写入约定本地交付目录后由 Root 记录本地交付回执；这是已配置的本地交付语义，不声称用户已阅读。API/MCP 用显式 ack 确认正确包，取回失败不清理。GET/QUERY 不产生确认。回执丢失可精确重试，同键异包拒绝。

### 10.3 可恢复收尾

业务终态与 cleanup_jobs 创建同事务，待办不随 requests 删除级联消失。流程为：停止新业务→处理在途/UNKNOWN→确认受控进程退出→不可变成果/回执和经验收尾落盘→登记批准保留范围→删除清单内临时文件→删请求私有行→标记待办完成。每步有幂等检查点；经验未完成、唯一成果未安全转存或未知副作用未核清时保留必要数据并说明阻塞。

重启扫描全部未完待办，包括 DELIVERED/FAILED/CANCELLED/SUPERSEDED。失败保留 retry/error，不改变成功业务结果。失败报告列已完成成果、失败原因与未决副作用。清理白名单来自受控资源清单，不按任意路径前缀删除。

建议默认保留获准交付包/经验和 30 天回执，删除临时 workspace/input/transcript/trace/op 输出与请求私有数据库记录。记忆反馈仅按批准政策保留。定期 VACUUM 是空间回收，不是安全擦除；Git 历史、备份和远端副本另行处理。M1保留合成资源状态；受控目录阶段与私有行清除分别记录，当前能力见[STATUS](../../STATUS.md)，不把单阶段checkpoint称作全局已清理。

## 11. 记忆（详见 03）

S3 拟实现四类四态、版本化 Markdown/Git 内容、SQLite 检索/反馈、规则确定性加载、卡片/主动/错误触发。使用绑定 memory_id/revision/load_id，修订 expected_base_revision CAS，统计与政策按版本/场景处理；加载不等于使用，任务成功不等于记忆有效。撤销先提交门禁，再通知和清副本；过滤可见范围/适用性后再 limit。

## 12. 接口

### 12.1 CLI

当前 `wls` 保留配置/Schema、submit/show/events/budget/config-snapshot、run-fake、amend/cancel/pending、init/doctor/tool-query，已有pump-fake/inbox/history/wait/wake和questions/submissions/answer；交付入口为deliveries/experience/closeout、publish-delivery/verify-delivery/ack-delivery；受控目录入口为allocate-workspace/owned-workspaces/cleanup-workspaces。目录映射和回执使用显式参数；只读查看不接管写者或代签接收。answer及ACK在写者前预检精确对象，拿到写者后仍核当前授权和完整版本；文件发布后最终提交再次复核。具体行为见 [S1.5契约](../../implementation/S1-acceptance-delivery.md)，历史入口的边界仍见对应契约。watch/ls、replace、cleanup retry、trace与wlsd仍待实现；S1前移single-agent对照，S3有memory管理。原 `wls861 demo` 继续M1合成演示。

### 12.2 本地 API

拟采用权限 0600 的 Unix 套接字 HTTP/JSON 与 SSE，身份/权限仍由宿主发行。请求/消息/事件/交付查询是明确接口；交付确认使用独立 POST ack。SSE 使用已持久事件 ID，断线从 Last-Event-ID 续传；清理后返回回执/过期状态，不声称历史永久可取。

### 12.3 MCP

S4 实现经过同一入口的 submit/status/amend/answer/get_delivery/ack/cancel。协议版本与 C++ 库选择在开工时核验，不能根据旧 SDK 列表冻结事实。工具返回结构合格不授予跨项目或跨 Root 控制权。

### 12.4 事件

事件覆盖请求/计划/任务/团队、AMEND 待处置与处置结果、说明/应用、操作意图/结果/核对、问题、候选/审核/失效、经验待办/完成、预算尝试/未知费用、交付/回执及清理检查点。状态和事件一起提交；事件消费另有持久处理记录，不用一个 command_id 同时冒充业务幂等。

## 13. 配置

示例位于仓库 config/examples；按请求冻结 system defaults、功能 Root/角色覆盖、模板/能力表和上下文依赖。S1.1 已接入严格 LibYAML 加载器、完整冻结快照、离线恢复与字段来源解释。配置检查包括类型、引用、能力、预算、审核双名额、隔离等级、确定性验收器、存储耐久性和保留规则。默认 fake、memory.enabled=false、real_calls_enabled=false、max_paid_retries=0。通过配置检查不代表已执行环境 check、沙箱、真实模型或清理；未实现的政策执行器仍按任务卡补齐。

### 13.1 存储准入窗口

存储行数和事件容量纳入冻结system.limits.store_capacity。业务与控制分别计数，恢复维护单列；
准入同时核对worker/团队/返工的六事件生命周期预算。旧快照整块缺失使用发布时的旧常量，不读取
新默认或改写hash。告警和容量暂停与触发它的状态同事务；已承诺副作用必须保有派发/结算控制空间。
Root以证据和窗口CAS检查点续进；原审计、幂等结果和所有语义/业务预算不重置。容量暂停是独立准入
状态，不代替业务WAITING或AMEND。实现字段与控制边界见[容量契约](../../implementation/S1-capacity-windows.md)。

## 14. 存储

### 14.1 目录

拟使用数据根下的数据库、artifacts、workspaces、inputs、transcripts、traces、deliveries、memory、cleanup staging 与轮转日志。目录和资源归属由运行时创建/登记；从模型传入的路径不能成为删除授权。

### 14.2 数据库与耐久性

以 db/schema.sql 和 db/README 为结构/示例事务契约，C++ Store 另有实际源码和回归。005 保留非空 402 数据并升级到 403，保存不可变工作目录/策略、执行结果和二进制输出；S1.3 的 006 保留非空 403 数据并升级到 404，保存角色待办/领取、等待和完整反馈。007保留非空404升级405，保存原问题/答案/转发、完整提交字节、团队检查与返工计数。008保留非空405升级406，新增当前验收/报告/交付/回执事实并复用独立经验与收尾作业。009保留非空406升级407，追加受控资源所有权和清理检查点。已发布schema/004–009字节均保留。默认 WAL + synchronous=FULL + foreign_keys=ON；只读连接不能关闭安全选项。NORMAL 必须显式选择并声明不同断电边界。Python 参考测试不证明 C++ 行为，C++ 临时库测试也不证明 MemoryEngine 或整机断电可靠性。

## 15. 可观测性

记录每次模型尝试的调用/预算/费用状态、各修订和代次、实际工具操作、候选/审核绑定、经验待办、清理检查点和隔离等级。追踪与日志按作用域及保留政策处理；报告已知、未知、未执行和失败，不泄露凭据。用量统计明确 NULL 和被删历史的范围。

## 16. 技术栈与现有代码承接

S1 工程默认：C++20/CMake；Asio/Beast/OpenSSL；JSON/YAML 与 draft-07 校验库；SQLite WAL FULL；有界日志；bwrap/cgroup；ULID。逐模块引入依赖并保留 Linux 平台隔离，不能用建立空文件替换现有源码。

标准构建入口为 `make -j2 test PYTHON=.local/test-venv/bin/python`，另有 CMake/CTest；先在该环境按 requirements-test.txt 安装契约测试依赖。M1 内核仍无第三方依赖；新 S1 库使用 Boost 1.83+、SQLite 3.37+、OpenSSL 3+、LibYAML 0.2.5 及固定 Valijson v1.0.6 头，来源与许可证见 [third_party](../../../third_party/README.md)。当前 include/wls、src、tests 和 Journal 测试全部保留；新 Store/Agent/Sandbox 接口复用身份、版本、幂等和验收语义。是否重排目录是可逆实现选择，不是重新开发所有模块的理由。

## 18. 风险与验收要求

S1.6发布门禁补充：严格构建和UBSan测试以非root身份执行；故障注入只能调整自建临时夹具，
且必须确认丢包/坏包已真实产生后再调用运行器。新回归同时核验正常清理不改变交付原字节和
只读权限。开发分支应用补丁前的旧源码CI成功不能代替新源码验证，最终主分支须有同一SHA的CI结果。
实际记录见[发布复验](../../reports/s1-owned-cleanup-followup-validation.md)。

必须有针对性的反例：遗漏 AMEND 任务继续暂停；旧计划/说明/模型结果不能盖新版本；暂停/预算满仍能 ack/cancel/核对；workspace UNKNOWN 不盲重做；普通 Dispatcher/Worker 全满时审核仍能启动；请求配置不漂移；依赖变则缓存指纹变；每次重试计费，未知费用不归零；终态崩溃继续清理/经验待办；Schema pass 不能代替证据；记忆旧版本不继承新版本成绩、CAS 冲突不覆盖、撤销即刻阻断后续派发、可见过滤先于 limit。

全部用例的计划、执行结果和豁免分别记录。不得修改原档案“未执行”单元格，不以 SQLite 建表成功或 Schema 样例通过证明真实多 Agent 系统已可用。

### R2 拒绝后继约束（ADR-070）

否定验收与TeamLead返工耗尽不隐式发新说明。Dispatcher可捕获原提交及任务版本后，
在冻结共享返工额度内请求保持TaskBrief的修订，或为该被拒提交创建一次用户问题。
原成果、检查、拒绝事实和累计消耗保持不变；新任务修订必须经过TeamLead新说明及Worker确认。
用户回答只解除对应等待，不授予更多返工额度，不替代AMEND/CANCEL或核对UNKNOWN。
实现及验收边界见 [ADR-070](../../adr/070-bounded-rejection-followup.md)。
